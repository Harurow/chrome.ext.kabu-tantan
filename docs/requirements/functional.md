## FR-04 TradingView から遷移先サイトを開ける

TradingView のチャート画面で、表示中の銘柄について遷移先サイトを開けること。

- チャートの右クリックメニューに項目を追加する
- **右クリックメニューの拡張は、チャート領域上で右クリックしたときに限る。**
  ウォッチリスト・ツールバー・銘柄検索など、チャート以外を右クリックしても項目を追加しない
  （表示中の銘柄と無関係な場所で、その銘柄のリンクを出さないため）
- ツールバーに専用ボタンを置き、そこからも開ける
- 銘柄コードが取得できないときはボタンを出さない

> **FR-19 との関係（2026-08-23 追記 / 同日の実 DOM 調査を反映）:**
> 上記の「チャート以外を右クリックしても項目を追加しない」は、
> FR-19（ウォッチリストの行からの起動）で**部分的に緩める**。
> 緩めるのはウォッチリストの銘柄行に限り、かつ「右クリックしたその行の銘柄を出す」ことが条件。
> **表示中チャートの銘柄を他の場所で出さない**という本条の目的自体は変えない。
>
> 実 DOM 調査で、ウォッチリストの行が銘柄を保持していること、およびチャート由来・
> ウォッチリスト行由来・銘柄検索由来を判別できることが確認できた（FR-19 参照）。
> **FR-19 が未実装のあいだ、本条はそのまま有効。** FR-19 が満たされた時点で、
> 本条の禁止対象から「ウォッチリストの銘柄行」を除外する
> （ツールバー・銘柄検索・行を特定できない場所は引き続き禁止）。

**修正履歴（2026-08-23 判明 → 同日修正）:**

FR-12 の検証（`docs/SELECTOR-CHECK.md`）の初回実行で、TradingView の検出用セレクタ
4対象のうち2対象が**実サイトでヒット 0 件**だった。

| ヒット 0 件だった対象 | 検証で分かっていること |
| --- | --- |
| ツールバーへの挿入先（「株Link」ボタンの置き場） | 検出用セレクタのヒットが 0 件。ページ自体には到達している |
| 右クリックメニュー | 検出用セレクタのヒットが 0 件。右クリックでメニューは開いている |

チャート本体とオーバーレイレイヤーの検出は正常だったが、**拡張機能が実際に注入した要素は

追加項目も出ていない可能性が高い**（目視確認は未実施）。

**この検証で分かるのはヒット件数までで、なぜ 0 件なのかは分からない。**
実 DOM は未確認であり、原因の特定は修正タスクで行う。

> 別途 developer が手動で調べた範囲（2026-08-23）では、依存しているクラス名が変わり、

**この破損は 1.10.1 で修正済みのため、現在の `docs/SELECTOR-CHECK.md` には残っていない**（TradingView 4対象はすべて ✅）。

修正内容: 検出用セレクタ2値の差し替え、銘柄取得を canvas 経路に統一、

## FR-07 遷移先サイトを定義で管理できる

遷移先サイトは1箇所の定義で管理し、追加・削除がそこだけで完結すること。

- 銘柄コードを URL に埋め込めること
- 国内株と米国株で異なる URL 形式に対応できること
- 米国株に対応しないサイトは米国株のメニューに出さないこと

**判定基準（TradingView の「株Link」ボタンメニュー、2026-08-23 追加）:**

不整合が残っているのはボタンメニューだけなので、判定基準はここに限って書く。

1. 米国株を表示しているとき、**米国株用の URL 形式を持たないサイトがボタンメニューに出ない**こと。
   「出るがクリックしても何も開かない項目」が 0 件であること
2. 国内株を表示しているときに出る項目は、現行と同じ一覧であること
   （米国株向けの絞り込みで国内株の項目が減らない）
3. 項目の並び順が、オプションページで設定した並び順（FR-09）と一致すること
4. 同じ銘柄について、ボタンメニューの情報サイト項目が、
   右クリックメニュー（FR-18）の入れ子に出る情報サイト項目と**同じ集合・同じ順序**であること

**やらないこと:**

- 証券会社の項目（FR-06）をボタンメニューに追加する／削るといった変更はしない。現行のまま
- ボタンメニューの見た目・開閉の作りは変えない（FR-18 のような入れ子化はスコープ外）

## FR-12 実サイトに対してセレクタの生存を判定できる

注入対象サイトの改修で**検出用セレクタ**が効かなくなったことを、
利用者からの報告を待たずに、開発者が任意のタイミングで確認できること。

**検証対象（検出用セレクタ）** — 壊れると機能そのものが消えるもの:

| サイト | 対象 |
| --- | --- |
| 楽天証券 | 銘柄コードを含む要素を探すセレクタ。**お気に入り〜株価検索の12ページすべて** |
| 楽天スーパースクリーナー | 結果一覧の銘柄コード要素を探すセレクタ |
| SBI証券 | 個別銘柄・ポートフォリオの銘柄コード要素を探すセレクタ |
| SBI銘柄スクリーニング | 結果一覧の銘柄コード要素を探すセレクタ |
| TradingView | チャート本体の検出、ツールバーへの挿入先の検出、右クリックメニューの検出 |

> 楽天証券は同一セレクタを使うページが複数あるが、**間引かない**。
> セレクタが同じでもサイト側の DOM は個別に改修されうる。

**検証対象外（模倣用クラス）** — 壊れても見た目が崩れるだけのもの:

- 拡張機能が見た目を合わせるために自分で付与するクラス（TradingView のメニュー項目・区切り線など）
- これらは人の目で確認する（`docs/MANUAL-CHECKLIST.md` A-9）

**判定基準:**

1. 検証対象のセレクタごとに「対象ページでヒットした要素数」を出力すること
2. 各対象ページについて、以下の3状態を区別できること

   | ページ自体を識別する手がかり | 銘柄要素のセレクタ | 判定 |
   | --- | --- | --- |
   | ヒットする | 1件以上 | **正常** |
   | ヒットする | 0件 | **破損**（サイト改修でセレクタが効かなくなった） |
   | ヒットしない | — | **ページを開けていない／ページ構造そのものが変わった** |

   > 「保有銘柄が無いので0件」と「セレクタが壊れて0件」を取り違えないための区別。
   > 実現手段（実装側のセレクタ定義に何を持たせるか）は設計側で決める。
   >
   > **この表だけでは分類を誤る場合があることが実データで判明した。**
   > ページ識別セレクタがヒットしなくても、題名から対象ページに到達できたと分かる場合がある
   > （2026-08-23、楽天証券・国内株式・株価検索）。この是正は FR-22 で扱い、1.12.2 で実装し、
   > **2026-08-24 のフル実行で実データとして確認した**（FR-22 判定基準 4）。

3. 「破損」が 1 つでもあれば、成功と失敗を機械的に区別できること
   （終了コード等、目視によらない手段で区別できること）
4. どのサイトのどのページのどのセレクタが破損したかが、出力だけで特定できること
5. **「破損」または「ページを開けていない」と判定した対象について、
   原因の切り分けに使える手がかりを結果に残すこと**（2026-08-23 追加）

   目的は、次の3つを**結果ファイルを読むだけで**区別できるようにすること。

   | 疑うこと | 手がかりの例 |
   | --- | --- |
   | ページの URL が変わった | 到達先の題名が対象ページと別物 |
   | ログイン画面・エラー画面に飛ばされた | 到達先の題名がログイン系、見出しの構造が対象ページと違う |
   | 描画待ちが足りず、判定時点でまだ中身が無い | 題名は対象ページだが、主要コンテナが見当たらない |

   **残すもの:**

   | 内容 | 粒度 |
   | --- | --- |

## FR-15 1回の実行で全対象サイトを検証し終えられる

FR-12 の検証を、**1回の実行で最後まで通せる**こと。

- ログインは実行の冒頭に、サイトごとに 1 回だけ行えばよいこと
  （検証項目ごとに再ログインを求められないこと）
- 検証の途中で利用者に追加のログインを要求しないこと
- **楽天証券の12ページと TradingView への遷移は自動で行うこと。**
  利用者がこれらを手で開いて回らずに済むこと
- 以下は例外とし、**利用者が実行前にタブを開いておく**。
  ツールはそのタブを探して判定する

  | 対象 | 利用者がタブを開く理由 |
  | --- | --- |
  | SBI証券・個別銘柄 / ポートフォリオ | ページの URL がセッションと遷移経路に依存し、URL の指定だけでは開けない |

  | SBI銘柄スクリーニング | 同上 |

  > タブが無い場合は「破損」ではなく「未実施」として記録する（FR-17）
- ログイン待ちに時間制限を設けないこと（所要時間は利用者次第）
- あるサイトの検証が失敗しても、残りのサイトの検証が続行され、
  最後まで実行された結果が出力されること

## FR-22 到達できているページを「未到達」と判定しない ✅

FR-12 の検証で、**対象ページに到達できているのに検出用セレクタが 0 件**の場合を、
「ページを開けていない（⚠️）」ではなく「破損（❌）」として扱えること。

**困りごと:** 2026-08-23 の実行で、楽天証券・国内株式・株価検索は
題名から到達が確認できるにもかかわらず ⚠️ と分類された。
一方、同じ ⚠️ には「ツールがエラーページに飛ばされた4ページ」も混ざっている。
**直すべきもの（拡張の破損）と、直さなくてよいもの（ツールの到達失敗）が同じ記号になる。**
結果ファイルを開いて手がかりを読まないと区別できず、判定を機械的に扱えない
（FR-12 判定基準 3 の「破損があれば失敗として区別できること」が実質的に働かない）。

**判定基準:**

1. 対象ページへの到達可否を、**ページ識別セレクタのヒット数だけで決めないこと**。
   到達したと判断できる別の手がかり（到達先の題名など）を判定に使うこと
2. 到達したと判断できる場合、検出用セレクタが 0 件なら **❌（破損）** と分類すること
3. 到達したと判断できない場合は、従来どおり **⚠️（未到達）** のままとすること
4. 2026-08-23 のケースで、株価検索が ❌、楽天の他4ページが ⚠️ に分かれること
   （既存の実データで検算できること。**検算に使う実データは 3回目版 `git show e0d3c5e:docs/SELECTOR-CHECK.md`。
   そこでは5ページとも ⚠️ で、この分類は本要件の実装で変わるため次回の実行では再現しない**）
5. ❌ に分類された対象は FR-12 判定基準 3 の終了コードに反映されること
6. 誤って ❌ にした場合の害（存在しないページを破損と呼ぶ）を避けるため、
   **到達の判断根拠を結果ファイルに残すこと**（FR-12 判定基準 5 の手がかりの範囲を超えないこと）

**やらないこと:**

- ページ識別セレクタの仕組みそのものを廃止しない（到達判断の材料は増やすが、置き換えではない）
- 到達判断のために新しい情報（HTML・スクリーンショット・URL）を記録しない（CON-10, NFR-12）
- 判定記号を増やさない（✅ / ❌ / ⚠️ / — の4つのまま）

**決着（2026-08-23 / 1.12.2）:**

「到達したと判断できる」の決め方は、**対象ページごとに正解の題名を持つのではなく、
「未到達の目印」（エラー画面・ログイン画面の題名）に当たらなければ到達とみなす**方式で決着した
（ADR-0006）。持つ情報が対象ページ数ではなく目印の数で済むため、
未確定として挙げていた二重管理の増加（NFR-13 の趣旨）は最小限にとどまった。

> 代償として、**対象ページとは別の正常なページに飛ばされた場合も「到達」と見なす**。
> このとき ❌（破損）に分類されるため、**❌ を見たらまず手がかりの題名が対象ページのものかを人が読む**
> 運用が要る。
>
> **2026-08-24 に実例が出た。** 楽天証券・株価検索（FR-20）が ❌ に分類されたが、
> 到達判定は「未到達の目印に当たらない」しか見ないため、
> 対象ページ（検索結果画面）に着いているのか別の正常なページに着いているのかは区別できていない。
> **この ❌ は「破損の確定」ではなく「人が題名を読んで判断すべき対象」である**（FR-20 参照）。

### FR-13 注入失敗時のリトライ ❌

固定待機時間内にサイト側の描画が終わらなかった場合でも、最終的にメニューが注入されること。

   > 件数が版ごとに揺れても判定できる。4回目版の実データでは全20対象で 注入 ≤ ヒット が成立しており
   > （20/20・553/550・1150/50・24/2・1/1・1/0）、現状を追認する形の条件になっている。
   >
   > **(c) の限界。** 注入がヒットより構造的に少ない3対象
   > （楽天証券・ランキング・楽天内 553/550、楽天スーパースクリーナー 1150/50、
   > SBI証券・ポートフォリオ 24/2）では、二重注入しても 注入 ≤ ヒット を満たしてしまうため検知できない。
   > この3対象は**実サイトで同じ銘柄コードにメニューが2つ出ないことを目視で確かめる**（判定基準 3）。
   >
   > **注入 = ヒット を求めるのは上表の8対象だけ。** この8対象は「ヒットした要素それぞれに
   > 1つ注入する」関係が4回目版で成立しており、比率が崩れたら実装の退行を疑える。
   > **崩れた原因がサイト側の変更だと分かった場合は、その旨を記録したうえで例外として扱ってよい**
   > （比率そのものはサイトの DOM 構造に依存するため）。
   > 残る3対象と (a) の4対象は比率が 1:1 でない、または実装前で比率が分からないため、
   > 注入 ≤ ヒット だけを課す。
   >
   > **残り5対象（楽天証券のお気に入り / お気に入り編集 / 保有商品一覧2ページ / 株価検索）は
   > (a) にも (b) にも含めない。** 4回目版の注入は 0 件だが、原因は本要件ではなく
   > ツールがページに到達できていないこと（FR-23）とページ側の破損（FR-20）で、
   > 本要件を実装しても変わらない。4（a）＋ 11（b）＋ 5（対象外）＝ FR-12 の全20対象。
   >
   > **「注入」列は現在 FR-12 の判定に使わない参考値**（出典は `docs/specs/selector-check.md`
   > 「参考値（判定には使わない）」節）。本要件が満たされれば Content Script の固定待機と
   > ツールの計測タイミングの競合が解消するため、**(a) の4対象についても注入を条件にできるようになる**
   > （FR-12 の「注入 0 件の切り分け」の整理による）。FR-12 側の判定規則を変えるかどうかは別途扱う

6. **TradingView で、リトライによって注入された場合も、銘柄を切り替えたときにボタンの状態が
   追随すること**（銘柄コードを取り出せない銘柄ではボタンが消え、取り出せる銘柄では出る）。
   TradingView は自動テストの対象外（CON-08）のため、手動で確認する

   > **なぜ判定基準 5 と別に置くか:** 判定基準 5 は「注入された要素の数」しか見ないため、
   > **ボタンは出たが銘柄切替への追随だけ失われている**状態を検知できない。
   > TradingView では起動時の同じ処理でボタンの注入と銘柄切替の追随が用意されるため、
   > **ボタンだけを再試行の対象にすると追随が落ちたままになる**（下記「適用範囲」）

**適用範囲（2026-08-25 に決定）:**

対象は**注入先 5 本すべて**とする。同じ欠陥（固定待機が明けた時点で挿入先が無ければ諦める）を

TradingView のシンボル表記がこの形式のため、コピーして右クリックする使い方と直撃する。

### FR-19 TradingView のウォッチリストの行から遷移先サイトを開ける ❌

TradingView のチャート画面のウォッチリストで銘柄行を右クリックしたとき、
**その行の銘柄**について遷移先サイトを開けること。

**困りごと:** 現在はウォッチリストで見つけた銘柄を調べるのに、
いったんチャートの銘柄を切り替えてから右クリックする必要がある。

**判定基準:**

1. ウォッチリストの銘柄行を右クリックすると、拡張の項目が出ること
2. 出る項目の銘柄が、**右クリックしたその行の銘柄**であること。表示中チャートの銘柄ではない
   （チャートに銘柄 A を表示した状態でウォッチリストの銘柄 B を右クリックしたら、B のリンクが出る）
3. 行から銘柄コードが読み取れないときは、項目を追加しないこと（誤った銘柄のリンクを出さない）
4. メニューの形は FR-18 に従う（直下1行＋入れ子）
5. チャートとウォッチリスト以外（ツールバー・銘柄検索など）では、
   引き続き項目を追加しないこと（FR-04）
6. **国内株の行と米国株の行の両方で、その市場に応じた正しいリンクが開くこと。**
   国内株は国内株用の遷移先、米国株は米国株用の遷移先（判定は目視。
   国内株と米国株を混在させたウォッチリストで確認する）
7. **銘柄コードとして扱えない行では項目を追加しないこと。**
   指数・先物・FX・暗号資産など、既存の遷移先サイトが対象にしていない行が該当する
   （判定基準 3 の具体化。「何も起きない」が正しい挙動であり、
   誤って国内株・米国株のリンクを出さないこと）
8. **ウォッチリストをスクロールした後、および別のウォッチリストへ切り替えた後でも、
   画面に見えている行を右クリックすれば判定基準 1・2 を満たすこと**
   （行が入れ替わっても、右クリックした行の銘柄が出る）

**やらないこと:**

- **対象はチャート画面のウォッチリストウィジェットに限る。**
  ウォッチリスト専用ページ・スクリーナー・ホットリスト・ニュース等の他ウィジェットは対象外。
  そこで項目が出なくても本要件の未達としない（判定基準 5 の側で「出さない」が正しい）
- 行にホバーしたときのボタン表示・行内へのアイコン追加はしない（右クリックのみ）
- 複数行を選択しての一括オープンはしない
- ツールバーの「株Link」ボタン（SPEC-CS-12）の挙動は変えない

**FR-04 との関係:**

FR-04 は「チャート領域上で右クリックしたときに限る」と定めている。
これは「ウォッチリストで銘柄 B を右クリックしたのに、表示中チャートの銘柄 A のリンクが出る」
退行を防ぐためのもの。本要件はこの禁止を全面的に解くのではなく、
**右クリックした行から銘柄を特定できる場合に限って**対象を広げる。
判定基準 2 を満たさない実装は FR-04 違反として扱う。

本要件が満たされた時点で、FR-04 の禁止対象から「ウォッチリストの銘柄行」を除外する。
ツールバー・銘柄検索・ウィジェットの余白など、**行を特定できない場所は引き続き禁止**。

**実 DOM 調査で判明したこと（2026-08-23 / 利用者のログイン済み環境で実測）:**

**取り下げ条件（行から銘柄コードを取れない）は解消した。** 実装可能である。

| 確認したこと | 結果 |
| --- | --- |
| 行から銘柄が読めるか | 読める。各行は `EXCHANGE:CODE` 形式（例 `TSE:8253`）と<br>コード単独（例 `8253`）の両方を属性として持つ |
| 銘柄の表記形式 | チャートから取っている `EXCHANGE:CODE` と同じ形式。<br>既存の取引所コード表（`exchanges`）の解釈がそのまま通じる |
| 行の目印が安定しているか | クラス名はハッシュ付きで不安定だが、銘柄を保持する**属性**は<br>クラス名に依存せずに引ける（CON-08 の変わりやすさへの耐性は属性側が高い） |
| 右クリックメニューの器 | チャートと同じメニューが開く。器を新設する必要はない |
| 由来（チャート／ウォッチリスト／銘柄検索）の判別 | 判別できることを実測で確認。判定基準 2・5 は実現可能 |
| 銘柄を持つ行の出現範囲 | 調査時のレイアウトでは**全件がウォッチリスト内**。<br>チャート・ツールバー・銘柄検索には無い |

**残る未調査（実装時に確認する。取り下げ条件ではない）:**

| 未調査 | 影響する判定基準 | 扱い |
| --- | --- | --- |
| 米国株・指数を含むウォッチリストでの銘柄表記（調査時は全件が国内株） | 6, 7 | 実装時に実データで確認する。<br>**確認には国内株・米国株・指数を混在させたウォッチリストが要る**（利用者に依頼） |
| スクロール・タブ切り替えで行が差し替わるときの挙動（仮想スクロールの可能性） | 8 | 実装時に実サイトで確認する |

いずれも「実現できるか」ではなく「実装時にどこまで確かめるか」の問題であり、
本要件の成立を左右しない。

| 状態 | ❌ 未実装。**着手可能**（実 DOM 調査で実現可能性が確定し、取り下げ条件は解消済み） |

### FR-20 楽天証券・国内株式・株価検索でリンクメニューが出ない ❌

### FR-23 楽天証券の全12ページを検証ツールで判定できる ❌

FR-12 が対象とする楽天証券12ページのうち、現在4ページが**恒久的に判定できない**。
この4ページについても判定結果が出ること。

対象: お気に入り / お気に入り編集 / 保有商品一覧・すべて / 保有商品一覧・国内株式

**困りごと:** 2026-08-23 の実行で、この4ページは到達先の題名が
「エラー | 楽天証券[PC]」で、主要コンテナも4ページで完全に同一だった
（2026-08-24 のフル実行でも同じ）。
ツールが生成した URL を直接開いてもエラーページに飛ばされている（遷移元が要る等）。
**目視ではメニューが出ており拡張機能は正常**（`docs/MANUAL-CHECKLIST.md` C-1）。
つまり FR-12 の目的（利用者の報告を待たずに破損を知る）が、この4ページだけ達成できていない。

**判定基準:**

1. 4ページそれぞれについて、✅ / ❌ のいずれかの判定が出ること
   （⚠️ や — のままにならないこと）
2. 現状（目視でメニューが出る状態）で実行すると、4ページとも ✅ になること
3. 他の8ページの判定が変わらないこと
4. 利用者の手順の増加が、FR-15 の「例外4対象」と同程度に収まること
   （ログインのついでに開けるタブを増やす程度。1ページごとの手作業の確認にしないこと）
5. 到達のために**サイト内のリンクをたどる場合**は、下記「判定基準 5 の条件」を
   すべて満たすこと（2026-08-24 追加。**リンクをたどること自体は要件側で許可した**）

**取りうる方向（設計側で選ぶ）:**

| 方向 | 備考 |
| --- | --- |
| **到達方法を変える（ログイン済みのポータルからリンクをたどる）** | **2026-08-24 に利用者が提案。CON-10 の範囲内であることを下記で確認済み**（要件側の可否は決着。どのリンクをどうたどるかは設計側） |
| FR-15 の「利用者がタブを開いておく例外」に移す | 確実だが利用者の手順が4つ増える。判定基準 4 の許容範囲内 |

**判定基準 5 の条件（2026-08-24 に判断）:**

**条件そのものは `CON-10`「リンクのクリックを許容する条件」を正とする。**
リンクをたどってよいのは、そこに挙げた条件をすべて満たす場合に限る。

> **ここに条件を再掲しない理由（2026-08-25）:** 以前は同じ4項目を CON-10 と本項に
> 逐語で二重に書いていた。片方だけ直すと乖離するため、**本項からは参照だけにする。**
> 条件を足す・狭めるときは CON-10 を直す。
>
> **なぜ CON-10 に反しないか（2026-08-24 の整理）:**
> CON-10 が禁じているのは「ログイン操作の自動化」「フォーム送信」「データの一括取得」であり、
> **ページからページへ移動すること自体は既に許容されている**
> （「ログイン済みセッションで対象ページの URL へ遷移する ✓」）。
> リンクを1回クリックして移動するのは、URL を直接開くのと同じ GET 遷移で、
> サイトへの負荷も利用者が手で見て回るのと変わらない。
> **「リンクのクリックは送信ではない」と整理する。** CON-10 に許容行として明記した。
>
> 境界は「サイト側の状態を変えるか」で引く。同じクリックでも、検索条件を送る・注文を出すものは不可。
>
> **2026-08-25 の見直し:** 当初は「リンクの実体が JS 経由の POST なら、画面遷移が目的なら可・
> データ送信が目的なら不可」としていたが、**JS 経由の POST はまさに「判断がつかない」類**で
> 自己矛盾していた。たどってよい対象を**素の `<a href>` の GET 遷移**に限定する形に狭めた。
> `onclick` などの JavaScript ハンドラで遷移するものは、画面遷移が目的に見えても採らない（CON-10）。

**やらないこと:**

- ログイン操作の自動化はしない（CON-10）
- フォーム送信・データ取得はしない（CON-10）
- 利用者に4ページを1つずつ目視させる形にはしない（判定基準 4）
