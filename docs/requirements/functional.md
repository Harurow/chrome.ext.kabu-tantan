## FR-04 TradingView から遷移先サイトを開ける

TradingView のチャート画面で、表示中の銘柄について遷移先サイトを開けること。

- チャートの右クリックメニューに項目を追加する
- **右クリックメニューの拡張は、チャート領域上、またはウォッチリストの銘柄行で
  右クリックしたときに限る**（ウォッチリストの行は 1.15.0 で追加。FR-19）。
  ツールバー・銘柄検索・行を特定できない余白など、それ以外の場所を右クリックしても項目を追加しない
  （表示中の銘柄と無関係な場所で、その銘柄のリンクを出さないため）
- **ウォッチリストの行では、表示中チャートの銘柄ではなく、右クリックしたその行の銘柄を出す**
  （FR-19 判定基準 2）。行から銘柄を特定できないときは項目を追加しない
  （チャートの銘柄に落とさない）
- ツールバーに専用ボタンを置き、そこからも開ける
- 銘柄コードが取得できないときはボタンを出さない
- **銘柄コードが単独のトークンとして現れているときだけ切り出すこと**
  （FR-08「切り出してよい後続だけを許す」をこの経路にも適用する）。
  `NYSE:BRK.B` を表示中のチャートで右クリックしても `BRK` を出さない

> **FR-19 との関係（2026-08-29 更新。1.15.0 で除外を確定した）:**
> 上の1点目は 2026-08-23 まで「チャート領域上で右クリックしたときに限る」で、
> ウォッチリストも禁止対象だった。FR-19 の実装（1.15.0）に合わせて、
> **禁止対象からウォッチリストの銘柄行を除外した。**
> ツールバー・銘柄検索・行を特定できない余白は引き続き禁止で、
> **表示中チャートの銘柄を他の場所で出さない**という本条の目的は変えていない。
>
> **除外を「実装時点」で確定させた理由（analyst 判断 2026-08-29）。**
> FR-19 は実サイト未確認（⚠️）のままだが、本条の禁止は
> **「実装が何をしてよいか」の線引き**であって、FR-19 が実際に動くかどうかとは別の問題である。
> 1.15.0 の実装はウォッチリストの行でメニューを拡張するため、除外を実サイト確認まで先送りすると
> **現行実装が必須要件である本条に違反している、という誤った記録になる。**
> 加えて、FR-19 の未確認箇所（行の目印が推測値であること）が外れたときの影響は
> 「ウォッチリストで何も出ない」であり、その状態は除外の前後どちらの文言でも満たす。
> **除外を先に確定させても隠れる不具合は無い。**

## FR-07 遷移先サイトを定義で管理できる

遷移先サイトは1箇所の定義で管理し、追加・削除がそこだけで完結すること。

- 銘柄コードを URL に埋め込めること
- 国内株と米国株で異なる URL 形式に対応できること
- 米国株に対応しないサイトは米国株のメニューに出さないこと

**判定基準（TradingView の「株Link」ボタンメニュー、2026-08-23 追加）:**

不整合が残っているのはボタンメニューだけなので、判定基準はここに限って書く。

1. 米国株を表示しているとき、**米国株用の URL 形式を持たないサイトがボタンメニューに出ない**こと。
   「出るがクリックしても何も開かない項目」が 0 件であること
2. 国内株を表示しているときに出る項目は、現行と同じ一覧であること
   （米国株向けの絞り込みで国内株の項目が減らない）
3. 項目の並び順が、オプションページで設定した並び順（FR-09）と一致すること
4. 同じ銘柄について、ボタンメニューの情報サイト項目が、
   右クリックメニュー（FR-18）の入れ子に出る情報サイト項目と**同じ集合・同じ順序**であること

**やらないこと:**

- 証券会社の項目（FR-06）をボタンメニューに追加する／削るといった変更はしない。現行のまま
- ボタンメニューの見た目・開閉の作りは変えない（FR-18 のような入れ子化はスコープ外）

## FR-08 国内株と米国株の銘柄コードを判別できる

文字列から銘柄コードを取り出し、国内株か米国株かを判別できること。

- 国内株: 4桁。**2024年以降の英字を含むコード（例 `135A`）に対応すること**
- 米国株: 英字1〜5文字。取引所コード（`NASDAQ` / `NYSE`）が付く場合も扱えること
- **日本語文中の大文字並びを誤って米国株と判定しないこと**
- **銘柄コードが単独のトークンとして現れているときだけ切り出すこと。**
  直後に続く文字が「切り出してよい」と決めたものでない場合は、何も返さないこと
  （2026-08-29 追加。下記「切り出してよい後続だけを許す」）

**切り出してよい後続だけを許す（2026-08-29 に規則の向きを変えた）:**

**原則:** 銘柄コードとして切り出してよいのは、**直後の文字が下表のいずれかに当たる場合だけ**とする。
**当たらない文字（未知の記号・数字を含む）が続く場合は何も返さない。**

| 切り出してよい後続 | 例 | 理由 |
| --- | --- | --- |
| 文字列の終わり | `AAPL` | 銘柄コードが単独で置かれている |
| 空白（半角・全角・タブ・改行） | `AAPL Apple Inc.` / `AAPL - Apple Inc.` / `AAPL ・ MSFT` | 同上。**空白で切れていれば、その先に何があっても関係ない。ただしコロンは除く**（下記） |
| **日本語の本文文字**（かな・漢字・カタカナ） | `AAPL の株価` / `AAPL株` | 銘柄コードの一部になりえず、そこで語が切れている |
| **文を終わらせる記号**（列挙する。**半角・全角の両方**） | `AAPL,` / `AAPL)` / `AAPL's price` / `AAPL;` / `AAPL!` / `AAPL?` / `AAPL。` / `AAPL、` / `AAPL」` / `AAPL）` | 銘柄コードを別の表記に**続けている**のではなく、文の中で**終わらせている**。害が生じない |

> **コロンだけは「空白で切れていれば関係ない」が成り立たない**（2026-08-29 の最終レビュー）。
> `AAPL : 100` / `AAPL　：　決算` は落ちる。**空白の種類（半角・全角・タブ・改行）を問わない。**
> 判定基準 7 の区切りが**コロンの前後の空白まで含む**ためで、
> 他の記号（`AAPL - Apple Inc.` / `AAPL ・ MSFT` / `AAPL . Apple`）は空白を挟めば落ちない。
> 詳しくは下記「許容した代償の内訳」の注。
>
> **コロン（半角 `:` / 全角 `：`）は本表に入っているが、先頭では効かない**
> （2026-08-29 の最終レビューで書き直した。当初「本表に入れない」と書いていたのは誤り）。
>
> | 位置 | 扱い | 例 |
> | --- | --- | --- |
> | **銘柄コードの先頭側** | **判定基準 7 が先に落とす。** 本表まで届かない | `AAPL: 100ドル` / `AAPL：決算発表` → 何も開かない |
> | **取引所プレフィックスの後ろ** | **本表の終止記号として働く** | `NYSE:AAPL:` / `NYSE:AAPL：` → `us AAPL @NYSE` |
>
> 先に取引所が引けている（`NYSE:`）ので、その後ろのコロンは
> **もう「取引所とコードの区切り」ではありえず、文を終わらせているだけ**である。
>
> **2026-08-29 訂正: 当初この表には「非 ASCII 文字なら許可」と書いていたが、これは誤りだった。**
> 「非 ASCII だから米国ティッカーの一部になりえない」は正しいが、
> **危険なのは「ティッカーの一部になること」ではなく「別の表記に続けていること」である。**
> 全角の連結記号（`Ｓ＆Ｐ５００` の `＆` など）は非 ASCII でありながら後者に当たり、素通りしていた。
> **ASCII かどうかは、安全性の代理指標として使えない。**
>
> **「開かない」ほうを選ぶ。** 判別できない入力では何も開かないことを正とし、
> **その結果として開けなくなる入力があっても本項の未達としない**（下記「許容した代償」）。
> 利用者は選択し直せるが、別銘柄のページを開かれると気づけないため。
> **この原則を、未知の入力に対しても貫くのが本規則である。**

**判定基準:**

1. **日本語の文中で銘柄コードを終わらせる書き方が落ちないこと。**
   `AAPL の株価` / `AAPL。` / `AAPL、` / `AAPL」` / `AAPL）` は引き続き `AAPL` を開く
2. **英文で銘柄コードを終わらせる書き方が落ちないこと。**
   `AAPL,` / `AAPL)` / `AAPL;` / `AAPL!` / `AAPL?` / `AAPL's price` / `AAPL Apple Inc.` は
   引き続き `AAPL` を開く。**`AAPL:` は含めない**（判定基準 7 の代償。下記「許容した代償の内訳」）
3. **別の表記に続いているものは何も開かないこと。**
   `BRK.B` / `BRK-B` / `BRK/B` / `A+` / `S&P500` / `U.S. 株式` / `A/B テスト` / `SP500` / `A_B` は何も開かない
4. **列挙にない文字が続いたら何も開かないこと**（`AAPL#` / `AAPL=` / `AAPL*` など）。
   **新しい記号が現れても要件と実装を直さずに 3 を満たせること**が本規則の目的
5. **連結記号は、半角・全角・字形の違いで結果が変わらないこと**（2026-08-29 追加）。
   同じ役割の記号は同じ結果になること

   | 半角 | 同じ結果にすべきもの |
   | --- | --- |
   | `S&P500` | `S＆P500` |
   | `BRK.B` | `BRK．B` |
   | `A-Z` | `A－Z` / `A–Z` / `A—Z` / `A−Z`（全角ハイフン・ダッシュ類） |
   | `AAPL/MSFT` | `AAPL／MSFT` |
   | `A+` | `A＋` |
   | （半角に相当なし） | `AAPL・MSFT`（中黒） |
   | `AAPL-MSFT` | **`AAPLーMSFT`（長音 U+30FC）/ `AAPLｰMSFT`（半角長音 U+FF70）** |
   | `A:Z` / `SP:SPX` | **`A：Z` / `SP：SPX`（全角コロン U+FF1A）** |

   > **長音符は「文字」だが例外として許可しない**（2026-08-29 判断。当初は許可のままとしたが、
   > 同日の再レビューで塞ぐ側に改めた）。Unicode 上は記号ではなく文字（Lm）だが、
   > **日本語入力ではハイフンを打つと長音符が出るため、ダッシュの代用として実際に打たれる。**
   > `BRKーB` は本項が消しにいった偽陽性そのものである。
   > **半角形 `ｰ`（U+FF70）も同じ扱いにする**（判定基準 5 の趣旨）。
   >
   > **反復記号（`々` U+3005 / `ゝ` U+309D / `〆` U+3006）は許可のままとする。**
   > 同じ「文字なのに記号に見える」仲間だが、**ダッシュや連結の代用に使われることが無い**
   > （`AAPL々` に対応する表記が存在しない）。**例外にする基準は「文字かどうか」ではなく、
   > 連結記号の代用として実際に打たれるかどうか**であり、長音符2字だけがこれに当たる。

6. 判定基準 1〜5・7 が、**銘柄コードを取り出すすべての経路**で同じ結果になること（下記「適用範囲」）
7. **取引所プレフィックスの形（`EXCHANGE:CODE`）で、対応していない取引所が付いている入力は
   何も開かないこと**（2026-08-29 追加。レビューでの実測から）。
   **コロンは半角・全角の両方を区切りとして扱う**（判定基準 5）。
   下表はいずれも**実在する別企業**を開いていた

   | 入力 | 開いていたもの | 本来 |
   | --- | --- | --- |
   | `SP:SPX`（S&P500 指数） | **`SP`（SP Plus Corp）** | 何も開かない |
   | `CME:ES1!`（先物） | **`CME`（CME Group）** | 同上 |
   | `ICE:BRN1!`（先物） | **`ICE`（Intercontinental Exchange）** | 同上 |
   | `SIX:NESN`（スイス取引所） | **`SIX`（Six Flags）** | 同上 |
   | `TVC:NI225` / `IDX:BBCA` / `LSE:VOD` / `OANDA:EURUSD` | 各トークン | 同上 |
   | `XETR:BMW` | `XETR`（実在しない。404） | 同上 |
   | `A：Z` / `S：SPX` / `SP：SPX`（全角コロン） | **`A`（Agilent）/ `S`（SentinelOne）/ `SP`** | 同上 |

   > **`S&P500` を止めたのと同じ害である。** 本項は `S&P500` から `S`（SentinelOne）を
   > 切り出さないために規則を作り直した。**`SP:SPX` は同じ指数の別表記で、同じ別企業ではないが
   > 同じ「実在する別企業を開く」形**であり、片方だけ許す理由が無い。
   >
   > **`EXCHANGE:CODE` は FR-14 が狙った主用途そのもの**（TradingView のシンボルをコピーして
   > 右クリックする）であり、**害の出る経路として最も太い。**
   > また FR-19 判定基準 7 は、ウォッチリストの行では指数に何も出さないと定めている。
   > **同じ文字列が経路によって違う結果になるのは判定基準 6 に反する。**

> **許可する終止記号の網羅は仕様側で詰める。** 要件が定めるのは判定基準 1・2・5 を満たすことで、
> どの文字を並べるかは実測に委ねる。**足りなければ判定基準 1・2 が落ちるので、機械的に気づける。**
>
> **NFKC 正規化だけでは判定基準 5 を満たさない**（2026-08-29 に実測）。
> `＆` `．` `－` `／` `＋` は半角に畳まれるが、**中黒 `・`・ダッシュ類 `–` `—` `−`・長音 `ー` は畳まれず、
> そのまま素通りする。** 手段の選択は仕様側だが、**正規化を入れたら満たせる、とはならない。**

**やらないこと（2026-08-29 に決めた範囲）:**

- **クラス株そのものを開けるようにはしない。** `BRK.B` は「何も開かない」が正しい挙動であり、
  バークシャー・ハサウェイ B 種のページを開くことは本項に含めない
  （下記「積み残し（クラス株の表記そのもの）」）
- **記号を個別に判断する運用はもうしない。** 未知の記号は既定で「切り出さない」側に落ちるため、
  記号が1つ見つかるたびに要件を直す必要が無くなった（下記「なぜ向きを変えたか」）
- **`.` を条件付きで許可する例外は設けない。** 「`.` の後ろが空白か終端なら許す」とすれば
  `AAPL.` を救えて `BRK.B` は止められるが、**危険な文字に例外を戻す形**になり、
  本規則が消したはずの特例判断が復活する。`AAPL.` が落ちる代償を受け入れる側を採る
- **全角英数字で書かれた銘柄コードを認識するようにはしない**（2026-08-29 判断。下記
  「積み残し（全角英数字の認識）」）。`ＡＡＰＬ` / `７２０３` は現在も何も開かず、**それは安全側**である。
  本項は**害を消す作業**であり、認識できる入力を増やす作業と混ぜない

**なぜ向きを変えたか（2026-08-29 の記録）:**

規則は当初、**害のある区切り記号を禁止列挙する**形だった。`.` → `-` `/` → `+` → `&` と、
**同じ日に3回、同じ形の発見を繰り返した。** 毎回「害のある記号が1つ見つかる」→「要件を直す」
→「必須要件が ⚠️ に落ちる」→「実装して ✅ に戻す」を回した。
**これは列挙の漏れではなく、規則の向きの問題だった。**

| | 禁止列挙（〜2026-08-29） | 許可列挙（現行） |
| --- | --- | --- |
| 未知の後続文字が来たら | **切り出す**（＝別銘柄を開きうる） | **切り出さない** |
| 危険側に倒れるのは | **未知の記号すべて** | 無し |
| 新しい表記が出たら | 要件と実装を直す。**それまで害が出続ける** | 直さなくてよい |

**禁止列挙は、未知の入力で「開かないより悪い」側に倒れていた。** これは本項の原則と向きが逆である。
実測（2026-08-29）でも、禁止列挙の5記号を除いた ASCII 記号 **27種すべてが切り出していた**
（`! " # $ % ' ( ) * , : ; < = > ? @ [ \ ] ^ _ \` { | } ~`）。数字も同様（`SP500` → `SP`）。

**禁止列挙で挙げていた5記号と、その実害（経緯として保存）:**

| 記号 | 誤って開いていた例 | 開いていたもの | 現実の経路 |
| --- | --- | --- | --- |
| `.` | `BRK.B` / `NYSE:BRK.B`（クラス株）、`U.S. 株式` | `BRK` / **`U`（Unity Software）** | TradingView・Nasdaq 系の表記 |
| `-` | `BRK-B`（クラス株）、`A-Z`（範囲表記） | `BRK` / **`A`（Agilent Technologies）** | **`finance.yahoo.co.jp` は本拡張の遷移先の1つ**で、Yahoo Finance 系はクラス株を `-` で書く。**自分が開いたページからコピーして右クリックする経路がある** |
| `/` | `BRK/B`（クラス株）、`A/B テスト` / `A/Bテスト`、`AAPL/MSFT` | `BRK` / **`A`（Agilent Technologies）** | 一部の情報ベンダーがクラス株を `/` で書く。加えて**「A/B テスト」は日本語の技術文で普通に出る** |
| `+` | `BBB+ 相当の信用力`、`AA+`、`A+`（格付け表記） | **`BBB`（Bed Bath & Beyond）** / **`AA`（Alcoa）** / **`A`（Agilent Technologies）** | **日本語の金融文書に格付け表記が普通に出る** |
| `&` | `S&P500` / `S&P 500`（指数名）、`P&G`、`AT&T`、`A&B` | **`S`（SentinelOne）** / `P` / `AT` / `A` | **`S&P500` は日本語の金融文書で頻出。** 本拡張は指数を扱わないので、`S&P500` では何も開かないのが正しい挙動（FR-19 判定基準 7 と同じ考え方） |

> **`A` と `U` が実在するティッカーであることが、この規則の要点。**
> 1文字ティッカーがあるため、「切り出した結果が短すぎるから無害」という逃げ道が無い。
> `BBB`（Bed Bath & Beyond）や `AA`（Alcoa）のように、**格付けの記号列がそのまま実在ティッカー**
> になる例もある。
>
> **この5記号は許可列挙でも当然に落ちる**（どれも許可する後続に入らない）。
> 上表は「なぜこの規則が必要か」を示す証拠として残しているだけで、**規則の正本ではない。**
> 保留にしていた `_`（`A_B` → `A`）も、許可列挙では個別の判断なしに落ちる。
> **記号を1つずつ利用者に諮る運用は、これで終わりにする。**

**向きを変えても1度だけ穴が残った（2026-08-29 の2つ目の記録）:**

許可列挙にした直後、**全角の連結記号が素通りする**ことが分かった（`S＆P500` → `S`（SentinelOne））。
原因は許可表に置いた「**非 ASCII 文字なら許可**」という行で、これは
**「非 ASCII なら安全」という誤った代理指標**だった。

| | 誤り | 正しい切り分け |
| --- | --- | --- |
| 何が危険か | 米国ティッカーの一部になりうる文字 | **銘柄コードを別の表記に続けている文字**（文字種は関係ない） |
| 何が安全か | 非 ASCII 文字 | 銘柄コードを**終わらせている**もの（終端・空白・句読点・閉じ括弧・日本語の本文文字） |

**教訓は「向きを正しても、許可する側の定義を代理指標で書けば同じ穴が開く」ということ。**
判定基準 5 は、この穴を**記号を全角側で再列挙せずに**塞ぐために置いた
（半角側の規則1つが全角にも及ぶ形にする）。

> **`Ｓ＆Ｐ５００` のように全体が全角のものは、当時から何も開かなかった**（英字1〜5文字の照合が
> 半角しか見ないため）。**危険なのは「半角の英字＋全角の連結記号」という混在形**だけである。

**規則を足したら、崩れていないはずの性質も測り直す（2026-08-29 の3つ目の記録）:**

判定基準 7（取引所プレフィックスの落ち方）を足した結果、**判定基準 5 が1組だけ成立しなくなった。**
`A:Z` は打ち切られるのに `A：Z`（全角コロン）は終止記号として通り、
**パリティが 42/42 から 41/42 に落ちていた。** 全角コロンを区切りに含めて 42/42 に戻した。

| | |
| --- | --- |
| なぜ見落としたか | 42/42 は**判定基準 7 を足す前に測った値**で、規則を1つ足したときに測り直していなかった |
| 教訓 | **検算は「変わる入力」だけでなく、「変わらないと主張している性質」も再実行する。** 判定基準 5 のような**横断的な性質**は、別の判定基準を足しただけで崩れる |
| 副産物 | 全角コロンを区切りに含めたことで、**`NYSE：AAPL` が `us NYSE`（誤り）から `us AAPL @NYSE` になった。** `TSE：7203` / `TSE_DLY：7203` も正しく解釈される（FR-14 の主用途の全角版） |

## FR-12 実サイトに対してセレクタの生存を判定できる

注入対象サイトの改修で**検出用セレクタ**が効かなくなったことを、
利用者からの報告を待たずに、開発者が任意のタイミングで確認できること。

**検証対象（検出用セレクタ）** — 壊れると機能そのものが消えるもの:

| サイト | 対象 |
| --- | --- |
| 楽天証券 | 銘柄コードを含む要素を探すセレクタ。**お気に入り〜株価検索の12ページすべて** |
| 楽天スーパースクリーナー | 結果一覧の銘柄コード要素を探すセレクタ |
| SBI証券 | 個別銘柄・ポートフォリオの銘柄コード要素を探すセレクタ |
| SBI銘柄スクリーニング | 結果一覧の銘柄コード要素を探すセレクタ |
| TradingView | チャート本体の検出、ツールバーへの挿入先の検出、右クリックメニューの検出 |

> 楽天証券は同一セレクタを使うページが複数あるが、**間引かない**。
> セレクタが同じでもサイト側の DOM は個別に改修されうる。

**検証対象外（模倣用クラス）** — 壊れても見た目が崩れるだけのもの:

- 拡張機能が見た目を合わせるために自分で付与するクラス（TradingView のメニュー項目・区切り線など）
- これらは人の目で確認する（`docs/MANUAL-CHECKLIST.md` A-9）

**判定基準:**

1. 検証対象のセレクタごとに「対象ページでヒットした要素数」を出力すること
2. 各対象ページについて、以下の3状態を区別できること

   | ページ自体を識別する手がかり | 銘柄要素のセレクタ | 判定 |
   | --- | --- | --- |
   | ヒットする | 1件以上 | **正常** |
   | ヒットする | 0件 | **破損**（サイト改修でセレクタが効かなくなった） |
   | ヒットしない | — | **ページを開けていない／ページ構造そのものが変わった** |

   > 「保有銘柄が無いので0件」と「セレクタが壊れて0件」を取り違えないための区別。
   > 実現手段（実装側のセレクタ定義に何を持たせるか）は設計側で決める。
   >
   > **この表だけでは分類を誤る場合があることが実データで判明した。**
   > ページ識別セレクタがヒットしなくても、題名から対象ページに到達できたと分かる場合がある
   > （2026-08-23、楽天証券・国内株式・株価検索）。この是正は FR-22 で扱い、1.12.2 で実装し、
   > **2026-08-24 のフル実行で実データとして確認した**（FR-22 判定基準 4）。

3. 「破損」が 1 つでもあれば、成功と失敗を機械的に区別できること
   （終了コード等、目視によらない手段で区別できること）
4. どのサイトのどのページのどのセレクタが破損したかが、出力だけで特定できること
5. **「破損」または「ページを開けていない」と判定した対象について、
   原因の切り分けに使える手がかりを結果に残すこと**（2026-08-23 追加）

   目的は、次の3つを**結果ファイルを読むだけで**区別できるようにすること。

   | 疑うこと | 手がかりの例 |
   | --- | --- |
   | ページの URL が変わった | 到達先の題名が対象ページと別物 |
   | ログイン画面・エラー画面に飛ばされた | 到達先の題名がログイン系、見出しの構造が対象ページと違う |
   | 描画待ちが足りず、判定時点でまだ中身が無い | 題名は対象ページだが、主要コンテナが見当たらない |

   **残すもの:**

   | 内容 | 粒度 |
   | --- | --- |
   | 到達先ページの題名（`title` 要素の文字列） | そのまま |
   | 見出し要素（`h1`〜`h3`） | **タグ名・`id`・`class` 名のみ** |
   | 主要コンテナ | **タグ名・`id`・`class` 名のみ** |

   **残してはいけないもの:**

   | 内容 | 理由 |
   | --- | --- |
   | 要素のテキスト（題名を除く） | 銘柄名・保有状況などページ本文が混ざる（CON-10） |
   | URL・クエリ文字列・セッション ID | 認証情報を記録に残さない（NFR-12） |
   | HTML そのもの・スクリーンショット・Cookie | ページ内容を保存しない（CON-10, NFR-12） |

   > 題名は「どのページに着いたか」を人が読んで判断するための唯一の本文テキストとして許す。
   > ただし題名にセッション ID・URL が含まれている場合は記録しない。
   > 「主要コンテナ」として具体的に何を拾うかは設計側で決めてよいが、
   > **拾う対象を増やすほど本文が漏れる危険が上がる**ことを前提に、最小限にとどめる。

**対象の優先順位:**

TradingView を主対象、楽天証券・SBI証券を従とする。
TradingView の検証対象が判定できていれば、楽天証券・SBI証券は後から追加してよい。

> 根拠: `tradingview-cs.js` はハッシュ付きクラス名に依存しており、
> サイト改修で壊れる頻度が楽天証券・SBI証券より高い。

## FR-15 1回の実行で全対象サイトを検証し終えられる

FR-12 の検証を、**1回の実行で最後まで通せる**こと。

- ログインは実行の冒頭に、サイトごとに 1 回だけ行えばよいこと
  （検証項目ごとに再ログインを求められないこと）
- 検証の途中で利用者に追加のログインを要求しないこと
- **楽天証券の12ページと TradingView への遷移は自動で行うこと。**
  利用者がこれらを手で開いて回らずに済むこと
- 以下は例外とし、**利用者が実行前にタブを開いておく**。
  ツールはそのタブを探して判定する

  | 対象 | 利用者がタブを開く理由 |
  | --- | --- |
  | SBI証券・個別銘柄 / ポートフォリオ | ページの URL がセッションと遷移経路に依存し、URL の指定だけでは開けない |
  | 楽天スーパースクリーナー | 結果一覧を出すには検索の実行（フォーム送信）が要る。CON-10 で禁止している |
  | SBI銘柄スクリーニング | 同上 |

  > いずれもログインのついでに開けるため、利用者の手間はログイン操作から実質増えない。
  > タブが無い場合は「破損」ではなく「未実施」として記録する（FR-17）
- **楽天証券にログインしたタブを、合図のあとも閉じずに残しておくこと**（1.15.0 で追加。FR-23）。
  4ページはこのタブのリンクをたどって到達する。**開くタブは増えない**（もともと開いているタブを残すだけ）
- ログイン待ちに時間制限を設けないこと（所要時間は利用者次第）
- あるサイトの検証が失敗しても、残りのサイトの検証が続行され、
  最後まで実行された結果が出力されること

**流れ:**

1. 開発者が検証を開始する（`npm run check:selectors` を想定。名称は設計で変わってよい）

## FR-18 TradingView の右クリックメニューを1項目に集約する ✅

TradingView のチャートの右クリックメニューに拡張が追加する行を1行にまとめ、
遷移先サイトはその入れ子（サブメニュー）に出すこと。

**困りごと:** 現在は有効な遷移先サイトが平らに並ぶため、20件有効なら20行伸びる。
メニューが長くなり、目的のサイトを探しにくい。

**判定基準:**

1. チャートを右クリックしたとき、拡張が**メニュー直下に追加する行は常に1行**であること
   （区切り線を除く）。有効サイトの件数、および楽天証券・内藤証券の項目の有無に関わらず、
   直下の行数は変わらない
2. その1行のラベルが「`<銘柄コード>` を開く」であること
   （国内株は「`7203` を開く」、米国株は「`AAPL` を開く」）。**銘柄名は出さない**
   （TradingView のメニューに既に出ているため）
3. その行にホバーすると、有効な遷移先サイトの一覧が入れ子で開くこと
4. 入れ子の中身が次の順に並ぶこと

   | 順 | 内容 |
   | --- | --- |
   | 1 | 楽天証券・内藤証券の項目（FR-06。ログイン中のみ出る） |
   | 2 | 区切り線（上が1件以上あるときのみ） |
   | 3 | 情報サイトの項目。**オプションページで設定した並び順（FR-09）と一致すること** |

5. 入れ子の項目をクリックすると、その銘柄のページが新しいタブで開くこと（現行と同じ）
6. **有効な遷移先サイトが0件のときは、直下の1行ごと出さないこと**（現行と同じ）
7. 入れ子が画面に収まらない長さになった場合、**入れ子の中をスクロールして
   すべての項目に到達できる**こと。
   スクロールせずに全項目が見えることは求めない
8. 入れ子が開いた状態で **Esc キー**を押すと、メニューが閉じること
9. 入れ子が開いた状態で**メニューの外をクリック**すると、メニューが閉じること
10. 追加した1行と入れ子の見た目が、TradingView 自身のサブメニュー
    （「チャートテンプレート ▶」など）と揃っていること（判定は目視）

**やらないこと:**

- ツールバーの「株Link」ボタンのメニュー（SPEC-CS-12）は**今回のスコープ外**。
  同じ「長い」問題を抱えるが、独立したメニューなので別要件として扱う
- 楽天証券・SBI証券のページのメニューは対象外
- 入れ子内での検索・絞り込みは作らない
- **キーボードでの項目移動・決定（矢印キー・Enter）は対象外。**
  キーボード操作は Esc による閉じのみを対象とする

**制約との関係（CON-03）:**

TradingView のサブメニューの開閉はサイト側の JS が担っており、拡張から呼べない。
開閉は拡張が自前で持つ。見た目を合わせる模倣用クラス（SPEC-CS-16）が
TradingView 側の改修で変わると見た目は崩れるが、**崩れても項目の選択と遷移は動くこと**。

## FR-21 SBI証券・ポートフォリオのリンクメニューが他の拡張機能に依存しない ✅

SBI証券のポートフォリオで、保有銘柄の銘柄コードからリンクメニューを開けること
（FR-03 が満たせていなかった1ページ。**破損の解消**であり、新機能ではない）。

**困りごと:** 保有銘柄を見ているその場から、その銘柄の情報サイトへ移動できない。
個別銘柄ページでは出るため、このページだけ操作が途切れる。

**原因（2026-08-23 3回目の `npm run check:selectors` で確定）:**

根拠はすべて **3回目版**（`git show e0d3c5e:docs/SELECTOR-CHECK.md`。1.12.1 で生成し、1.12.2 のコミットに収録）の「SBI証券」節にある。

| 事実 | 根拠（3回目版の該当箇所） |
| --- | --- |
| ページには到達している | 「ポートフォリオの手がかり」節。到達先の題名が「ポートフォリオ｜SBI証券」 |
| 検出用セレクタの先頭 `body.vsc-initialized` が 0 件 | 同節のプレフィックス追跡の段階1 |
| 当該クラスは `body` に付与されていない | 「ポートフォリオの追加検査」節 |
| 当該クラスを外すと 24 件ヒットする | 同節 |

> **出典をリビジョンで固定している理由:** 上表の根拠は、次に `npm run check:selectors` を実行した時点で
> 作業ツリーの `docs/SELECTOR-CHECK.md` から消える。
>
> - 「ポートフォリオの追加検査」は `vsc-initialized` 専用の一時的な仕掛け（SPEC-SC-12。廃止・欠番）で、
>   **原因が確定し恒久修正が入ったため 1.12.2 で生成器ごと削除した。** 再実行しても再生成されない
> - ポートフォリオの判定自体も 1.12.2 の修正で ❌ から ✅ に変わる見込みで、
>   ❌ / ⚠️ にだけ出力される「手がかり」節（FR-12 判定基準 5）も出なくなる
>
> 同種の混入の再発防止は CON-11 のガードが担う。

`vsc-initialized` は **SBI証券が付けるクラスではなく、別の Chrome 拡張機能
（Video Speed Controller）が `<body>` に付けるクラス**である。
`git log -S'vsc-initialized' -- src/` は `657f366 SBI証券のサポート領域を拡張` を指す。
当時その拡張を入れていた環境の DOM を見て、サイト側のクラスと誤認して取り込んだと考えられる。

**つまりこれは「サイト改修で壊れた」のではなく、
最初から「その別拡張を入れている環境でしか動かなかった」欠陥である。**

**判定基準:**

1. **株リンク以外の拡張機能を入れていない Chrome** で SBI証券のポートフォリオを開き、
   銘柄コードにホバーするとリンクメニューが出ること
2. 選ぶとその銘柄のページが新しいタブで開くこと（他のページと同じ挙動）
3. `npm run check:selectors` のポートフォリオの判定が ✅ になり、
   **注入された要素が 1 件以上**であること
4. SBI証券の他の対象（個別銘柄・銘柄スクリーニング）の判定が変わらないこと
5. **他の拡張機能の有無で結果が変わらないこと**が本要件の核心。
   判定 1 の「株リンクだけの環境」で満たせていれば足りる。
   Video Speed Controller を入れた環境での再確認は任意（入れると直る側なので、
   退行の危険が小さい）

**やらないこと:**

- ポートフォリオ以外の SBI証券ページの見直しは対象外（別途 CON-11 の点検で扱う。
  2026-08-23 に検出用セレクタ 20 件を全点検し、混入は本件 1 件だけと確認済み）
- 保有銘柄が 0 件のときの表示は対象外（もとから注入対象が無い）

## FR-22 到達できているページを「未到達」と判定しない ✅

FR-12 の検証で、**対象ページに到達できているのに検出用セレクタが 0 件**の場合を、
「ページを開けていない（⚠️）」ではなく「破損（❌）」として扱えること。

**困りごと:** 2026-08-23 の実行で、楽天証券・国内株式・株価検索は
題名から到達が確認できるにもかかわらず ⚠️ と分類された。
一方、同じ ⚠️ には「ツールがエラーページに飛ばされた4ページ」も混ざっている。
**直すべきもの（拡張の破損）と、直さなくてよいもの（ツールの到達失敗）が同じ記号になる。**
結果ファイルを開いて手がかりを読まないと区別できず、判定を機械的に扱えない
（FR-12 判定基準 3 の「破損があれば失敗として区別できること」が実質的に働かない）。

**判定基準:**

1. 対象ページへの到達可否を、**ページ識別セレクタのヒット数だけで決めないこと**。
   到達したと判断できる別の手がかり（到達先の題名など）を判定に使うこと
2. 到達したと判断できる場合、検出用セレクタが 0 件なら **❌（破損）** と分類すること
3. 到達したと判断できない場合は、従来どおり **⚠️（未到達）** のままとすること
4. 2026-08-23 のケースで、株価検索が ❌、楽天の他4ページが ⚠️ に分かれること
   （既存の実データで検算できること。**検算に使う実データは 3回目版 `git show e0d3c5e:docs/SELECTOR-CHECK.md`。
   そこでは5ページとも ⚠️ で、この分類は本要件の実装で変わるため次回の実行では再現しない**）
5. ❌ に分類された対象は FR-12 判定基準 3 の終了コードに反映されること
6. 誤って ❌ にした場合の害（存在しないページを破損と呼ぶ）を避けるため、
   **到達の判断根拠を結果ファイルに残すこと**（FR-12 判定基準 5 の手がかりの範囲を超えないこと）

**やらないこと:**

- ページ識別セレクタの仕組みそのものを廃止しない（到達判断の材料は増やすが、置き換えではない）
- 到達判断のために新しい情報（HTML・スクリーンショット・URL）を記録しない（CON-10, NFR-12）
- 判定記号を増やさない（✅ / ❌ / ⚠️ / — の4つのまま）

**決着（2026-08-23 / 1.12.2）:**

「到達したと判断できる」の決め方は、**対象ページごとに正解の題名を持つのではなく、
「未到達の目印」（エラー画面・ログイン画面の題名）に当たらなければ到達とみなす**方式で決着した
（ADR-0006）。持つ情報が対象ページ数ではなく目印の数で済むため、
未確定として挙げていた二重管理の増加（NFR-13 の趣旨）は最小限にとどまった。

> 代償として、**対象ページとは別の正常なページに飛ばされた場合も「到達」と見なす**。
> このとき ❌（破損）に分類されるため、**❌ を見たらまず手がかりの題名が対象ページのものかを人が読む**
> 運用が要る。
>
> **2026-08-24 に実例が出た。** 楽天証券・株価検索（FR-20）が ❌ に分類されたが、
> 到達判定は「未到達の目印に当たらない」しか見ないため、
> 対象ページ（検索結果画面）に着いているのか別の正常なページに着いているのかは区別できていない。
> **この ❌ は「破損の確定」ではなく「人が題名を読んで判断すべき対象」である**（FR-20 参照）。

### FR-13 注入失敗時のリトライ ⚠️

固定待機時間内にサイト側の描画が終わらなかった場合でも、最終的にメニューが注入されること。

**困りごと:** 待機が明けた時点で挿入先や銘柄コード要素が無いと、そのページ読み込みでは
**二度と注入されない**（再試行しないため）。利用者からは
「たまにボタンやメニューが出ない。タブを再読み込みすると出る」という形で見える。

**判定基準:**

1. ページを開いた直後に挿入先・銘柄コード要素が無くても、**後から現れたら注入されること**
   （タブを再読み込みさせずに済むこと）
2. 注入対象が最後まで現れないページで、**再試行が無限に続かないこと**（打ち切る条件があること）。
   **打ち切ったときは、再試行のために張った監視も外すこと**（他社サイト上で監視・再試行が
   走り続けないこと。NFR-01）
3. 同じ要素に**二重に注入しないこと**（メニューやボタンが2つ出ない）。
   機械的な確認は判定基準 5 (c)。(c) が検知できない3対象は目視で確かめる（同 (c) の「限界」）
4. **切断状態（NFR-14）を検知したら、再試行を停止し、そのために張った監視も外すこと。**
   切断状態では注入しないこと（NFR-14 判定基準 2、および「切断を検知したら監視そのものを外す」
   という現行の方針を維持する）

> 1回きりの注入に起因する本要件の問題が起きない（同じ実行で右クリックメニューだけ注入 1 件に

- タブの自動再読み込みはしない

### FR-19 TradingView のウォッチリストの行から遷移先サイトを開ける ⚠️

TradingView のチャート画面のウォッチリストで銘柄行を右クリックしたとき、
**その行の銘柄**について遷移先サイトを開けること。

**困りごと:** 現在はウォッチリストで見つけた銘柄を調べるのに、
いったんチャートの銘柄を切り替えてから右クリックする必要がある。

**判定基準:**

1. ウォッチリストの銘柄行を右クリックすると、拡張の項目が出ること
2. 出る項目の銘柄が、**右クリックしたその行の銘柄**であること。表示中チャートの銘柄ではない
   （チャートに銘柄 A を表示した状態でウォッチリストの銘柄 B を右クリックしたら、B のリンクが出る）
3. 行から銘柄コードが読み取れないときは、項目を追加しないこと（誤った銘柄のリンクを出さない）。
   **銘柄コードが単独のトークンとして現れているときだけ切り出すこと**を含む
   （FR-08「切り出してよい後続だけを許す」。`NYSE:BRK.B` の行で `BRK` を出さない）
4. メニューの形は FR-18 に従う（直下1行＋入れ子）
5. チャートとウォッチリスト以外（ツールバー・銘柄検索など）では、
   引き続き項目を追加しないこと（FR-04）
6. **国内株の行と米国株の行の両方で、その市場に応じた正しいリンクが開くこと。**
   国内株は国内株用の遷移先、米国株は米国株用の遷移先（判定は目視。
   国内株と米国株を混在させたウォッチリストで確認する）
7. **銘柄コードとして扱えない行では項目を追加しないこと。**
   指数・先物・FX・暗号資産など、既存の遷移先サイトが対象にしていない行が該当する
   （判定基準 3 の具体化。「何も起きない」が正しい挙動であり、
   誤って国内株・米国株のリンクを出さないこと）
8. **ウォッチリストをスクロールした後、および別のウォッチリストへ切り替えた後でも、
   画面に見えている行を右クリックすれば判定基準 1・2 を満たすこと**
   （行が入れ替わっても、右クリックした行の銘柄が出る）

**やらないこと:**

- **対象はチャート画面のウォッチリストウィジェットに限る。**
  ウォッチリスト専用ページ・スクリーナー・ホットリスト・ニュース等の他ウィジェットは対象外。
  そこで項目が出なくても本要件の未達としない（判定基準 5 の側で「出さない」が正しい）
- 行にホバーしたときのボタン表示・行内へのアイコン追加はしない（右クリックのみ）
- 複数行を選択しての一括オープンはしない
- ツールバーの「株Link」ボタン（SPEC-CS-12）の挙動は変えない

**FR-04 との関係:**

FR-04 は「チャート領域上で右クリックしたときに限る」と定めている。
これは「ウォッチリストで銘柄 B を右クリックしたのに、表示中チャートの銘柄 A のリンクが出る」
退行を防ぐためのもの。本要件はこの禁止を全面的に解くのではなく、
**右クリックした行から銘柄を特定できる場合に限って**対象を広げる。
判定基準 2 を満たさない実装は FR-04 違反として扱う。

**2026-08-29 に FR-04 の禁止対象からウォッチリストの銘柄行を除外した**（1.15.0 の実装時点で確定。
理由は FR-04 の「FR-19 との関係」）。ツールバー・銘柄検索・ウィジェットの余白など、
**行を特定できない場所は引き続き禁止**。

**実 DOM 調査で判明したこと（2026-08-23 / 利用者のログイン済み環境で実測）:**

### FR-20 楽天証券・国内株式・株価検索でリンクメニューが出ない ❌

楽天証券の「国内株式・株価検索」で、検索結果の銘柄コードからリンクメニューを開けること
（FR-02 が満たせていない1ページ。**破損の解消**であり、新機能ではない）。

**困りごと:** 銘柄コードで検索して結果を見ている、まさにその場からリンクをたどれない。
他の11ページでは出るため、このページだけ操作が途切れる。

**判定基準:**

1. 株価検索の**結果画面**で、銘柄コードにホバーするとリンクメニューが出ること
2. 選ぶとその銘柄のページが新しいタブで開くこと（他のページと同じ挙動）
3. `npm run check:selectors` の当該ページの判定が ✅ になること
4. 他の11ページの判定が ✅ のまま変わらないこと（巻き添えの退行を出さない）

**分かっていること（2026-08-23 の `npm run check:selectors` の実データ。2026-08-24 のフル実行でも同じ結果）:**

| 事実 | 根拠 |
| --- | --- |
| **ツールは正しいページに到達している** | 到達先の題名が「国内株式トップ \| 株価検索 \| 国内株式トップ \| 国内株式 \| 楽天証券[PC]」。エラーページでもログイン画面でもない |
| **検出用セレクタの先頭 `div#line1` が 0 件** | プレフィックス追跡の段階1で 0 件。以降を追う必要がない |
| **同じ検出用セレクタを使う「国内株式・個別銘柄」は ✅**（ヒット1・注入1） | 同一セレクタでも結果が割れる。**株価検索ページだけ DOM が別物** |
| 株価検索ページの見出しは `h1.hdg-l1-01`（`hdg-l1-01-title` ではない） | 手がかりの見出し欄。検出用セレクタが前提にしている構造と食い違う |
| 主要コンテナに `div.mbody` があり、`div#mwfooter` は無い | エラーページ（4ページ）と異なる。到達成功の裏づけ |

**したがって、以下は否定された:**

- 「エラーページ・ログイン画面に飛ばされた」— 題名が対象ページのものであり、
  他の4ページ（題名が「エラー」）とは明確に違う
- 「ツールと拡張の問題が同時に起きていて切り分けられない」— 少なくとも到達は成功している

**残る読み方は2つ。どちらもページの現物を見ないと決まらない:**

| 読み方 | 支持する材料 | 反する材料 |
| --- | --- | --- |
| (a) サイト改修で株価検索ページの DOM が変わり、`div#line1` が無くなった | 利用者の目視でもメニューが出ない（2026-08-23）。見出しが `h1.hdg-l1-01` で、セレクタが前提とする `hdg-l1-01-title` と違う | — |
| (b) ツールが開いた URL では**結果画面ではなく検索フォーム／国内株式トップが返っている** | 題名に「国内株式トップ」が2度出る。ツールは個別銘柄と同じ銘柄クエリを付けているだけで、**検索そのものは実行していない**（フォーム送信は CON-10 で禁止） | 目視でも出ないことは (b) だけでは説明できない |

> **2026-08-24 の再実行では決着しなかった。** FR-22 の実装により分類は ⚠️ から ❌ に変わったが、
> 到達判定は「題名が未到達の目印（エラー画面・ログイン画面）に当たらない」ことしか見ない。
> **「対象ページに着いた」ことまでは確かめていない**ため、(b) は排除できていない。
> 決着には依然として利用者の環境で実ページを見る必要がある（下の「残る調査」）。
>
> (b) だった場合、株価検索は**ツールでは判定できないページ**ということになり、
> FR-15 の「利用者がタブを開いておく例外」に移す必要がある
> （**FR-23 の楽天4ページは 1.15.0 でこの例外ではなく「ポータルのリンクをたどる」方を採った。**
> 例外への移動は、そちらが実サイトで効かなかったときの退避先として残っている）。

### FR-23 楽天証券の全12ページを検証ツールで判定できる ⚠️

FR-12 が対象とする楽天証券12ページのうち、4ページが**判定できない**。
この4ページについても判定結果が出ること。

> 「恒久的に」と書いていたのは 1.13.0 まで。1.15.0 で到達方法を変えたが、
> **効いたかどうかは実サイトで走らせるまで分からない**（下記「状態」）。

対象: お気に入り / お気に入り編集 / 保有商品一覧・すべて / 保有商品一覧・国内株式

**困りごと:** 2026-08-23 の実行で、この4ページは到達先の題名が
「エラー | 楽天証券[PC]」で、主要コンテナも4ページで完全に同一だった
（2026-08-24 のフル実行でも同じ）。
ツールが生成した URL を直接開いてもエラーページに飛ばされている（遷移元が要る等）。
**目視ではメニューが出ており拡張機能は正常**（`docs/MANUAL-CHECKLIST.md` C-1）。
つまり FR-12 の目的（利用者の報告を待たずに破損を知る）が、この4ページだけ達成できていない。

**判定基準:**

1. 4ページそれぞれについて、✅ / ❌ のいずれかの判定が出ること
   （⚠️ や — のままにならないこと）
2. 現状（目視でメニューが出る状態）で実行すると、4ページとも ✅ になること
3. 他の8ページの判定が変わらないこと
4. 利用者の手順の増加が、FR-15 の「例外4対象」と同程度に収まること
   （ログインのついでに開けるタブを増やす程度。1ページごとの手作業の確認にしないこと）
5. 到達のために**サイト内のリンクをたどる場合**は、下記「判定基準 5 の条件」を
   すべて満たすこと（2026-08-24 追加。**リンクをたどること自体は要件側で許可した**）

**取りうる方向（2026-08-29 に1つ目を採用。2つ目は退避先として残す）:**

| 方向 | 状態 |
| --- | --- |
| **到達方法を変える（ログイン済みのポータルからリンクをたどる）** | **採用。** 2026-08-24 に利用者が提案し、CON-10 の範囲内であることを下記で確認。設計は SPEC-SC-26 / ADR-0011、実装は 1.15.0 |
| FR-15 の「利用者がタブを開いておく例外」に移す | **退避先として残す。** 実サイトで上が効かなかったときに切り替える（「判定基準 1 の読み方」3）。確実だが利用者の手順が4つ増える。判定基準 4 の許容範囲内 |

**判定基準 5 の条件（2026-08-24 に判断）:**

**条件そのものは `CON-10`「リンクのクリックを許容する条件」を正とする。**
リンクをたどってよいのは、そこに挙げた条件をすべて満たす場合に限る。

> **ここに条件を再掲しない理由（2026-08-25）:** 以前は同じ4項目を CON-10 と本項に
> 逐語で二重に書いていた。片方だけ直すと乖離するため、**本項からは参照だけにする。**
> 条件を足す・狭めるときは CON-10 を直す。
>
> **なぜ CON-10 に反しないか（2026-08-24 の整理）:**
> CON-10 が禁じているのは「ログイン操作の自動化」「フォーム送信」「データの一括取得」であり、
> **ページからページへ移動すること自体は既に許容されている**
> （「ログイン済みセッションで対象ページの URL へ遷移する ✓」）。
> リンクを1回クリックして移動するのは、URL を直接開くのと同じ GET 遷移で、
> サイトへの負荷も利用者が手で見て回るのと変わらない。
> **「リンクのクリックは送信ではない」と整理する。** CON-10 に許容行として明記した。
>
> 境界は「サイト側の状態を変えるか」で引く。同じクリックでも、検索条件を送る・注文を出すものは不可。
>
> **2026-08-25 の見直し:** 当初は「リンクの実体が JS 経由の POST なら、画面遷移が目的なら可・
> データ送信が目的なら不可」としていたが、**JS 経由の POST はまさに「判断がつかない」類**で
> 自己矛盾していた。たどってよい対象を**素の `<a href>` の GET 遷移**に限定する形に狭めた。
> `onclick` などの JavaScript ハンドラで遷移するものは、画面遷移が目的に見えても採らない（CON-10）。

**判定基準 1 の読み方（2026-08-29 に確定。設計からの差し戻しへの回答）:**

設計側から「判定基準 1 と、到達できなかったときの正直な判定が両立しない」という差し戻しがあった
（SPEC-SC-26「判定（⚠️ が残る場合がある）」、ADR-0011 の 5）。
たしかに、ポータルのリンクをたどれなかった対象を文字どおり ✅ / ❌ に倒すと、
**✅ なら破損を見逃し、❌ ならツールの到達失敗を破損と呼ぶ**（FR-22 が解いた問題の再発）。

**しかし両立しないのは、判定基準 1 を「ツールが実行時に守る規則」と読んだ場合だけである。**
本項の判定基準は**要件が満たされたかどうかを判定する条件**であって、ツールへの指示ではない。
そこで次のとおり読む。**判定基準 1 の文言は変えない（緩和しない）。**

| # | 読み方 |
| --- | --- |
| 1 | **ツールは、到達できなかった対象を ✅ / ❌ に倒してはならない。** ⚠️ のままとし、理由（リンクが見つからない／素の `a href` でない／たどった先が対象ページでない）を結果ファイルに残すこと。これは FR-22 が確立した規則（直すべきものと直さなくてよいものを同じ記号にしない）の適用であり、**緩和ではなく本要件が要求する側の振る舞い**である |
| 2 | 実サイトのフル実行で4ページとも ✅ / ❌ が出て初めて判定基準 1 を満たす。**⚠️ が残る実行は「本要件が未達」を意味する**（実装の欠陥ではなく、到達方法が成立しなかったという事実の記録） |
| 3 | 到達方法が成立しなかったときは、上の「取りうる方向」表の2番目（FR-15 の「利用者がタブを開いておく例外」へ移す）に切り替える。それが判定基準 4 の許容範囲内であることは 2026-08-24 に合意済み |

> **この読み方で失うものは無い。** 実装は差し戻しの結論によらず変わらない（ADR-0011 の 5）。
> 変わるのは「⚠️ が残る実行を FR-23 の達成として記録してよいか」だけで、**記録してはならない**とした。
>
> 言い換えると、**リンクをたどる方式は「判定基準 1 を満たしうる手段」であって、
> 採用・実装したこと自体は達成ではない。** 手段が効かなければ、次の手段に移って効くまで本項は ✅ にならない。

**やらないこと:**

- ログイン操作の自動化はしない（CON-10）
- フォーム送信・データ取得はしない（CON-10）
- 利用者に4ページを1つずつ目視させる形にはしない（判定基準 4）
- **到達できなかった対象を ✅ / ❌ に倒して判定基準 1 の形だけ整えることはしない**（上記の読み方 1）
