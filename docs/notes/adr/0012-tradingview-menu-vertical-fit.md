# ADR-0012 画面下部で見切れる右クリックメニューをどう収めるか

| | |
| --- | --- |
| 状態 | 採択（2026-08-30）。**1.16.0 で実装**（1〜5）。**4 は利用者の実機確認で「足さない」に確定** |
| 対象 | FR-24（＋ FR-04, FR-18, FR-19, NFR-01, CON-03, CON-08） |
| 仕様 | [SPEC-CS-24](../specs/content-scripts.md) |
| 発端 | 利用者が 1.15.0 を実機で確認し「下の方だと追加した分が見切れてしまう（画面からはみ出てクリックできない）。見切れる場合メニュー全体をその分上に移動してほしい」と報告した |

---

## 0. 何が起きているか

TradingView は右クリックの座標にメニューを置く。**その時点では拡張の3行はまだ無い。**
拡張は後から `<table>` に3行（区切り行・親行・受け皿行）を足すので、
**メニューは下へ伸びる。サイト側は伸びたことを知らないので位置を直さない。**

下端付近で右クリックすると、伸びた分がウィンドウの外に出る。
**行が見えない＝ホバーできない＝入れ子も開けない**ので、その位置では拡張の機能が丸ごと使えない。

**これは「見た目の問題」ではない。** FR-04（必須）の「遷移先サイトを開ける」が、
画面のどこで右クリックしたかによって成立しなくなる。

---

## 1. 誰の要素を触るか

**決定: TradingView 自身のメニュー要素（`div.context-menu`）の位置を、拡張が補正する。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | サイト側のメニュー要素を上へずらす | **伸ばした責任は拡張側にある。** 位置を直さないと、拡張が足した行だけでなく**サイト側の項目まで押し出して隠す**。触る範囲は1要素・1プロパティに限れる |
| (b) | 触らず、拡張の3行の中だけで何とかする（3行を短く／畳む） | 却下。**行の高さの問題ではない。** 1行に集約済み（FR-18）で、これ以上減らせない。減らしても下端ぎりぎりでは同じことが起きる |
| (c) | 拡張の3行をメニューの**先頭**に入れて、切れる側をサイト側の項目に回す | 却下。**サイト側の項目が選べなくなる**（FR-24 判定基準7 / NFR-01）。他人のメニューの先頭を奪うのは CON-03 の趣旨に反する |
| (d) | 追加をやめ、拡張のメニューを別の器（自前のポップアップ）で出す | 却下。FR-18 が「TradingView 自身のサブメニューと同じ見た目」を求めており、器を分けると見た目も操作感も別物になる。変更が大きすぎる |

**(a) の前提:** 触るのは**位置だけ**。項目の内容・並び・件数には手を入れない（判定基準7）。

---

## 2. どうやってずらすか

**決定: メニュー要素の `margin-top` に負の値を入れる。`top` / `transform` は書き換えない。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | `style.marginTop = '-Npx'` | **サイト側がどちらの手段で位置決めしていても効く。** `top` でも `transform` でも、マージンは箱の位置をそのままずらす。**サイト側の値を読まず、上書きもしないので衝突しない。** 元に戻すのはインラインスタイルを消すだけ |
| (b) | `style.top` を読んで書き換える | 却下。**サイト側が `top` で位置決めしているとは限らない**（`transform: translate(...)` の可能性がある）。読めた値の単位（`px` / `%` / `auto`）で分岐が要り、外すと**メニューが画面の別の場所へ飛ぶ** |
| (c) | `style.transform` に `translateY(-N)` を足す | 却下。サイト側が `transform` を使っていた場合、**上書きすると位置決めごと壊れる**。連結して書くと元の値の解析が要る |
| (d) | 親メニューにも自前のスクロール層を被せる | 却下（第一手としては）。**利用者が求めたのは「上に移動」**で、スクロールは収まらないときの最後の手段（下記 4） |

> **`margin-top` を選ぶ理由は「サイト側の位置決めの実装を知らなくても成立する」こと。**
> 他社サイトの DOM は読めても、**なぜその値なのかは分からない**（CON-03）。
> 読まずに済む手段があるなら、それを採る。

---

## 3. 上端の扱い

**決定: 上端はウィンドウの外に出さない。ずらす量は「はみ出した量」と「上の余地」の小さい方。**

```text
shift = min(下にはみ出した量, メニュー上端から画面上端までの距離)
```

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 上端で止める | 下の見切れを上の見切れに置き換えない（判定基準3）。**サイト側の項目は上に並んでいる**ので、上を切ると今度はサイト側の機能が使えなくなる |
| (b) はみ出した分だけ無条件にずらす | 却下。メニューが画面より高いとき、上端が画面外へ出て**サイト側の項目が消える**。NFR-01（サイトの機能を損なわない）に反する |

---

## 4. 画面より高いメニュー（判定基準4）

**決定: 拡張はスクロール層を足さない。TradingView 自身のスクロールに委ねる。**
**（2026-08-30 の利用者確認で確定。「TradingView のメニューはスクロールできる」）**

- メニューの外枠には**サイト側のスクロール層**がある（模倣用クラス `scrollWrap`。SPEC-CS-16）。
  採択時は**それが実際にスクロールするかが未確認**だった
- **確認できるまで拡張側で対処しない**という判断で保留にし、手動確認（A-18）に回した。
  自前のスクロール層を被せるとサイト側のスクロールと二重になり、どちらが効くか読めなくなるため
- **確認の結果、足さないで確定した。** 判定基準4 はサイト側のスクロールで満たされる。
  本 ADR の 2 の (d) は**採らない**

> **判定基準4 だけは「確認してから決める」に倒した。** 利用者が求めたのは移動で、
> スクロールは analyst が補った未確認の想定だった（FR-24 の「確定」欄）。
> **未確認の想定に対して先回りで他人の DOM を触らない。**
>
> **この判断が正しく働いた例になった。** 先に被せていたら、
> **必要のないスクロール層を恒久的に抱える**ことになっていた。

## 5. いつ測るか

**決定: 3行を追加した後、`requestAnimationFrame` で1回だけ測って補正する。**
**実装は `fitContextMenuIntoWindow()`（1.16.0）。**

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 次のフレームで測る | **サイト側がメニューを置き終えているとは限らない。** 監視コールバックはノードが追加された直後に走るので、その場で測ると位置決め前の値を拾いうる |
| (b) 追加直後に同期で測る | 却下。上記のとおり値が信用できない。**間違った量ずらすと、直すどころか悪化する** |
| (c) `ResizeObserver` / `MutationObserver` で追い続ける | 却下。高さが変わるのは**拡張が3行を足した瞬間だけ**（入れ子は `position: fixed` で親の高さに影響しない）。監視を増やす理由が無い（NFR-01） |

**補正の取り消し:** 0件・例外で3行を除去する経路（SPEC-CS-11）では、
**インラインの `margin-top` も元に戻す。** 拡張の痕跡を残さない方針（FR-18 判定基準6）と同じ。

## 6. 「株Link」ボタンのメニュー（SPEC-CS-12）

**決定: 本 ADR では扱わない。ただし同じ症状があるかを手動確認で見る。**

ボタンのメニューは**拡張が自分で座標を決めて置いている**（`position: fixed; top: <クリック位置>`）。
**縦のはみ出しを見ていない**ため、同じことが起きる可能性が高い。
FR-24 は対象外としているが、「同じ症状が出るなら別途起こす」とも書いてある。
A-18 に観察ステップを置き、**出るなら analyst に新しい要件として起こしてもらう。**
