## 0. どこで空振りするか（1.12.2 の実装を読んだ結果）

> 以下の表は**採択時（1.12.2）の実装**を指す。1.13.0 で本 ADR の 1〜8 を実装し、
> ここに挙げた空振りはいずれも再試行または常設監視が受け持つようになった。

| 注入先 | 空振りする箇所 | 空振り後 |
| --- | --- | --- |
| `rakuten-cs.js` | 500ms 時点で `menuSelectors` のセレクタが 0 件 | 何も起きない。再試行なし |
| `sbi-cs.js` | 同上 | 同上 |
| `rakuten-scr-cs.js` | 500ms 時点で `div#resultpanel div.pagenavcontrolbox` が無い → `return` | **監視すら張られない**。以降どれだけページ送りしても注入されない |
| `sbi-scr-cs.js` | 1500ms 時点で `div#root div.App div.Screener div.resultpane` が無い → `return` | 同上。実測で 2 日連続の注入 0 件 |
| `tradingview-cs.js` | 500ms 時点で `chart-canvas` が 0 件 → `if` の中に入らない<br>／`toolbar-container` が 0 件 → `appendTo()` が黙って何もしない | **canvas 監視とボタンの両方**、または**ボタンだけ**が失われる |

`tradingview-cs.js` の `body` 監視（オーバーレイレイヤー待ち）だけは空振りしない。
`$('body')[0]` は必ず取れ、オーバーレイが現れるまで監視が続くため。
**同じ実行で右クリックメニューだけ注入 1 件になるのはこれが理由**で、
「1回きりの注入か、現れるまで待つ注入か」の差だけが症状を分けている。

## 1. 再試行を何で駆動するか

**決定: タイマー（`setInterval`）。**

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 一定間隔のタイマーで `setup()` を呼び直す | 設置先の**祖先が存在しない段階**でも回せる（`MutationObserver` は監視対象のノードが要る）。停止が `clearInterval` 1 本で済み、打ち切り（FR-13 判定基準2）と切断（同 4）の停止経路を一致させられる。1 tick のコストはセレクタ 1〜2 本の評価だけ |
| (b) `document.body` を `subtree` 監視して、変化のたびに `setup()` を呼ぶ | 却下。他社サイトの DOM 変化すべてを受け取ることになり、**再試行が終わるまでの負荷がサイトの実装しだいで青天井**になる（NFR-01, CON-03）。React 製の SBI銘柄スクリーニングでは変化が多い |
| (c) 固定待機を延ばす（500ms → 3000ms 等） | 却下。**遅い環境では依然として空振りし、速い環境ではメニューが出るまで遅くなる**（NFR-09）。閾値をどこに置いても当てずっぽうになる |
| (d) `requestIdleCallback` で暇なときに試す | 却下。呼ばれる保証が無く、打ち切りまでの時間が読めない。TradingView のように常に忙しいページで回らない |

> **タイマーは背景タブで 1 秒に丸められる**（Chrome の throttling。長く隠れていると更に粗くなる）。
> 打ち切りは経過時間で見るので影響は「試行回数が減る」だけだが、
> **人が開いて放置するタブ（スクリーナー2種）を再試行だけで支えるのは危うい**。
> これが 3 の判断（常設監視を分ける）の理由でもある。

## 2. 打ち切りの条件と値

**決定: 最初の試行から 30 秒。間隔 500ms（最大 60 回）。**

| 案 | 判定 |
| --- | --- |
| 打ち切らない | 却下。FR-13 判定基準2 が明示的に禁じている。他社サイト上で走り続ける（NFR-01, CON-03） |
| 回数で打ち切る（例 20 回） | 却下ではないが、**間隔を変えると意味が変わる**。「何秒まで待つか」が要件の関心なので時間で持つ |
| **採用: 時間で打ち切る（30 秒）** | 「ページを開いてから 30 秒たっても現れないものは、そのページの対象ではない」と言い切れる。TradingView のチャート描画は実測で数秒。検証ツールの計測点（TradingView は遷移後 5000ms）より十分に長い |
| 指数バックオフ | 却下。稼ぐのは高々数十回分の評価コストで、**現れた瞬間からの遅れが伸びる**（利用者から見える劣化）。一定間隔のほうが読みやすい |

**30 秒の代償を承知で採る。** 対象要素が最初から無いページ（例: 保有 0 件のお気に入り、
SBI証券の対象外ページ）では、30 秒かけて 60 回空振りする。1 回のコストはセレクタ評価だけで、
DOM は一切変更しない（NFR-01「対象要素が見つからない場合は DOM を一切変更しない」を保つ）。

> `rakuten-cs.js` は URL で対象ページを絞る（SPEC-CS-07）。**一致する `menuSelector` が 0 件なら
> 再試行そのものを始めない**（SPEC-CS-14）。`sbi-cs.js` は URL で絞らない実装のため、
> SBI証券の対象外ページでも 30 秒の空振りが起きる。**これは受け入れる**
> （絞り込みを足すと SPEC-CS-09 の「URL による絞り込みは行わない」を変えることになり、
> FR-13 の範囲を超えて退行の危険が増える）。

## 3. 「常設監視」と「再試行」を分ける

**決定: 2 つを別物として定義し、スクリーナー2種の常設監視の対象を `document.body` へ上げる。**

| 区分 | 目的 | 寿命 | 打ち切り |
| --- | --- | --- | --- |
| **再試行** | **設置そのもの**（注入・監視の開始）が空振りしたときに繰り返す | 成功・打ち切り・切断まで | あり（2） |
| **常設監視** | 設置した後、**ページの変化に追随して**注入し続ける | タブの寿命（切断時のみ外す） | なし |

FR-13 判定基準2 の「打ち切ったときは、再試行のために張った監視も外すこと」は**再試行側**への要求と読む。
本設計では再試行をタイマーで駆動するため、これは `clearInterval` に対応する。
常設監視（スクリーナー2種のページ送り監視、TradingView の `body` / オーバーレイ監視）は
FR-13 が新設するものではなく、ADR-0005 の 4 で決めた既存の仕掛けで、**切断時に外す規則は変えない**。

**スクリーナー2種の監視対象を上げる理由。** 現行は「結果一覧の器が既にある」ことを前提に、
その器（`div.pagenavcontrolbox` / `div.resultpane`）を監視している。
ところが FR-15 の手順では**人が検索するのは実行の直前**で、
ページを開いてから検索するまでの時間に上限が無い。

| 案 | 判定 |
| --- | --- |
| (a) 現行の器を再試行で待つ | 却下。人が 5 分後に検索したら打ち切り（30 秒）に間に合わない。**タイマーは背景タブで丸められる**ため更に不利（1 の注記） |
| (b) 打ち切りを長くする（数分） | 却下。他社サイト上でタイマーを分単位で回すことになる（NFR-01）。上限を伸ばしても「人しだい」には勝てない |
| **(c) 採用** 常設監視の対象を `document.body`（`childList` + `subtree`）に上げ、器の出現も**監視で**拾う | 空振りする箇所が消える（`document.body` は `$()` の時点で必ずある）。**`MutationObserver` は背景タブでも丸められない**。上限時間という概念が要らない |

**(c) の代償と抑え。** 監視範囲が広がるぶんコールバックの発火回数が増える。
**デバウンス（200ms で束ねる）**を必ず入れる。
注入パスは冪等（SPEC-CS-02）なので、パス自身の DOM 変更が次のパスを呼んでも、
そのパスは何も注入せず変更も生まないため**そこで止まる**（発火は高々 1 往復増えるだけ）。

> 楽天スーパースクリーナーは実測で失敗していない（注入 50 件）。それでも同じ形にする。
> FR-13 の適用範囲が「同じ欠陥を片方にだけ残さない」と定めており、
> **人が検索する手順が同じである以上、失敗していないのは運の問題**だから。

## 4. TradingView のボタンと canvas 監視を分けるか

**決定: 分けない。1 つの再試行単位にする。**

**1.12.2 まで**はこの形で、**canvas が空振りすると監視とボタンの両方が消えた**。

```javascript
const canvas = $(selectorOf('chart-canvas'))[0]
if (canvas) {
  const canvasObserver = new MutationObserver(canvasObserverCallback)
  canvasObserver.observe(canvas, { attributes: true })
  createKabuLinkMenu()
}
```

| 案 | 判定 |
| --- | --- |
| (a) ボタンだけを再試行の対象にする | 却下。**FR-13 判定基準6 が落ちたまま判定基準5 を通ってしまう。** 判定基準5 は注入された要素の数しか見ないため、「ボタンは出たが銘柄切替に追随しない」を検知できない |
| (b) canvas 監視とボタンを別々の再試行単位にする | 却下。停止条件が 2 つに増え、「監視はあるがボタンが無い」「ボタンはあるが監視が無い」の 4 状態を仕様で管理することになる。**後者は判定基準6 違反そのもの** |
| **(c) 採用** `chart-canvas` と `toolbar-container` の**両方が揃ったときだけ**設置し、監視とボタンを同じ関数で作る | 「ボタンがあるなら canvas 監視もある」が**構造的な不変条件**になる（判定基準6）。両方が揃うまで再試行し、揃わなければ打ち切る |

**(c) で失うものは無い。** canvas 監視の唯一の仕事はボタンの表示切替
（`updateKabuLinkMenu()` は `.ktt-tv-kabuLinkMenu` を走査する）で、
ボタンが無ければ何もしない。「監視だけある」状態には価値が無い。

**「一度作られたボタンが後で消える」（SPEC-CS-12 の既知の制限）は本 ADR の範囲外。**
挿入先が TradingView 側で作り直された場合の再注入は、**タブの寿命いっぱいの常設監視**が要る。
FR-13 が求めているのは「初回の設置に失敗したときの再試行」であり、
判定基準5 も初回の注入しか見ない。**別タスクとして残す。**

## 5. 再試行の「成功」をいつ宣言するか

**決定: サイトごとに述語を分ける。楽天・SBI の 4 本は「静止」を成功とする。**

| 注入先 | 成功の条件 |
| --- | --- |
| `rakuten-cs.js` / `sbi-cs.js` | **これまでに 1 件以上注入した**かつ**直近のパスで新規注入が 0 件**（＝静止した） |
| `rakuten-scr-cs.js` / `sbi-scr-cs.js` | 常設監視を張れた（`document.body` が取れた）＝実質つねに初回で成功 |
| `tradingview-cs.js` | `chart-canvas` と `toolbar-container` が揃い、監視とボタンを設置した |

**「1 件でも注入できたら成功」にしない理由。** 表が段階的に描画されると、
最初のパスで一部の行だけ注入して止まり、**注入 < ヒット**の状態が残る。
これは FR-13 判定基準5 (c) の「注入 = ヒット」を課している 8 対象を直接壊す。
静止を条件にすると、行が増えるあいだは注入し続け、増えなくなった時点で止まる。

代償は**成功の宣言が 1 tick（500ms）遅れる**こと。注入そのものは最初のパスで終わっているので、
利用者から見える遅れは無く、検証ツールの計測にも影響しない（8 の表）。

**残る限界（静止条件そのものの弱点。2026-08-25 追記）。** 「新規注入 0 件のパスを 1 回見たら止める」ため、
**行が時間を空けて 2 回に分かれて現れると 2 回目の行を取りこぼす。**
t=0 の行を t=500 のパスで注入 → t=1000 のパスで `after === before` が成立して停止 →
t=1200 に現れた行には誰も注入しない（`rakuten-cs.js` / `sbi-cs.js` に常設監視は無い）。

| 直し方 | 判定 |
| --- | --- |
| 静止を **N 回連続**で見てから止める | 却下。N をいくつにしても「N+1 回目に現れる行」は取りこぼす。待つ時間だけが伸びる |
| 楽天・SBI にも `document.body` の常設監視を置く | 却下。**FR-13 の範囲を超える**（本要件は「初回の設置に失敗したときの再試行」）。2 本の作りをスクリーナー2種に寄せる変更で、退行の危険が再試行より大きい |
| **採用: 限界として記録し、実装は変えない** | 影響は楽天・SBI の通常ページ2本のみ（スクリーナー2種は常設監視、TradingView はボタン 1 つで足りる）。症状は「たまに一部の行だけメニューが出ない」で、**タブを再読み込みすれば出る**（1.12.2 までのページ全体の欠落より軽い） |

**「たまに一部の行だけ出ない」報告が来たら、まずここを疑う。**

## 6. 二重注入をどう防ぐか（判定基準3）

**決定: 既存の構造的な性質に、明示のガードを 2 つ足す。**

| 層 | 防ぎ方 |
| --- | --- |
| 楽天・SBI 4本（既存・構造的） | `attachMenu()` は**テキストノード**を `span.x-kabu-root` に置換する。置換後の子ノードはテキストノードではないため、同じ要素を何度走査しても 2 度目は置換が起きない（SPEC-CS-02） |
| 楽天・SBI 4本（追加） | 注入対象が `span.x-kabu-root` の内側にある場合は何もしない。**注入したメニュー項目の `<a>` が検出用セレクタに再びヒットする**ため（楽天スーパースクリーナーのヒットが 1150 件になるのはこれ）。パスを繰り返す設計に変わる以上、構造的な性質だけに頼らない |
| TradingView ボタン（追加） | `$('.ktt-tv-kabuLinkMenu').length > 0` なら**設置済み**として成功を返す |
| TradingView 右クリック（既存） | `tr[data-kabu-tantan]` のガード（SPEC-CS-11 条件1）。**本 ADR では触らない** |

## 7. 停止経路を 1 本にする

**決定: 成功・打ち切り・切断・例外の 4 経路すべてを同じ `stop()` に通す。**

| 経路 | 要件 |
| --- | --- |
| 成功 | — |
| 打ち切り（30 秒） | FR-13 判定基準2 |
| **切断状態を検知**（`isExtensionAlive()` が偽） | FR-13 判定基準4 / NFR-14 判定基準2 |
| `setup()` が例外を投げた | NFR-01（サイト側の処理を止めない） |

**切断の判定を毎 tick 行うことは必須。** 楽天・SBI の 4 本は起動時に読んだ `keys` を
キャッシュして使うため、切断後も**拡張 API に触れずに注入できてしまう**。
これは ADR-0005 の 4 で「実害が無くても止める」と決めた経路と同じで、
再試行はその経路を**時間方向に広げる**。門を tick ごとに置かないと NFR-14 判定基準2 が破れる。

例外で打ち切る理由: セレクタの構文誤りのように**次の tick で直らない**失敗が大半で、
30 秒間投げ続けても得るものが無い。例外は外へ出さない。

**「4 経路すべてが `stop()` を通る」はタイマーが張られた後の話**（2026-08-25 追記）。
初回は同期で 1 回試すので、そこで成功または例外になった場合は `setInterval` を張る前に返る。
`stop()` は通らないが、**止めるべきタイマーが存在しない**ので放置は起きない。

## 8. 検証ツールがいつ数えるか（reviewer 指摘への回答）

**決定: 「静止してから数える」を `settleMs` の下限として明文化し、`tab` 到達の 4 対象を 500ms → 3000ms に引き上げる。**

FR-13 判定基準5 は**連続 2 回**の合格を求める。計測点が早すぎると、
正しい実装でも「注入 < ヒット」を拾って落ちる。必要な `settleMs` は次で決まる。

```text
settleMs ≧ 固定待機 + 再試行間隔 + デバウンス + 余裕(500ms)
```

| 到達 | 対象 | 固定待機 | 必要 | 現行 | 変更 |
| --- | --- | --- | --- | --- | --- |
| `goto` | 楽天証券 12ページ | 500 | 1500 | 2000 | 据え置き |
| `goto` | TradingView | 500 | 1500 | 5000 | 据え置き |
| `tab` | 楽天スーパースクリーナー / SBI証券 2ページ / SBI銘柄スクリーニング | 500〜1500 | 2700 | **500** | **3000 に引き上げる** |

`tab` の 4 対象は「人が先に開いたタブ」なので固定待機は明けている**はず**だが、
**開いた直後に合図を出された場合**は明けていない。1 回の実行で +10 秒の代償と引き換えに、
その揺れを消す（連続 2 回の合格を求める要件では、揺れは常に不利に働く）。

**`context-menu` の「注入 = ヒット」には前提がある。** 検出用セレクタは `div.context-menu table`、
注入は `tr[data-kabu-tantan]`。**計測時に開いている `div.context-menu` が 1 つだけ**でなければ等号は崩れる。

| 崩す操作 | 何が起きるか | 現状 |
| --- | --- | --- |
| 入れ子（サブメニュー）を開いたまま数える | 親の `div.context-menu` の内側に `<table>` ごと入るため ヒット 2 / 注入 1 | 現行の `action: 'context-menu'` は右クリックするだけでホバーしない。**発火しない** |
| 「株Link」ボタンのメニューを開いたまま数える | 自前メニューの器が `context-menu` クラスを持つ（SPEC-CS-16 `menuWrap`）ため ヒット 2 / 注入 1 | ツールはボタンを押さない。**発火しない** |

どちらも**ツールの手順が変われば踏む**（FR-19 など）。手順を変えるときは
`context-menu` を等号の対象から外す。これは要件側の判断材料なので analyst へ申し送る。

## 9. やらないと決めたこと

| やらないこと | 理由 |
| --- | --- |
| 固定待機（500ms / 1500ms）の廃止 | 再試行が入っても、初回を早めに撃つ意味は変わらない。**廃止すると (b) 非退行の 11 対象の初回注入タイミングが動く**。FR-13 は「実現手段は設計側」としており、動かさないことを選ぶ |
| 一度作られたボタンが消えた場合の再注入 | 4 の末尾。常設監視が要り、FR-13 の範囲を超える |
| 注入できなかったことの通知 | FR-13「やらないこと」／ NFR-14 の方針 |
| タブの自動再読み込み | 同上 |
| 再試行の間隔・上限を利用者設定にする | 設定項目が増えるだけで、利用者が値を決める根拠を持てない |

## 10. canvas 監視を切断状態で外すか（2026-08-25 追記。**1.13.0 で実装**）

**決定: 外す。** 他の3種の監視と同じ形（コールバック先頭の門 →`disconnect()`）に揃える。1.13.0 で実装した。

`tradingview-cs.js` の canvas 監視（ボタンの表示切替）は 1.12.0 以来、
切断状態の門も `disconnect()` も持たない**唯一の監視**だった。
1.13.0 で 4 の決定によりこの監視は `retrySetup()` の `setup()` の中で張るようになったため、
**FR-13 判定基準4「切断状態を検知したら、再試行を停止し、そのために張った監視も外すこと」に直接かかる。**

| 案 | 判定 |
| --- | --- |
| (a) SPEC-CS-19 の除外として明記し、実装は変えない | 却下。実害の大小ではなく**規則に例外を作ること**が代償。「本拡張が張る監視はすべて切断で外れる」という不変条件が崩れ、次に監視を足す人がどちらに倣うか決められない |
| **(b) 採用** 他の3種と同じ形に揃える | 正常時の振る舞いは変わらず（門が真なら従来どおり）、規則が例外なしで保てる。`canvasObserverCallback` は監視オブジェクトを参照できないため、`bodyObserver` と同じく無名コールバックで包む |

**リリースブロッカーではなかった。** 切断状態でこの監視が行っていたのは自前の
`.ktt-tv-kabuLinkMenu` の show/hide だけで、**要素を追加しないため NFR-14 判定基準2 は破っていない**。
それでも 1.13.0 に入れたのは、(a) の代償（規則の例外）を次版まで残さないため。
実装形と検証手順は [SPEC-CS-22](../specs/content-scripts.md) の
「canvas 監視の切断時の停止」（検証表 9）。

| 検証 | 内容 |

| 自動（正常時の非退行） | `tests/tradingview.spec.mjs` の「TradingView: 「株Link」ボタンの表示」（2026-10-12〜。旧手動確認 A-8 の拡張側。NFR-14 判定基準3） |
