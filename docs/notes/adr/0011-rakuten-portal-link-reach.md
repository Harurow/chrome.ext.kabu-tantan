## 1. 到達方法をどう変えるか

**決定: ログイン済みページに実在する `<a href>` の href を読み取り、その URL へ遷移する（案 c）。**

| 案 | 判定 |
| --- | --- |
| (a) 組み立て URL にクエリ・パラメータを足して直打ちを成功させる | 却下。エラー画面に飛ばされる原因が未特定（SPEC-SC-18）で、足すべき値を実 DOM でも通信でも確認していない。当て推量で1回ずつ試すことになり、外れても「なぜ外れたか」が分からない |
| (b) FR-15 の「利用者がタブを開いておく例外」へ4対象を移す | **却下せず次善として残す。** 確実だが利用者の手順が4つ増え、FR-15 が定めた「12ページはツールが自動で開く」を4ページ分やめることになる。(c) が成立しないと判明した場合にここへ戻る（7 の「外れたときの次の一手」） |
| (c) **採用** ログイン済みページの `<a href>` を1つ選び、その href へ遷移する | 利用者の手順は増えない（判定基準4）。CON-10 の許容行に既にある操作だけで済む。失敗しても現状と同じ観測に退避でき、**失敗の理由が結果ファイルに残る**（次の一手が決まる） |
| (d) ログイン後の画面遷移を自動化する（メニュー操作・フォーム送信を含む） | 却下。CON-10 が禁止 |

**(c) は CON-10 の緩和を必要としない。** 許容行の1つ目「ログイン済みセッションで対象ページの URL へ
遷移する ✓」にそのまま当たる。2026-08-24 に足した2つ目の許容行（リンクのクリック）は**使わない**（3 参照）。

## 2. リンクをどう特定するか

**決定: 遷移先 URL のパス（`menuSelectors[].url`）だけを手がかりにする。**

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 遷移先 URL の**パスとクエリ**で `a[href]` を絞る | 手がかりが `menuSelectors[].url` と `targets.mjs` の定数 ＝ **既にある情報源**（SPEC-SC-02）で、検証ツールに新しい知識も推測値も持ち込まない。遷移**前に**遷移先が対象ページだと確定できるので、CON-10 の「遷移先は FR-12 の検証対象ページに限る」を機械的に守れる。**当初はパスだけで足りると判断したが誤りだった**（9-4） |
| (b) リンクの表示名（テキスト）で探す | 却下。理由は2つ。**(1)** 表示名を実測できず、`targets.mjs` に推測値の配列を持つことになる。外れれば毎回この4ページが未到達に戻り、外れたことに気づく手段も無い。**(2)** より重い問題として、表示名だけで遷移先を決めると**対象ページ以外へ遷移しうる**。`保有商品一覧・国内株式` の候補に `国内株式` を挙げれば、グローバルナビの「国内株式」トップへ出る。CON-10 の条件（遷移先は検証対象ページに限る）を破る。**遷移前にパス一致を必須にする限り、表示名を足しても絞り込みは1件も増えない** |
| (c) クラス名・`id`・グローバルナビの DOM 構造で辿る | 却下。実 DOM を知らずに書けば当て推量になる。当たっても楽天証券の改修で無言のうちに壊れ、その壊れ方は「この4ページだけ永遠に ⚠️」＝ 今と同じ症状。CON-11 の趣旨（見た DOM を鵜呑みにしない）にも反する |
| (d) 何番目のリンク、といった位置指定 | 却下。(c) より弱い。根拠が無い |

> **(b) を却下したことは「フォールバックを持たない」ことを意味しない。**
> 退避は**別の手がかりへ**ではなく、**従来の直打ちへ**倒す（4）。手がかりを増やすほど
> 「どの手がかりで着いたか分からないページを検証する」危険が増える。

### パスの一致を前方一致にしない

`/app/info_jp_prc_reg_lst.do` と `/app/info_jp_prc_reg_lst_edit.do` は、
現物の文字列では `.do` の位置が違うため前方一致でも衝突しない。
それでも**規則としては「完全一致、またはパスパラメータ `;` が続く場合」に固定する**。
楽天証券が `.do` を廃した命名に変えたときに、静かに別ページへ行くのを防ぐため。

## 3. どうやってたどるか（クリックするか）

**決定: クリックしない。資格審査を通った href へ `page.goto()` する。`referer` だけ実際のクリックと同じ値を付ける。**

| 案 | 判定 |
| --- | --- |
| (a) アンカーを左クリックする | 却下。CON-10 が許容してはいるが、**`addEventListener` で付いたハンドラは外から見えない。** インライン `onclick` を除外しても、実体が `form.submit()` や XHR POST であるリンクを踏む可能性が消えない。踏んでからでは送信を取り消せない。CON-10 の「判断がつかないものは採らない」に従う |
| **(b) 採用** href を読み取り `page.goto(href)` する | `page.goto()` は常に GET で、**POST が起きる経路が実装上存在しない**。JS ハンドラは定義上発火しない。CON-10 の許容行1（URL へ遷移する）にそのまま当たり、許容行2（クリック）を使わずに済む。**この選択は自動テストで固定していた**（`links.mjs` のソースにクリック・送信の呼び出しが現れないことを文字列で検査。旧 `到達リンク` 40・41。9-5）。**14 の撤去で 40・41 も消えたため、`check.mjs` を見る `セレクタ定義` 52 に置き直した**（SPEC-SC-16） |
| (c) (b) に加えて、失敗したらクリックで再試行する | 却下。同じページへ2回アクセスすることになり（CON-10 の最小性）、しかも2回目は (a) の危険をそのまま持つ |

### `referer` を付ける理由

`page.goto()` は既定で `Referer` を送らない。直打ちが失敗する原因が遷移元の有無であった場合、
href だけ正しくしても同じエラー画面に着く。**アンカーを見つけたフレームの URL を `referer` に渡す。**

- これは実際にそのリンクを押したときにブラウザが送る値と同じで、偽装ではない
- ヘッダを1つ足すだけで、リクエストは GET のまま。POST 化しない
- 付けない場合と付ける場合で2回遷移する案は採らない（CON-10 の最小性）。**最初から付けて1回で行く**

## 4. たどれなかったときにどこへ倒すか

**決定: 従来の組み立て URL による `goto` へ退避し、判定は ⚠️ のままにする。**

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 直打ちへ退避し、退避したことを備考に残す | 最悪でも現状（1.13.0）と同じ観測になる。**非退行が構造的に保証される。** 退避理由を「リンクが無い」「素の `a href` でない」に分けて残すので、次の一手（1 の案 b へ戻るか）が結果ファイルだけで決まる |
| (b) 退避せず、リンクが無ければ即 ⚠️ | 却下。現状より情報が減る。直打ちの結果（題名がエラー画面かどうか）は今も判断材料になっている |
| (c) たどれなかったら ❌（破損）にする | 却下。**FR-22 が解いた問題を作り直す。** ツールが到達できないことは拡張機能の破損ではない。❌ に混ぜると「直すべきもの」と「直さなくてよいもの」が再び同じ記号になり、終了コード 1 が意味を失う |
| (d) 判定記号を増やす（例: 🔗 到達手段なし） | 却下。FR-22「やらないこと」が記号を4つに固定している |
| (e) たどれなかったら —（未実施）にする | 却下。`--only` の除外・ログインなし・タブ未開封と混ざる（SPEC-SC-10 の未実施表）。「実施したが着けなかった」は ⚠️ の定義そのもの |

## 5. FR-23 判定基準1 との衝突を提起した（analyst が決着）

**決定（設計側）: たどれなかった対象を ✅ / ❌ に倒さない。この扱いが判定基準1 と衝突して見えたので要件側へ提起した。**
**決着（2026-08-29 / analyst）: 判定基準1 は緩和しない。⚠️ が残る実行は FR-23 の未達として記録する。**

FR-23 判定基準1 は「4ページそれぞれについて ✅ / ❌ のいずれかの判定が出ること
（⚠️ や — のままにならないこと）」を求める。一方 4 の決定により、リンクをたどれなければ ⚠️ が残る。

| 選択肢 | 帰結 |
| --- | --- |
| たどれなかった対象を ✅ / ❌ に倒し、判定基準1 の形を整える | 却下。✅ に倒せば破損を見逃し（FR-12 の目的が消える）、❌ に倒せば 4 の (c) と同じ害。**どちらも嘘をつく** |
| **採用** ⚠️ ＋ 理由を残し、衝突は要件側に判断を委ねる | 実装はどちらに決着しても変わらない（下記）。設計が勝手に要件の判定条件を読み替えない |

### analyst の決着（2026-08-29）

**衝突は「判定基準1 を**ツールが実行時に守る規則**と読んだ場合にだけ起きる」**というのが結論。
判定基準は**要件が満たされたかを判定する条件**であって、ツールへの指示ではない。

| # | 確定した読み方 |
| --- | --- |
| 1 | ツールは到達できなかった対象を ✅ / ❌ に倒してはならない。⚠️ ＋ 理由を残す。これは **FR-22 の規則の適用であって緩和ではない**（要件が要求する側の振る舞い） |
| 2 | **⚠️ が残る実行は「FR-23 が未達」を意味する。** 判定基準1 の文言は変えない |
| 3 | 手段が効かなければ 1 の案 (b)（FR-15 の「利用者がタブを開いておく例外」へ移す）に切り替える |

設計側が出していた文言案（「**たどれた実行では** ✅ / ❌ が出ること」）は**採られなかった**。
その文言だと **⚠️ が残ったままの実行を FR-23 の達成として記録できてしまう**ため。
正本は FR-23 の「判定基準 1 の読み方」。

> **この決着で実装は変わらない。** 提起の時点で「差し戻しの結論がどちらでも作るものは同じ」と
> 書いたとおりで、変わったのは**記録の扱い**（⚠️ が残る実行を達成と呼ばない）だけ。
> **リンクをたどる方式は「判定基準1 を満たしうる手段」であって、実装したこと自体は達成ではない。**
>
> 本節を経緯として残すのは、次に同種の衝突を見つけたときに
> 「判定基準を実行時の規則と読み違えていないか」を先に疑うため。

## 6. 非退行（他の8ページ）をどう担保するか

**決定: `reach` の値で経路を分け、既存8対象のコードパスに一切触れない。**

| 案 | 判定 |
| --- | --- |
| **(a) 採用** `reach: 'link'` を新設し、4対象だけに付ける | 8対象は `reach: 'goto'` のまま。URL の組み立て・`settleMs`・判定・手がかり採取の経路が変わらない。差分がターゲット表の4行に閉じるので、退行の有無をコードを読んで確認できる |
| (b) 楽天証券の全12対象をリンク経由にする | 却下。今 ✅ が出ている8対象を、実測できていない前提（ポータルにリンクがある）に賭けることになる。FR-23 判定基準3 に正面から反する |
| (c) 直打ちを先に試し、エラー画面ならリンク経由に切り替える | 却下。同じページへ2回アクセスする（CON-10 の最小性）。「エラー画面か」の判定は題名の目印に依存し、目印が当たらない形のエラー画面では切り替わらない |

到達後のパス確認（SPEC-SC-26）も `reach: 'link'` の対象にだけ掛ける。
8対象に掛けると、着いているのに ⚠️ に落ちる新しい誤判定を持ち込みうる。

## 7. 推測に頼っている箇所と、外れたときの次の一手

**設計時点で実測できていない前提を、外れたときの観測とあわせて明示する。**
どれが外れても**現状より悪くならない**（4 の退避）ことが、この設計を今出せる根拠。

| # | 前提 | 実測 | 外れたときの観測 | 次の一手 |
| --- | --- | --- | --- | --- |
| 1 | ログイン後のポータルに、対象4ページへのリンクが `a[href]` として存在する | **外れた（1対象）。** お気に入り編集で `no-candidate`（2026-08-30） | 備考が `到達方法: URL 直打ち（パス一致のリンクが見つからない）` | ハブの取り方を見直す（別の楽天証券ページを起点にする）。それでも無ければ 1 の案 (b) へ |
| 2 | そのリンクが素の `a href` で、インラインハンドラを持たない | **外れた（3対象）。** お気に入り・保有商品一覧2ページで `not-qualified`（2026-08-30）。**ただし6条件のどれで落ちたかは不明**（10） | 備考が `到達方法: URL 直打ち（パス一致のリンクが GET 遷移の条件を満たさない）` | **条件6（クエリ）なら広げうる、それ以外なら 1 の案 (b) へ。** どちらかは 10 の内訳で決める |
| 3 | 直打ちが失敗する原因が「URL の作りの差」または「遷移元の欠如」である | **未確認**（原因未特定。SPEC-SC-18） | リンク経由でもエラー画面（題名が `エラー …`）に着き ⚠️ のまま | 原因はセッションでも Referer でもない（画面遷移の状態を持っている）と分かる。1 の案 (b) へ |
| 4 | ポータルのリンクのパスが `menuSelectors[].url` と一致する | **未確認** | 1 と同じ観測（リンクが見つからない） | パスが違うなら**拡張機能側も動いていない**（`location.href.indexOf(menuSelector.url)` で判定するため）。その場合は FR-02 の破損であり、FR-20 と同じ扱いで別要件にする |
| 5 | ポータルのリンクのクエリが空、または `eventType=init` だけである | **未確認**（1.15.0 で追加した資格6。9-4 (a)） | 2 と同じ観測（`GET 遷移の条件を満たさない`） | 実口座で走らせた結果、必須クエリ（`rowNo` など）を持つと分かったら、**そのキーが「開くだけ」を意味すると確認できた場合に限り** `RAKUTEN_OPEN_QUERY` を広げる。確認できなければ広げず、1 の案 (b) へ |

> 4 は「一致しないなら拡張機能も壊れている」という関係になっており、
> **手がかりをパスに限ったことで、ツールの到達失敗と拡張機能の破損が同じ根に結びつく。**
> 表示名で探す案（2 の (b)）はこの性質を持たない（拡張機能が動かないページに到達して ✅ を出しうる）。

## 8. 実装の分担（純関数と副作用）

SPEC-SC-20（手がかり）と同じ分担にする。**ページ側は生の値だけを返し、判断は Node 側の純関数で行う。**

| 層 | 持つもの | 自動テスト |
| --- | --- | --- |
| ページ側（`frame.evaluate`） | `a[href]` の総数・パス一致の総数・候補の生の値（`rawHref` / `href` / インラインハンドラの有無）と、`location.pathname`。**判定は持たない**（9-4 (b)） | 不可（ブラウザが要る）。ただし**実物のコールバックを Node 上で実行する**配線テストは書ける |
| Node 側（純関数） | パス一致規則 `matchesTargetPath()`、クエリ規則 `isOpeningQuery()`、資格審査と選択 `pickLink()` | **可**（SPEC-SC-16 の `到達リンク`） |
| Node 側（副作用） | `goto`・パス確認の呼び出し・備考への1行 | 配線テスト（スタブ）＋ 半自動（実行して結果ファイルを読む。**未実施**） |

ログインが要る経路は自動テストにできない（CON-10）ため、**純関数に落とせるところを最大化する**。
`pickLink()` が「なぜ落としたか」を返すのは、備考の文言（退避理由）を純関数の側で決めるため。

## 9. 実装後に増えた判断（1.15.0）

| # | 論点 | 決定 |

| 9-1 | サイト固有の値をどこに置くか | `targets.mjs` の `RAKUTEN_ORIGIN` と `RAKUTEN_OPEN_QUERY` が1箇所で持ち、`sites[].link` に載せて純関数へ渡す。対象（`targets[]`）にフィールドは足さない。組み立て URL と同じ値を1箇所で持てて**ずれようがない**（NFR-13）。`links.mjs` は引数で受け取り、サイト固有の値を持たない。**受け取り方は 9-6 で是正した** |

### 9-4. レビュー（1.15.0）で覆した2つの判断

#### (a) 資格審査がパス止まりだった 🔴

### 9-5. 遷移する側の担保（🟡 M-3）

`goto` を実際に呼ぶのは `check.mjs` 側なのに、構造テストが `links.mjs` しか見ていなかった。

### 9-6. サイト固有の値は「検証中のサイト定義」から引く（再レビュー s-2。是正済み）

**指摘:** `check.mjs` の `findPortalLinkAsync()` が `RAKUTEN_ORIGIN` を名指しで `import` している。
**関数名は `reach: 'link'` 全般なのに、値だけ楽天固定。**

| | |
| --- | --- |
| 是正前の動作 | 正しかった（`reach: 'link'` は楽天証券の4対象だけ） |
| 何が起きるか | 他サイトに `reach: 'link'` を付けると、**楽天のオリジンでハブを走査して 0 件**になる |
| なぜ危ないか | 0 件は `no-candidate` → 直打ち退避で、**例外も判定の変化も出ない**。4 で設計した「悪化しない退避」が、ここでは**設定ミスを隠す**方向に働く。**静かに壊れる形**であり 9-4 (b) と同じ型 |

> **9-1 の判断（値は `targets.mjs` が1箇所で持つ）は覆っていない。** 変わるのは**受け取り方**だけで、
> 「組み立て URL と同じ値を使う」ことは保たれる。振る舞いも変わらない（楽天の4対象は同じ値を使う）。
>
> **教訓: 「純関数はサイト固有の値を持たない」と決めたら、呼び出し側も同じ規律で書く。**
> 純関数の側だけを一般化しても、呼び出し側が固定なら一般化されていない。

>
> **副産物: `RAKUTEN_ORIGIN` がモジュール外から参照されなくなった。**
> `export` は外してよいが、**未使用の `export` は ESLint が検出しない**ため放置すると
> 「外から使われている」と読者に誤解させる。振る舞いに影響しない整理なので、
> **次に `targets.mjs` を触るときに外す**（SPEC-SC-26「`export` は外部から参照するものだけに付ける」）。
> `RAKUTEN_OPEN_QUERY` は自動テストが参照するので残す。

**7 の前提2（リンクが素の `a href` である）は当たっていた。** 外れていたのは
「`eventType=init` の完全一致で足りる」という**こちらの条件の側**である。

### 何を許すか

**決定: 許可列挙を維持し、キーを2種類に分ける。`pinned`（値まで一致）＋ `anyValue`（キーだけ許す）。**

| 案 | 判定 |
| --- | --- |
| (a) 「`eventType=init` があれば他のキーは無視する」 | **却下。** `?eventType=init&rowNo=3` のような**未知のキーを何でも通す**。禁止列挙より弱く、実質「クエリを見ない」に等しい。資格6 を足した理由（同一パスで操作を切り替える）が消える |
| (b) 操作を表すキー（`delete` / `remove` 等）が**無い**ことを条件にする（禁止列挙） | **却下。** FR-08 で3度繰り返した誤りの再演。**未知のキーが危険側に倒れる。** 楽天が別の語を使えば素通りし、しかも**素通りしたことに気づけない**（通れば ✅ になるので診断が出ない） |
| **(c) 採用** キーの許可列挙を広げ、`eventType` だけ値を固定する | 未知のキーは**落ちる側**に倒れる（FR-08 の教訓）。落ちても `not-qualified` ＋ 内訳が出るので、**次の一手が結果ファイルだけで決まる** |
| (d) 値まで含めて許可列挙する | **却下。** `l-id` はトラッキング値、`gmn` 等は画面ごとに異なり、**列挙できない**。加えて値は結果ファイルに出していない（SPEC-SC-14）ので、列挙するための材料が無い |

### どのキーを許すか

| キー | 判断 | 根拠 |
| --- | --- | --- |
| `eventType` | 許す（**値は `init` に固定**） | 組み立て URL と同じ情報源。**サイトが操作の種類をこのキーで表している**と読めるので、ここを緩めると資格6 が骨抜きになる |
| `gmn` / `fmn` / `lmn` / `smn` | 許す（値は問わない） | global / first / large / small menu の階層。**どのメニューから来たかを表すだけ**で、遷移先の内容にも状態にも影響しない |
| `l-id` | 許す（値は問わない） | リンク識別子（流入元のトラッキング）。同上 |
| `local` / `type` / `sub_type` | **許さない** | 「表示の絞り込み」と読めるが**確証が無い**。同一パスで**操作**を切り替える可能性を否定できない。**CON-10「判断がつかないものは採らない」に従う** |

#### なぜ `pinned` のキーの**不在**は許してよいのか（最終レビュー W-4）

規則5 は `eventType` が**無い**リンク（`?gmn=J` だけ等）を通す。
観測した3対象の和集合にはいずれも `eventType` が含まれていたので、
**「観測の裏付けが無い緩和」という点では `local` / `type` / `sub_type` と同じに見える。**
それでも残すのは、**両者で広がるものが違う**からである。

| | `local` 等を許す | `pinned` の不在を許す（規則5） |
| --- | --- | --- |
| 何が増えるか | **許可集合に未知のキーが1つ増える**。そのキーが何を切り替えるか分からない | **増えない。** 通るのは「許可集合のキーだけで構成され、`eventType` が無い」リンク |
| 通ったリンクに何が残るか | `type=…` など**意味の分からない指示**が残る | メニュー階層（`gmn` / `fmn` / `lmn` / `smn`）と流入元（`l-id`）**だけ** |
| 操作を表しうるか | **否定できない** | **`eventType` が無い**。「操作は `eventType` で表される」という本節の読みを採る以上、**その不在は「操作でない」側の証拠** |

つまり規則5 は許可集合を広げず、**資格6 の本体（規則3: キーがすべて許可集合に属する）が
そのまま効いている状態**を保つ。`eventType` の不在を落とす（＝ `pinned` 必須にする）と、
**ポータルのナビゲーションリンクが `eventType` を持たない場合に到達できなくなる**。
和集合からは「少なくとも1本は `eventType` を持つ」ことしか分からず、
**それが許可集合だけで構成された候補と同一である保証は無い**（上記「和集合の読み方」と同じ理由）。

> **落とす判断もありえた。** 実測3対象は `pinned` 必須でも通る可能性が高い。
> 残す側に倒したのは、**規則5 が許可集合を広げない**ことと、
> **落とすと「取りこぼす」側の失敗が増える**（⚠️ が残り、しかも診断は「キーはすべて許可集合内」で読めない）ため。
> **緩和後に資格6 を支えているのがキー名の許可列挙だけになった**のは事実で、
> そこが破れる（許可集合のキーが操作を切り替える）ときは規則5 の有無に関わらず破れる。

### 和集合の読み方を誤っていた（最終レビュー C-1 の是正）

当初ここには「`local` / `type` / `sub_type` を許さなくても、対象ページが通らないとは限らない」と書いた。
**`クエリ 1 件` の対象については誤りである。**

| 事実 | 帰結 |
| --- | --- |
| 内訳は**候補ごとに最初に落ちた条件を1つ**数える（SPEC-SC-26 の「内訳の規則」1） | `クエリ N 件` の N ＝ 資格6 まで来て落ちた候補の数 |
| 資格を満たした候補が1つでもあれば `followed` になり内訳は出ない | **内訳が出ている＝通った候補は無い** |
| `queryKeys` は資格6 で落ちた候補からだけ集める | **N = 1 なら、和集合はその1本のリンクのキー集合そのもの** |

したがって **保有商品一覧・国内株式（クエリ 1 件 / キー9種）は、1.16.1 でも確実に落ちる。**
和集合の議論が効くのは **N ≧ 2 の対象だけ**（保有商品一覧・すべては N = 2 なので、
どちらか一方が許可集合だけで構成されていれば通る）。

**「実行してみないと分からない」と書いてはいけなかった。** 出ている数字だけで決まる。

> **ここで「たぶん絞り込みだから許す」と倒さない理由。** 利用者の実口座で走るツールである。
> 誤って操作リンクを踏んだときの害は**取り消せない**。
> 一方、許さなかった場合の害は「⚠️ が1つ残る」＝ 1.13.0 と同じ観測で、**取り返しがつく**。
> **非対称なので、確証が無い側は許さない。**
>
> 許すとしたら、**そのキーの値まで見て「絞り込みである」と確認できたとき**。
> ただし値の記録は SPEC-SC-14 が禁じている（NFR-12）。**値を出すために制約を緩める判断は、
> 別途 ADR を起こしてから行う**（本 ADR の範囲外）。

### 「お気に入り編集」は別の話

`no-candidate` で、**10フレーム・561リンクを読んだうえでパス一致 0 件**。
`（うち読めなかったフレーム N 件）` が出ていないので、**走査漏れではなく本当に無い**
（🟢8 で足した `unreadable` が効いた。10-2 の 6）。

**決定: 他3対象を通してから再判定する。** ハブは対象ごとに走査し直すため、
お気に入り（1つ前の対象）に到達できれば**その画面がハブに加わり**、そこにある編集リンクが候補になる。
編集リンクは一覧画面にあるのが自然で、ログイン直後の画面に無いのは筋が通る。

| 再実行の結果 | 次の一手 |
| --- | --- |
| お気に入り編集も通った | 連鎖の仮説が当たり |
| お気に入り編集だけ `no-candidate` のまま | **ハブの取り方を見直す**（対象ページに到達した直後の画面を明示的にハブへ加える等）。それで駄目なら下記の「終端」へ |

### 終端（同じ判断を繰り返さないための出口）

> **状態: 提案。利用者の同意待ち（FR-23 の確認事項）。**
> 「4対象のうち1つだけを FR-15 の例外へ回す」は**要件が挙げていなかった新しい選択肢**である。
> FR-23 の「取りうる方向」は4対象をまとめて移す前提だった。

**`local` / `type` / `sub_type` を許すかどうかは、値を見ない限り判断材料が増えない。**
値の記録は SPEC-SC-14 が禁じており（NFR-12）、**禁止を緩めない限り何回実行しても同じ内訳が出る。**
再実行を繰り返しても進まないので、次で終端する。

| # | 条件 | 決定 |
| --- | --- | --- |
| 1 | **候補が1件（`クエリ 1 件`）で、そのキー集合に許可集合外のキーが含まれる対象** | **その対象だけ** FR-23 の「取りうる方向」2つ目（**FR-15 の「利用者がタブを開いておく例外」**）へ回すことを**提案する**（**同意待ち**。上記の状態）。**CON-10 は緩めない** |

**現時点で 1 に当たるのは 保有商品一覧・国内株式 の1対象だけ。**

道連れにする理由が無いため。

### 読めない落ち方（最終レビュー W-2）

規則5（`pinned` は無くてもよい）と規則4（重複キーは落とす）を入れたことで、
`not-qualified` の残り方が**3通り**になったが、**結果ファイルから区別できるのは1通りだけ**
（SPEC-SC-26「資格6 の落ち方は3通りあり、結果ファイルからは1通りしか読めない」）。

**「クエリ N 件」なのに「キーはすべて許可集合内」が出たら、値違いか重複である。**
このとき採る手は次のとおり。

| 疑い | 根拠 | 手 |
| --- | --- | --- |
| `eventType` の値が `init` でない | **値は一度も観測していない。** 組み立て URL が `eventType=init` を使っているのは、ツール側がそう組み立てているだけで、**ポータルのリンクがそうだという証拠ではない** | `pinned` から `eventType` を外し、`anyValue` へ移すかを検討する。**ただし「操作は `eventType` で表される」という読みを捨てることになる**ので、捨てる前に本節の「どのキーを許すか」を書き直す |
| 同一キーの重複 | 楽天証券の URL 組み立てで同じキーが2度出る形は観測していない | 規則4（重複を落とす）を緩めるかを検討する。**重複を許すと「最後の値が勝つ」等の解釈がサイト依存になる**ので、優先度は低い |

**どちらも「実行を1回増やして分かること」ではない**（同じ内訳しか出ない）。
判断材料を増やすには**値を出す**しかなく、それは SPEC-SC-14 の変更＝別の ADR を要する。
**そこまでするより、上記「終端」の 1 に倒すほうが安い。**

> **「許すクエリを広げれば通る見込み」は、`eventType` の値が `init` である場合に限る。**
> 値は未観測なので、**3対象が通ることも確定していない**。

### この判断で受け入れる代償

**楽天がクエリのキーを増やすたびに、その対象は ⚠️ に戻る。**
許可列挙を選んだ以上これは避けられない。受け入れる根拠は次の2つ。

| | |
| --- | --- |
| 悪化しない | 落ちても直打ちへ退避するだけで、**1.13.0 と同じ観測**（4 の設計） |
| 気づける | `not-qualified` ＋ **内訳とキー名**が出るので、**次の一手が結果ファイルだけで決まる**（10 で足した診断） |

逆に禁止列挙（案 b）だと、**未知のキーは通ってしまい、通った以上は診断も出ない**。
「静かに危険側へ倒れる」ことになり、**気づく手段が無い**。
**許可列挙の代償は『うるさい失敗』で、禁止列挙の代償は『静かな成功』である。** 前者を採る。

## 13. 前提が崩れた: 直打ちの失敗は「クエリの欠落」だった可能性が高い

| | |
| --- | --- |
| 状態 | 採択（2026-08-30）。**1.18.0 で実装**（4対象を `goto` に戻し、実測クエリを付けた。SPEC-SC-06 / SPEC-SC-26）。**実サイトでの検算は未実施**（`docs/notes/manual-checklist.md` C-1） |
| 出典 | 利用者が提示した4ページの**アドレスバーの URL**（セッション ID を除く）。**結果ファイルではない** |

**利用者が ⚠️ の4ページを実際に開き、その URL を教えてくれた。**
本 ADR は「URL 直打ちではエラー画面に飛ばされる（遷移元が要る等）」を発端としていたが、
**組み立てていた URL のほうが実際の形と違っていた。**

### 組み立て URL と実測の突き合わせ

`targets.mjs` の `rakutenUrl()` は `パス + セッション + クエリ` を作る。
**4対象は `query` を渡していない**ので、組み立て結果は**クエリがまったく無い**。

| 対象 | ツールが組み立てていた URL | 利用者のアドレスバー |
| --- | --- | --- |
| お気に入り | `/app/info_jp_prc_reg_lst.do;<session>` | `…?eventType=init&gmn=J&smn=01&lmn=01&fmn=02` |
| お気に入り編集 | `/app/info_jp_prc_reg_lst_edit.do;<session>` | `…?eventType=init&pageNumber=1` |
| 保有商品一覧・すべて | `/app/ass_all_possess_lst.do;<session>` | `…?eventType=directInit&type=&sub_type=&local=&gmn=S&smn=01&lmn=01&fmn=01` |
| 保有商品一覧・国内株式 | `/app/ass_jp_stk_possess_lst.do;<session>` | **同じ文字列**（パスだけが違う）。**対称性からの推論ではなく、この対象の URL も利用者が個別に提示した** |

**パスもセッションの置き方も合っていた。違うのはクエリだけ**（有無そのもの）。

### なぜ他の8対象は動いていたのか

| 対象 | クエリ | 結果 |
| --- | --- | --- |
| ランキング6ページ | 無し（組み立ても実際も） | ✅ |
| 国内株式・個別銘柄 | `?eventType=init&dscrCd=…`（`RAKUTEN_STOCK_QUERY`） | ✅ |
| 国内株式・株価検索 | 同上 | ❌（FR-20。別の破損） |
| **今回の4ページ** | **組み立ては無し／実際は有り** | ⚠️ |

**`eventType` で処理を振り分ける `.do` は、それが無いとエラー画面を返す**、と読むと
「8対象は動くのに4対象だけ落ちる」がきれいに説明できる。
**`eventType` を渡している対象（個別銘柄）は動き、渡していない対象のうち
`eventType` を要求するものだけが落ちていた。**

### 1 の案 (a) を採り直す

1 で「(a) 組み立て URL にクエリ・パラメータを足して直打ちを成功させる」を**却下**していた。
却下理由は「**足すべき値を実 DOM でも通信でも確認していない**。当て推量で1回ずつ試すことになる」。

**その理由は今日まで正しかったが、値が分かった時点で消えた。** 当て推量ではなく**実測の写し**になる。

| 案 | 再評価 |
| --- | --- |
| **(a) 実測どおりのクエリを付けて直打ちする** | **採用（実測して確かめる）。** CON-10 の許容行1（ログイン済みセッションで対象ページの URL へ遷移する）そのもので、**リンクを探す機構が要らない**。最小性の原則に最も合う |
| (c) ポータルのリンクをたどる（本 ADR の現行方式） | **保留。** (a) が通れば**不要になる**。CON-10 上も、探索と資格審査という機構を持つぶん (a) より重い |
| (b) FR-15 の例外へ回す | 変わらず退避先。(a) も (c) も駄目なときだけ |

> **CON-10 の観点では直打ちのほうが安全である。**
> リンクをたどる方式は「素の `a href` か」「クエリが開くだけか」を**こちらで判定する**必要があり、
> 判定を誤れば操作リンクを踏みうる（だから資格1〜6 と診断3種を積み上げた）。
> 直打ちは**利用者が実際に開いている URL をそのまま開く**だけで、判定する対象が無い。
> **機構が要らないほうが安全**という、CON-10 の「最小性の原則」がそのまま効く。

| 4 | なおエラー画面に着くなら、原因はクエリではない。**`reach: 'link'` に戻す**（1行）。11・12 の許可集合の議論もそこで再開する |

**リンク機構は 3 の結果が出るまで消さない。** 消してから戻すのは高くつく。

> **ただし「`reach` の1語で戻せる」は正しくない。** 実測で `eventType=directInit` が見つかった以上、
> `reach: 'link'` に戻しても**資格6（`pinned: { eventType: 'init' }`）で落ちて `not-qualified` になる**。
> 構文上は1語でも、**機能として戻すには 11 の許可集合を書き直す必要がある**
> （`directInit` を許すか、`eventType` を `pinned` から外すか）。
> 段取り4 は「1語」ではなく「**11 の書き直し ＋ 1語**」である。

**クエリは実測どおりに写し、推測で削らない。** `type=` / `sub_type=` / `local=` が空でも、
`gmn` / `smn` / `lmn` / `fmn` の値がページごとに違っても、**そのまま持つ**。
「空だから要らない」「メニュー階層は飾りだろう」は、また当て推量になる。

### 11・12（許可集合の拡張）の扱い

**保留する。** 資格審査は**ポータルのリンクを踏むための仕組み**なので、
踏まなくてよいなら要らない。`pageNumber` を足すか、`eventType` に `directInit` を許すか、
`type=` の空値をどう扱うかは、**上記 4 に落ちたときだけ再開する**。

> **ただし、そこで得た事実は消えない。** 実測は次の3つを確定させた。
> **(1)** `eventType` の値は `init` とは限らない（`directInit` がある）。
> **(2)** `type` / `sub_type` / `local` は**空値**で付いてくる＝絞り込みの指示になっていない。
> **(3)** `pageNumber` が付くページがある。
> **11 で「`eventType` は `init` に固定」と書いた根拠（サイトが操作をこのキーで表す）は、
> 値が2種類ある時点で弱まっている。** 再開するときは 11 の表から書き直す。

### 教訓

| # | 何を誤ったか |
| --- | --- |
| 1 | **原因を特定しないまま到達方法を作り替えた。** 発端は「直打ちでエラー画面に飛ばされる（**遷移元が要る等**）」で、括弧の中は**推測**だった。1 の (a) を却下したとき「原因が未特定」と自分で書いておきながら、**原因を特定する手を打たずに** (c) の設計に進んだ |
| 2 | **利用者に URL を尋ねる安さを見誤った。** 10 の案 (c)「実 DOM を利用者に見てもらう」を「手間が大きい」と却下したが、**今回必要だったのはアドレスバーのコピー1回**である。DOM 調査とアドレスバーの確認を同じ重さで見積もっていた |
| 3 | **診断出力は「値」を出さない設計にした**（NFR-12 との両立。判断自体は正しい）。**その結果、`eventType` の値も空値も結果ファイルからは永久に読めない。** 出力を広げるのではなく**人に1回聞く**のが、制約を緩めずに済む安い手だった |

> **1 が本体である。** 2・3 は「原因を特定する手」を探さなかったことの現れでしかない。
> **「なぜ失敗するか」が未特定のまま「どう回避するか」を設計すると、
> 回避策の側に見えない前提が積み上がる。** 本 ADR は 9・10・11・12 と是正を重ねたが、
> そのすべてが**回避策の内部の整合**であって、前提そのものは一度も検算していなかった。
