# ADR-0003 TradingView の右クリックメニューを入れ子にする

| | |
| --- | --- |
| 状態 | 採択（2026-08-23）。**実装済み（1.11.0）** |
| 対象 | FR-18（＋ FR-04, FR-06, FR-07, FR-09, CON-03, CON-08） |
| 仕様 | [SPEC-CS-11 / 16 / 17 / 18](../specs/content-scripts.md) |
| 発端 | 有効サイトが多いと右クリックメニューが 20 行以上伸び、目的のサイトを探せない（FR-18） |
| 前提 | lead が 2026-08-23（ログイン済み / `TSE:7203`）に TradingView のサブメニュー実 DOM を実測した |

---

## 0. 実測で分かっていること（前提の事実）

| 対象 | 実測値 |
| --- | --- |
| 親行 | 通常行 ＋ `span.arrowIcon-WSeXSXQB[data-submenu-arrow]`（矢印 SVG）。**ホバー中もクラスは変わらない** |
| 受け皿行 | 親行の直後の `tr.subMenu-WSeXSXQB > td`。高さ 0 |
| サブメニュー本体 | 受け皿 `<td>` の中に、親と同構造の `div.context-menu` を描画 |
| 位置 | `position: fixed`、`left = 親メニューの右端`、`top = 親行の top`、`z-index: 500` |
| 監視への影響 | `overlap-manager-root` 直下には増えない（`subtree` なしの `childList` 監視に引っかからない） |

**開閉そのものは TradingView 側の JS が持っており、拡張から呼べない**（CON-03）。
模倣できるのは DOM の形だけで、開閉は拡張が自前で実装するしかない。この点は選択肢が無い。

---

## 1. 入れ子をどこに描画するか

**決定: 受け皿行 `tr.{subMenu} > td` の中に描画する。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | 受け皿 `<td>` の中 | TradingView 自身と同じ。**親メニューが閉じれば受け皿ごと消える＝後始末が不要**。`overlap-root` の監視（`subtree: false`）に引っかからず `attachMenu()` が再入しない |
| (b) | `div#overlap-manager-root` の直下 | 却下。自前の `childList` 監視が発火して `attachMenu()` が再入する。`tr[data-kabu-tantan]` のガードで実害は出ないはずだが、**自分が作った DOM で自分の監視を叩く**構造は壊れ方が読めない |
| (c) | `body` 直下（「株Link」ボタンのメニューと同じ） | 却下。親メニューが閉じても入れ子が残る。閉じるための `document` リスナが必須になり、解除漏れの経路が増える（CON-03） |

(a) は `position: fixed` なので、`<td>` の高さ 0 に押し込まれることはない。

---

## 2. 「閉じた」をどう判定するか

**決定: 「親行と入れ子の両方からポインタが外れて 150ms 経過」で閉じる。
Esc・外クリックは TradingView に任せ、拡張はリスナを追加しない。**

### 2-1. マウスが外れたときの判定

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | 親行・入れ子の双方に `mouseenter` / `mouseleave` を張り、`mouseleave` で 150ms のタイマーを予約、`mouseenter` で解除 | 隙間・下端の横切りで閉じない。状態は「開いている参照」と「タイマー」の2つだけ |
| (b) | 親行の `mouseleave` で即座に閉じる | 却下。入れ子は親**メニュー**の右端に出るので、親**行**の右端との間に数 px の隙間が生じうる。そこを通ると閉じる |
| (c) | `document` の `mousemove` で座標判定する | 却下。他社サイト上で毎フレーム走るリスナを増やす（NFR-01）。得られるのは (a) との僅かな挙動差だけ |

150ms は「意図せず閉じない」と「離れたのに残らない」の折衷。**根拠は経験値で、実測値ではない。**
手動確認で長すぎ／短すぎと感じたら調整する。

### 2-2. Esc と外クリック

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | 何もしない。TradingView が親メニューを閉じ、受け皿ごと入れ子が消える | リスナを増やさない。1 の (a) の帰結として自動的に成立する |
| (b) | `document` に `keydown` / `click` を張って自前で閉じる | 却下。TradingView も同じことをしており、二重に閉じるだけ。解除漏れが残ると閉じた後もキー入力を拾い続ける |

**懸念していたリスクは顕在化しなかった（実装後に追記）。** 入れ子は `position: fixed` で
視覚的には親メニューの外に出るため、TradingView の外クリック判定が**座標ベース**だと
項目をクリックした瞬間に親メニューが閉じて遷移できない、という想定をしていた。
**未ログイン環境の実測（1.11.0 / 2026-08-23）で遷移できた**ため、判定は DOM の
包含関係ベースと見てよい（入れ子は親メニューの子孫）。ログイン環境の確認は A-11 待ち。
再発した場合は入れ子の `mousedown` で `stopPropagation()` する対処に切り替える。

## 3. 楽天・内藤の `:info` をいつ問い合わせるか

**決定: 右クリック時（現行どおり）。ホバー時に遅延させない。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | `attachMenu()` の中で問い合わせ、項目を保持する | 入れ子を**同期的に**開ける。0 件判定（4）が右クリック時に確定する。問い合わせは右クリック1回につき1〜2回で上限がある |
| (b) | 入れ子を開くときに問い合わせる | 却下。右クリックは軽くなるが、**開くたび**に問い合わせることになり、開閉を繰り返すと回数が増える。応答待ちのあいだ入れ子が空になり、TradingView 自身のサブメニュー（即座に開く）と体感が揃わない |

`:info` の実体は `chrome.tabs.query` で、右クリック時のコストは元々小さい。
**利用者が待たされる場所はホバー側**なので、そちらを同期にする。

## 4. 画面右端にはみ出す場合

**決定: 左側に反転する。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | 描画後に幅を測り、はみ出すなら `left = 親メニューの left - 幅` にする。負なら `0` にクランプ | はみ出すと**項目が画面外に出て選択できない**＝ FR-18 判定基準5 を満たさなくなる。機能不全を避けるほうを優先する |
| (b) | はみ出しを許容する（TradingView と同じ挙動に賭ける） | 却下。**TradingView 自身の挙動は未確認**であり、「揃える」判断ができない。揃わないことを承知で機能を落とす選択になる |

代償: TradingView が右端で別の挙動（例: 画面内に押し込む）をしていた場合、見た目が揃わない。
見た目の差は A-10 / A-11 で見え、そのとき (b) 相当に寄せ直せる。

縦は**スクロールを許容する**（利用者が決定済み。TradingView 自身も同じ）。
ただし下端がはみ出すと同じく選択できなくなるので、`top` は画面内にクランプする。

## 5. 「株Link」ボタンのメニュー（SPEC-CS-12）とどこまで共通化するか

**決定: 項目リストを決める関数だけ切り出す（`makeLinkItemsAsync` / `makeBrokerItemsAsync`）。
DOM 生成は共通化せず、ボタン側の移行も今回はやらない。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | 項目リスト生成のみ関数化。右クリック側だけが使う | 重複していた「TradingView 除外」「`url3` 絞り込み」「タイトル」「URL 生成」が1箇所になる。ボタン側は後から呼び先を差し替えるだけで移行できる |
| (b) | メニューの器（`menuWrap` / `scrollWrap` / `menuBox` / `table`）まで共通化する | 却下。両者は**遷移方法が違う**（入れ子は `<a href>`、ボタンは `open-url` メッセージ）。背景レイヤー `ktt-tv-menuBack` の有無も違う。共通化すると両方の都合を引数で切り替える関数になり、片方の変更が他方に波及する |
| (c) | ボタン側も今回まとめて入れ子化する | 却下。FR-18 が明示的にスコープ外としている。ボタン側は「消えることがある」（SPEC-CS-12 の既知の制限）が未解決で、そちらの設計と混ざる |

## 6. FR-07 の既知の不整合（ボタンメニューが `url3` で絞らない）を今回直すか

**決定: 直さない。`makeLinkItemsAsync()` を用意するに留め、差し替えは別タスクにする。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | 共通関数だけ用意し、ボタン側は現行のまま | FR-18 の変更だけで手動確認が完結する。A-7b（現状追認の項目）を書き換えずに済む |
| (b) | 同じ変更で直す | 却下。TradingView は**自動テストが無い**（CON-08）。1回の手動確認で2つの要件の結果を見ることになり、A-7b が NG のとき FR-18 の実装が原因か FR-07 の実装が原因かを切り分けられない |

差し替えは1行で済む位置に置くので、次のタスクのコストは小さい。

## 7. 入れ子の項目の文言

**決定: 入れ子の項目は「`〈サイト名〉で開く`」。銘柄コードは親行のラベルにだけ出す。
`<a title>` には銘柄込みの文言を入れる。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | 親行「`7203` を開く」／項目「株探/基本情報で開く」 | 銘柄コードは親行で1回示せば足りる（FR-18 判定基準2 は「その1行に含まれること」を求めている）。「株Link」ボタンのメニュー（SPEC-CS-12）と文言が揃う |
| (b) | 現行どおり項目に「`7203` を株探/基本情報で開く」 | 却下。同じ銘柄コードが全項目に並び、サイト名の読み取りが遅くなる。入れ子は幅も広がる |
| (c) | 項目をサイト名だけ（「株探/基本情報」）にする | 却下。動詞が消えて「選ぶと何が起きるか」が読み取れない。ボタン側の文言とも揃わない |

(a) の代償として、入れ子だけ見ている状態では銘柄が分からない。
`<a title>` に「`7203` を株探/基本情報で開く」を入れてツールチップで補う。

## 8. 見た目が崩れても動くことをどう担保するか

**決定: 位置決めをインラインスタイルで持ち、背景の保険として自前クラス `ktt-tv-subMenu` を併記する。**

FR-18 は「模倣用クラスが崩れても**項目の選択と遷移は動くこと**」を求めている。

| 崩れた場合に失われるもの | 対処 |
| --- | --- |
| 位置（`position` / `left` / `top` / `z-index`） | **インラインスタイルで指定する**ので失われない |
| 背景・影 | `ktt-tv-subMenu`（`src/tradingview-cs.css`）で TradingView の CSS 変数を使って敷き直す |
| 行の高さ・字下げ | 失われる。見た目だけの問題で、クリックはできる |

`ktt-tv-subMenu` の `background` に**色の直値を書かない**。
ダークテーマで変数が死んだときに「白背景＋明色文字」になり、
背景が透明なままより読めなくなるため。変数名ごと変わった場合は `<a>` の文字色
（`--tv-color-popup-element-text`）も同時に死ぬので、A-10 / A-11 で気づく。

### 実装時に改めた点（2026-08-23、実装後に追記）

**当初の決定「変数のフォールバックも書かない」は誤りだった。実装値を正とする。**

| | 当初 | 実装 |
| --- | --- | --- |
| `background` | `var(--tv-color-popup-background)` | `var(--tv-color-popup-background, var(--color-popup-background))` |
| `border-radius` | `4px` | `6px` |

- `--tv-color-popup-background` は**現行の TradingView では未定義**（実測）。
  TradingView 自身も `.menuWrap-… { background-color: var(--tv-color-popup-background, var(--color-popup-background)) }`
  と2段で書き、実際の色はフォールバック側から来ている
- 変数を1つしか書かないと invalid at computed-value time で `transparent` に落ちる。
  さらに `div.ktt-tv-subMenu`（詳細度 0,1,1）が `.menuWrap-…`（0,1,0）に勝つため、
  **TradingView 自身の背景まで打ち消し**、チャートが透けて文字が浮く。
  本節が避けたかった状態を、保険そのものが作り出していた
- 色の直値を書かない方針は変えない。実装は light `rgb(255,255,255)` /
  dark `rgb(31,31,31)` で TradingView 自身と一致する
- `border-radius` も同じ詳細度の理屈で**常に勝つ**ため、TradingView 実測値の `6px` に揃える。
  `4px` のままだと入れ子だけ角丸が浅くなる（FR-18 判定基準10 への軽微なずれ）

**教訓:** 詳細度で勝つ自前クラスを「保険」として重ねる場合、
書いたプロパティは模倣用クラスが**生きている状態でも常に適用される**。
実測値と揃っていない値を足すと、保険ではなく上書きになる。

模倣用クラスを検証対象に格上げしない判断は ADR-0002 の 6 から変えない。
ただし**入れ子の分だけ「崩れたときの見た目の悪化」が大きくなる**ため、
手動確認に A-11 を新設して見る対象を増やす。
