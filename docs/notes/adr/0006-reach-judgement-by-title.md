## 0. なぜ「識別 0 件 = 未到達」が成り立たないのか

ページ識別セレクタは**検出用セレクタの祖先**から起こしている（SPEC-SC-05）。
つまり両者は相関しており、検出用セレクタが根元から壊れると識別セレクタも必ず 0 件になる。

| 対象 | 検出用セレクタ | ページ識別セレクタ |
| --- | --- | --- |
| 国内株式・株価検索 | `div#line1 h1.hdg-l1-01-title span:first` | `div#line1 h1.hdg-l1-01-title` |

`div#line1` が消えれば両方 0 件。**「未到達」と「根元からの破損」が同じ観測になる。**
分けるには、検出用セレクタと相関しない材料が要る。

## 1. 到達の材料に何を使うか

**決定: 到達先の題名（`document.title`）。ただし「正しい題名の許可リスト」ではなく
「未到達の目印の否定リスト」として使う。**

| 案 | 判定 |
| --- | --- |
| (a) 対象ページごとに正しい題名を書き、一致を見る | 却下。20対象ぶんの題名を手で書くことになり二重管理が増える（NFR-13 の趣旨）。さらに**サイトが題名を変えるたびに、壊れていないページが ⚠️ に落ちる**。⚠️ に落ちることは FR-22 が直そうとしている症状そのもので、直しに行った先で同じ症状を作る |
| (b) 対象の `key`（`menuSelectors` の `title`）からページ名を機械導出し、題名に含まれるか見る | 却下。二重管理はゼロで魅力的だが根拠が無い。`保有商品一覧・すべて` の「すべて」のような語が出るうえ、ランキング系9ページの実題名は**一度も観測していない**（✅ の対象は手がかりを採らないため）。外れると (a) と同じく ⚠️ に落ちる |
| (c) 主要コンテナの有無（エラー4ページに `div#mwfooter` があり、株価検索には無い） | 却下。楽天固有の DOM に判定を預けることになり、**検出用セレクタと同じ壊れ方**をする。実データも1回きりの観測で、サイト横断の規則にできない。`div.pcm-content` は両方にあり判別に使えない |
| (d) 遷移後の最終 URL を見る | 却下。URL は結果に記録できない（NFR-12 / SPEC-SC-14）ため、FR-22 判定基準6 の「判断根拠を残す」を満たせない。加えて楽天のエラー画面が同じ URL で返るかは未確認で、**実データで裏を取れていない** |
| **(e) 採用** 未到達の目印（題名の否定リスト）に当たらなければ到達とみなす | 手で持つのは目印の配列1本だけ。対象が増えても増えない。2026-08-23 の実データを判定基準4 どおりに分けられる |

## 2. 判断できないときにどちらへ倒すか

**決定: 反証（未到達の目印）が無ければ ❌ に倒す。**

(a)(b)(c) はいずれも「証拠が無ければ ⚠️」＝**分からないときは黙る**設計。(e) は逆に
「反証が無ければ ❌」＝**分からないときは騒ぐ**設計。決め手は誤りの見えやすさの非対称性。

| 誤り | 見え方 | コスト |
| --- | --- | --- |
| 誤 ❌（壊れていないのに破損と呼ぶ） | 終了コード 1 で目立つ。手がかりの題名を読めばすぐ分かる | 調査が1回無駄になる |
| 誤 ⚠️（壊れているのに未到達と呼ぶ） | 終了コード 2 に埋もれる。**誰も気づかない** | 利用者の報告を待つことになる = FR-12 の目的が消える |

FR-12 の目的は「利用者の報告を待たずに破損を知る」こと。黙る側の誤りはその目的を直接壊す。

ただし**題名が空・不記録のときは ⚠️ のまま**とする。これは「反証が無い」のではなく
「判断材料が無い」場合で、❌ にすると FR-22 判定基準6（判断根拠を残す）を満たせない。

**決定: `diagnostics.mjs` に `UNREACHED_TITLE_PATTERNS` として1本置く。
SPEC-SC-22 の `SUSPICIOUS_PATTERNS` とは分ける。**

| 案 | 判定 |
| --- | --- |
| (a) `SUSPICIOUS_PATTERNS` に相乗りする | 却下。狙いが違う（あちらは**記録してよいか**、こちらは**到達したか**）。片方の都合で緩めた瞬間、もう片方が壊れる |
| (b) サイトごとに `targets.mjs` へ持たせる | 却下。今それを必要とするサイトが無い。必要になってから足す（CON-09） |

未観測のものを入れても、対象20ページの正しい題名と衝突しないため実害が無い。

## 4. 判定と手がかり採取の順序

**決定: 採取 → 到達判定 → 再分類 → プレフィックス追跡。**

プレフィックス追跡は判定によって追う対象が変わる（❌ なら検出用セレクタ、⚠️ ならページ識別セレクタ。
SPEC-SC-21）。再分類を追跡の後に置くと、**再分類された ❌ でページ識別セレクタを追ってしまい、
いちばん知りたい「検出用セレクタのどこで切れたか」が出ない。**

そのため既存の `attachDiagnosticsAsync()` を「facts の採取」と「追跡」に割る。
副作用として `judgeReach()` が純関数として切り出され、実データでの検算を自動テストにできる。

## 5. FR-20（株価検索）との関係

この変更で株価検索は ❌ になるが、**❌ になったこと自体は原因の裏づけにならない。**
到達判定は「エラー画面ではない」ことしか言っておらず、
「ツールが結果画面ではなく検索フォーム／国内株式トップに着いている」可能性（FR-20 の読み方 (b)）を
排除できない。この限界は SPEC-SC-18 に限界として、SPEC-CS-20 に仮説 3b として書く。

**先回りして「株価検索は破損と確定した」とは書かない。**

## 6. 追補（1.12.2 の実装・レビューで判明した4点）

実装した4値では**言い当てられない状態**があると developer から報告があり、追加で2つ決めた（6-1・6-2）。
さらにレビュー指摘 S-2 で、再分類の適用条件をどこに置くかを決めた（6-3）。
レビュー指摘 S-3 で、6-3 の緩和策が挙げた「結果表の理由列」が実在しないと分かり、
読み分けの記述を実態に合わせた（6-4）。

### 6-1. 「評価できなかった」を5値目として足す

**決定: 足す。** 文言は `セレクタを評価できなかったため題名を見ていない`（`REACH_NOT_EVALUATED`）。
あわせて既存の `REACH_NOT_CONSULTED` の文言も
`ページ識別セレクタ・検出用セレクタのいずれかがヒットしたため題名を見ていない` に直す。

適用条件1（識別・検出の両方を評価できた）を満たさない経路が2つ残っており、
そこで `ページ識別セレクタがヒットしたため題名を見ていない` と出ていた。
**どちらの経路も件数を数え切れていない**（少なくとも一方が `null`）。
数え切れていない以上「いずれかがヒットしたから題名を見なかった」とは言えず、事実に反する。
識別セレクタが 1 件ヒットしていることもある（検出用セレクタの評価だけが例外になる経路。
SPEC-SC-24 のスタブ検証ケース5）ため、**条件は「どちらかが数値でない」であって
「識別が `null`」ではない**。

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 5値目を足す | 「記号や記録が実態とズレて切り分けを誤らせる」は FR-22 が直そうとした問題そのもの。同じ性質の誤りを、その修正のなかに残さない |
| (b) 4値のままにする（実害が出るまで放置） | 却下。2026-08-23 の実データに該当が無いのは**たまたま**で、jQuery 未注入・評価例外はどちらも「サイト側が変わったとき」に出る。いちばん読む必要がある場面で嘘が出る |
| (c) 該当経路では `到達判定` の行を出さない | 却下。FR-22 判定基準6 が「判断根拠を必ず残す」。行が消えると、消えた理由を読み手が推測することになる |
| (d) 該当経路にも `judgeReach()` を適用する（4値のまま） | 却下。検出用セレクタの件数が不明なままでは、到達していても「壊れている」と言えない。⚠️ を ❌ に変える根拠が無い |

**判定記号は増やさない**（FR-22 のやらないこと）。増えるのは手がかり節の文言だけで、
新しい種類の情報も記録しない（件数と固定文言だけ）。

### 6-2. 再分類で ❌ になった対象にも利用者データの注意書きを付ける

**決定: 付ける。** `judge()` の中で付けるのをやめ、**❌ が確定した後の1箇所**で付ける
（経路は `judge()` / 再分類 / 例外の3つ）。

理由は、**再分類の経路こそが「データが 0 件」の典型**だから。
`requiresUserData: true` の4対象はページ識別セレクタ自体がデータ表
（`form#form table.tbl-data-01` / `div#table_possess_data` / `table#poss-tbl-sp`）で、
登録が 0 件だと識別・検出がともに 0 件になり、題名は正常なページのものになる。
これは ⚠️ → ❌ の再分類にそのまま当たる。

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 経路を問わず1回付ける | 最も紛らわしい ❌ にこそ注意書きが要る。規則が「❌ かつ `requiresUserData` なら付ける」の1文で言い切れる |
| (b) 付けない（`judge()` の中に置いたまま） | 却下。`judge()` の中に付記があるという**実装の都合**が理由で、設計上の理由が無い。再分類の ❌ だけ注意書きが落ちるのは逆向き |
| (c) 再分類のときだけ別の文言にする | 却下。読み手がすべきこと（登録状況を確認する）は同じ。文言を分ける利得が無い |

この (a) が意図どおりに効くこと（再分類経路 × `requiresUserData: true` で注意書きが 1 回だけ付くこと）は、
スタブのフレームに `checkTargetAsync()` を配線ごと通して確認した。記録は
SPEC-SC-24「1.12.2 実装時のスタブ検証」の表（7ケース）。

### 6-3. 再分類の適用条件は `check.mjs` 側に置き、到達判定の行は上書きしない

**決定: `reclassifyByReach()` に「呼ばれた時点で ⚠️」のガードを足す。`decideReach()` は変えない。**

`decideReach()` の条件3（識別・検出がともに 0 件で題名が目印に当たらない）は、
**例外で既に ❌ になっている対象にも当たる**（注入セレクタの評価で例外・TradingView の接頭辞検査で例外。
どちらも件数を 0 まで数えた後に失敗するため `pageHits` / `hits` が 0 のまま残る）。
ガードが無いと、何も再分類していない対象の備考に
`ページ識別セレクタは 0 件だが、題名から到達と判断した` が付く。

| 案 | 判定 |
| --- | --- |
| **(a) 採用** `reclassifyByReach()` 側でガードする | 再分類は「⚠️ を ❌ に変える」操作なので、**変える対象があるか**は呼び出し側の状態。`decideReach()` は題名から何が言えるかだけを見る純関数のままでよい |
| (b) `decideReach()` に現在の判定を渡し、6値目を足す | 却下。5値は「題名について何を判断したか」で一貫している。「適用しなかった」は別軸の情報で、同じ列に混ぜると読み手が判断根拠を追えなくなる。純関数の入力に記号が増える割に、読み手の得が無い |
| (c) 例外経路では `到達判定` の行を出さない | 却下。6-1 の (c) と同じ理由（FR-22 判定基準6 が「判断根拠を必ず残す」） |

**あわせて、例外由来の ❌ に `到達したとみなす` が並ぶことは許容する。**
6-1 で 5 値目を足したのは、`REACH_NOT_CONSULTED` が
「識別セレクタがヒットした」という**観測を偽って**述べていたため。
今回残るのは「題名が未到達の目印に当たらない」という観測と、それに基づく判断で、**どちらも真**。
再分類が起きたかは備考の根拠1行の有無で、❌ の経路は**備考に載る消毒済み例外メッセージ**の
有無で読める（結果表に「理由」列は無い。6-4）。
記号と行が食い違って見えることは SPEC-SC-24 に読み分け表として明記した。

配線の確認は回帰テストに移した（`tests/selector-defs.spec.mjs` の `手がかり`。SPEC-SC-16 の `手がかり` 25・26）。
`識別・検出がともに 0 件の ⚠️ は題名から ❌ に再分類され、根拠が1行付く`（25）が
「ガードを通り抜けて再分類する」、`セレクタ評価の例外で ❌ になった対象には再分類の根拠を付けない`（26）が
「ガードで止まり根拠を付けない」を固定する。

> 番号は SPEC-SC-16 の固定番号で、`docs/TEST-CATALOG.md`（記述順）とは一致しない。
> **参照はテスト名で突き合わせる。**

### 6-4. ❌ の経路は備考の例外メッセージで読み分ける（結果表に「理由」列を足さない）

**決定: 文書を実装の実態に合わせる。`report.mjs` の出力書式は変えない。**

6-3 の「例外由来の ❌ に `到達したとみなす` が並ぶのを許容する」は、
読み手が経路を切り分けられることが前提。その切り分け先を
1.12.2 のレビューまで「結果表の理由列」と書いていたが、**そんな列は無い**。
`report.mjs` のサイト別結果表は `ページ / 判定 / 識別 / ヒット / 注入 / 備考` の6列で、
`result.reason` を印字するのは「未実施の対象」表だけ（`status === SKIPPED` の分岐）。

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 文書を実態に合わせ、切り分け先を「備考の**接頭辞の無い**消毒済み例外メッセージ」とする | 例外由来の ❌ では `check.mjs` が例外メッセージを**接頭辞なしで** `notes` に積む。❌ の他の2経路（`judge()` / 再分類）は積まず、他所で積む例外メッセージには接頭辞が付く（`手がかりを採れなかった:` など）。**有無**で切り分けられる（接頭辞なしのもう1つ `検証用 jQuery が注入されていない` は ❌ の行に出ない。下記） |
| (b) `reason` を ❌ の備考にも印字する | 却下。得られるのは固定文言 `セレクタの評価に失敗した` 1行だが、同じ事象の例外メッセージが既に隣に並ぶ。**生成物の書式変更**は `結果ファイルの書式` テストの追随と `docs/SELECTOR-CHECK.md` の再生成（実サイトへのログインを伴う手動実行）を要求する。費用が読み手の得に見合わない |
| (c) 読み分け表から「❌ になった経路」の行を消す | 却下。6-3 の判断がその読み分けに依っている。依存を消さずに記述だけ消すと、判断の根拠が読めなくなる |

**接頭辞なしで積まれるもう1つのメッセージ。** `check.mjs` の同じ `catch` は
`JQueryMissingError`（`検証用 jQuery が注入されていない`）も接頭辞なしで `notes` に積む。
ただしこの経路では `pageHits` / `hits` が `null` のままで、`decideReach()` の条件1（6-1 の
`REACH_NOT_EVALUATED`）に落ちて再分類されないため、**判定は必ず ⚠️ になり ❌ の行には現れない**。
(a) の切り分けはこの性質に依存する。`JQueryMissingError` の分類を ❌ 側へ変える、または
未注入でも件数を数える実装にする場合は、(a) が破れるため (b) を採り直す。

この依存も回帰テストで固定した（6-3 と同じ形）。`tests/selector-defs.spec.mjs` の `手がかり` の
`検証用 jQuery が未注入の対象は ⚠️ のままで、❌ の読み分けを壊さない`（SPEC-SC-16 の `手がかり` 27）が
`status === UNREACHED`・`pageHits` / `hits` / `injectedHits` が `null`・
`diagnostics.reach === REACH_NOT_EVALUATED`・備考に接頭辞なしの `検証用 jQuery が注入されていない` が
載ること・再分類の根拠が付かないことを検査する。**落ちるのは Node 側の分類を変える破り方に限る。**

| 破り方 | 27 が落ちるか |
| --- | --- |
| `check.mjs` の `catch` で `JQueryMissingError` を ❌ 側に分類する | 落ちる（実証: `BROKEN` に変えると `Expected: "unreached" Received: "broken"`） |
| Node 側で `{ missing: true }` を件数 0 と読み替える | 落ちる（`toBeNull()` と `diagnostics.reach`） |
| ページ側の関数内で jQuery を遅延ロードする | **落ちない。** スタブは常に `{ missing: true }` を返すためテストは緑のまま。実サイトでの手動実行でしか気づけない |

接頭辞が付かないというもう片側は 26 が固定している。

> **文言は前方一致になっている。** プレフィックス追跡が行えないときの1行要約
> `検証用 jQuery が注入されていないためプレフィックス追跡を行えない`
> （`diagnostics.mjs` の `TRACKING_UNAVAILABLE`）も接頭辞なしで `notes` に積まれ、
> 読み分けの目印 `検証用 jQuery が注入されていない`（`check.mjs`）を**先頭に含む**。
> 27 と 26 は `toContain`（配列の要素完全一致）で見ているので現状は取り違えない。
> **備考を部分一致（`includes` / 正規表現）で判定する実装・テストは書かないこと。**
> 部分一致にすると、追跡できなかっただけの対象を「未注入で ⚠️ に落ちた対象」と誤読する。

**限界。** 例外メッセージは jQuery / Playwright 由来の可変文言で、固定文言のような
