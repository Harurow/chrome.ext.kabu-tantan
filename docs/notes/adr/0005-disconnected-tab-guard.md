# ADR-0005 切断状態のタブでサイトを乱さないための守り方

| | |
| --- | --- |
| 状態 | 採択（2026-08-23）。**1.12.0 で実装** |
| 対象 | NFR-14（＋ NFR-01, NFR-05, CON-01, CON-03） |
| 仕様 | [SPEC-CS-19](../specs/content-scripts.md)（＋ SPEC-CS-01 起動時の門 / SPEC-CS-11 条件1 / SPEC-CS-12 手順2） |
| 発端 | 拡張機能を再読み込みした後の TradingView の古いタブで、右クリックのたびに「3行追加 → `chrome.runtime.sendMessage` で `TypeError` → 3行除去」が繰り返される（2026-08-23 実機） |

---

## 0. 何が起きているか（実装を読んだ結果）

| 経路 | 現状 | 症状 |
| --- | --- | --- |
| 右クリック（`addTickerMenuAsync`） | 3行を**同期的に**追加してから `await`。例外は `try` / `catch` で拾い3行を除去する（1.11.0 で入れた） | 追加と除去の往復が見える。**例外自体は捕捉済み** |
| 「株Link」ボタン（`createKabuLinkMenu` のクリックハンドラ） | 背景レイヤーを敷いてから `await chrome.runtime.sendMessage(…)`。`try` / `catch` **無し**。jQuery の `click` は返り値の Promise を見ない | **未処理の拒否**としてコンソールに `TypeError: Cannot read properties of undefined (reading 'sendMessage')` が出る。透明な全画面レイヤー `ktt-tv-menuBack` が残り、次のクリックが吸われる |

観測されたコンソールの例外は**ボタン側**、行の追加・除去は**右クリック側**。別々の経路が同時に見えている。

---

## 1. 切断をどう判定するか

**決定: `chrome.runtime.id` の存在確認。**

| 案 | 判定 |
| --- | --- |
| **(a) 採用** `typeof chrome !== 'undefined' && chrome.runtime != null && chrome.runtime.id != null` | 判定自体が例外にならない。同期で答えが出るので **DOM を触る前**に置ける |
| (b) `chrome.runtime.sendMessage` を投げてみて例外を見る | 却下。判定のために通信が発生し、Service Worker を起こす。非同期なので「DOM を触る前」に置けない |
| (c) `chrome.runtime.getURL('')` を `try` で囲む | 却下。(a) と情報量が同じで、`try` / `catch` の分だけ読みにくい |

`chrome.runtime.id` は **Service Worker が休止していても残る**（CON-01）。
休止と切断を取り違えない点が (a) を選ぶ決め手。

置き場所は `src/urls.js`。5本の Content Script すべてが読む唯一の共有ファイルで、
`linkMenu.js` は TradingView に読み込まれないため使えない（ビルドが無く `import` できない。CON-02）。

---

## 2. 門だけにするか、網も残すか

**決定: 両方。門（事前判定）＋網（`try` / `catch`）。**

| 案 | 判定 |
| --- | --- |
| (a) 門だけ | 却下。判定から `await` の完了までのあいだに拡張機能が更新されうる。開発中は現実に起きる |
| (b) 網だけ | 却下。**要素を追加してから消すことになり NFR-14 判定基準2 を満たさない**。今の 1.11.0 がこの状態 |
| **(c) 採用** 門＋網 | 門が判定基準2（追加しない）を、網が判定基準1（例外を出さない）を担う。既存の `try` / `catch` を消さずに済む |

---

## 3. 適用範囲（NFR-14 判定基準4「問い合わせを行うすべての注入先」）

**決定: 5本の Content Script すべて。**

判定基準4 の「問い合わせ」を `chrome.runtime.sendMessage` に限らず、
**`chrome.storage.sync.get`（`getEnableLinkKeysAsync()`）を含む**と解釈した。
どちらも切断状態で `undefined` になり同じ `TypeError` になるため、区別する理由が無い。

| 対象 | `sendMessage` | `storage` | 対応 |
| --- | --- | --- | --- |
| `tradingview-cs.js` | あり | あり | 門3箇所（起動・右クリック・ボタン。起動時の門は下記 6 で追加） |
| `rakuten-scr-cs.js` / `sbi-scr-cs.js` | なし | 起動時1回 | 門2箇所（起動・監視コールバック） |
| `rakuten-cs.js` / `sbi-cs.js` | なし | 起動時1回 | 門1箇所（起動） |

`rakuten-cs.js` / `sbi-cs.js` は「タブが切断状態になる頃には既に実行を終えている」ため
実害がほぼ無いが、**ページ読み込みから 500ms 以内に拡張機能を再読み込みすると踏む**（開発中に起きる）。
門は 1 行なので、対象から外して例外規定を作るより入れるほうが安い。

---

## 4. 切断状態のスクリーナーで注入を止めるか

**決定: 止める。**

スクリーナー2種は `MutationObserver` のコールバックが**キャッシュ済みの `keys`** を使うため、
切断状態でも例外を出さずにメニューを注入し続ける。しかも注入されたメニューは
`<a href>` だけなので**クリックすれば正しく開く**。つまり現状で実害が無い。

| 案 | 判定 |
| --- | --- |
| (a) 現状維持（切断状態でも注入し続ける） | 却下。NFR-14 判定基準2「切断状態のタブで、拡張機能が要素を一切追加しない」に正面から反する |
| **(b) 採用** 門を置いて注入を止め、監視も `disconnect()` する | 判定基準2 を満たす。復帰手段が無い以上（NFR-14「やらないこと」）、監視を続けても他社サイト上で無駄な処理が走るだけ（NFR-01） |

**副作用（劣化）を認識した上で採る。** 切断状態のスクリーナーでページ送りすると
新しい行にメニューが付かなくなる。既に注入済みのメニューは残す（取り除きはしない）。
利用者はタブを再読み込みすれば元に戻る。
判定基準2 は analyst と利用者が合意した要件であり、architect の側で緩めない。

---

## 5. 利用者への通知・自動復帰

NFR-14 の「やらないこと」で禁じられている。設計の選択肢は無い。**何もしないことが正しい振る舞い。**

---

## 6. 起動時の「株Link」ボタン注入を切断状態でも行うか

**決定: 行わない。`attach()` の先頭に門を置く。**

1.12.0 のレビューで、TradingView だけ**起動時**の門が無いことが分かった。
`attach()` は無条件に `createKabuLinkMenu()` を呼び、`buttonsWrapper` と
`div.ktt-tv-kabuLinkMenu` を DOM に追加する。chrome API を触らないので例外は出ないが、
**切断状態のタブに「押しても何も起きないボタン」が恒久的に残る**
（`openKabuLinkMenuAsync` の門が効くため無反応）。

| 案 | 判定 |
| --- | --- |
| **(a) 採用** `attach()` の先頭に `if (!isExtensionAlive()) return` を置く | 他4本と同じ形になり、5本すべてが「エントリポイントの先頭に門」で揃う。観測用の `MutationObserver` 2つと `contextmenu` リスナーも張らずに済む（NFR-01）。コストは1行 |
| (b) 既知の劣化として SPEC-CS-19 に明記する | 却下。下記 |

**(b) を却下した理由:**

| 理由 | 内容 |
| --- | --- |
| 判定基準2 の文言に正面から反する | NFR-14 判定基準2 は「切断状態のタブで、拡張機能が**要素を一切追加しない**」。ボタンは要素である |
| 4 の判断と矛盾する | スクリーナー（上記 4）では「**実害が無くても**判定基準2 を優先して止める」と決め、機能の劣化を受け入れた。同じ基準で、TradingView のボタンだけ「実害が小さいから残す」とは言えない |
| 劣化の質は 4 より悪い | 4 は「新しい行にメニューが**付かない**」（引き算）。こちらは「無反応なボタンが**残る**」（足し算）。他社サイトのツールバーに死んだ UI を置き続けることになる |
| コストが 1 行 | 例外規定を仕様に書くほうが、記述と維持のコストで上回る |

**正常時の退行は無い。** `isExtensionAlive()` が偽になるのは切断状態だけで、
通常のページ読み込み（500ms 後）では真になる。タブを再読み込みすればボタンは通常どおり出る。

**起動時の門は他の門の代わりにならない。** 踏むのは「ページ読み込みから 500ms 以内に
拡張機能を再読み込みする」窓だけで、実際に多いのは「正常に注入した後に更新される」経路。
既存の門（SPEC-CS-11 条件1 / SPEC-CS-12 手順2 / 監視コールバック）は**そのまま残す**。

確認は自動テスト `tests/disconnected.spec.mjs` の「切断状態: TradingView」（2026-10-12〜。Content Script の注入を CDP で捕まえ、直後に拡張機能を再読み込みして窓を踏む。SPEC-CS-19「検証との対応」）。
