## 0. 何を守るのが最優先か

FR-19 判定基準 2 を満たさない実装は **FR-04 違反**として扱う、と要件が明記している。
つまり本件の失敗には非対称性がある。

| 失敗の形 | 深刻さ |
| --- | --- |
| **右クリックした行と違う銘柄のリンクが出る**（チャートの銘柄が漏れる） | 重い。利用者が誤った銘柄のページを開く。FR-04 違反 |
| 何も出ない（項目が追加されない） | 軽い。従来どおりチャートを切り替えれば済む。FR-19 判定基準 3・7 では**これが正しい挙動** |

以下の判断はすべて「迷ったら何も出さない側に倒す」で揃えてある。

> **この方針は「起点をどう選ぶか」の判断にしか効いていない**（1・2・5・6）。
> **銘柄の解釈そのものは別で、実装当初（1.15.0 の開発中）に誤読の経路が実在した**
> （`NYSE:BRK.B` → `BRK`。下記 3 の追補1）。
> 起点の設計が正しくても、解釈側が誤った値を返せば重い失敗はそのまま起きる。

## 1. 起点をどう表現するか（チャート／行の取り違えを防ぐ）

**決定: 記録を1件に保ち、`contextmenu` の時点で「どちらの起点か」と「行なら銘柄」まで確定させる。
行の判定をチャートの判定より先に行う（行が優先）。**

現行は `chartContextMenuAt`（時刻のみ）で、チャート外なら `0` を入れて捨てている（SPEC-CS-11）。

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | 記録を `{ kind, at, code, type }` の1件にし、`contextmenu` で「行 → チャート → 捨てる」の順に解決する | 起点が同時に2つ存在しえないので取り違えが構造的に起きない。**行を先に見る**ので、TradingView がウォッチリストをチャートの内側に置く配置に変えても、行の銘柄が出る（判定基準 2 を守る） |
| (b) | チャート用と行用に記録を2つ持ち、`attachMenu()` 側で新しい方を採る | 却下。「どちらが新しいか」の比較を毎回正しく書く必要があり、片方を捨て忘れると**チャートの銘柄が漏れる**。0 の非対称性からいちばん避けたい壊れ方 |
| (c) | チャートを先に判定し、チャート外のときだけ行を見る | 却下。現在の配置では (a) と同じ結果になるが、ウォッチリストがチャートの内側に入った瞬間に**チャートの銘柄を出す**方向へ壊れる。壊れる向きが悪い |
| (d) | `attachMenu()` の時点で行の DOM をたどり直して銘柄を読む | 却下。仮想スクロールで行が差し替わりうる（FR-19 判定基準 8）。右クリックからメニュー生成までの間に別銘柄になる余地を残す |

(a) の代償: チャートの内側に候補属性を持つ要素があると、チャートの右クリックが「行」と判定され、
**チャート起点の項目が出なくなる**（FR-04 の退行）。ただし出るのは「何も出ない」であって誤銘柄ではない。

> **この代償は 2 の追補1・2（再レビュー M-5 / M-5b）で大きく縮めた**（完全には消えない。追補2）。
> 「行」の判定を**値の形**で行うようにし、チャート内の `main` / `8253` / `main:1` のような値は行と見なさない。
> 起点の優先順位（行 → チャート）自体は変えていない。非退行の目視は **A-17** に残す。

実装（1.15.0）は `resolveContextMenuOrigin()` がこの順序をそのまま持ち、
`findRowTickerCode()` の戻り値（`null` ＝行ではない／`{ code: null }` ＝行だが解釈不能）で
「捨てる」と「チャートへ進む」を分けている。

### 猶予時間

**決定: 1500ms のまま、チャート・行で共通の1つの定数を使う。**
別々に持つ理由が無く、2つあると「行だけ効かない」種類のバグを作れる。
記録が1件しか無いので、猶予の判定も1箇所（`Date.now() - origin.at > grace`）のまま変わらない。

## 2. 行から銘柄をどう取るか（属性名が推測であることへの備え）

**決定: 候補属性名の配列を1つ持ち、近い祖先から順に、解釈できた最初の値を採る。
取れなければ何もしない。**

要件は「各行は `EXCHANGE:CODE` 形式（例 `TSE:8253`）とコード単独（例 `8253`）の両方を属性として持つ」
としか書いていない。**属性名は記録が残っていない。**
TradingView のウォッチリストは一般に `data-symbol-full`（`TSE:8253`）と `data-symbol-short`（`8253`）を
行要素に持つことが知られており、要件の記述と一致するが、**これは推測であって本リポジトリの実測ではない。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | 候補属性名を定数配列に置き、値を既存の解釈器に通して、最初に成功したものを採る（**行と見なす条件は下記の追補で「値が `EXCHANGE:CODE` の形」に狭めた**） | 属性名を1つ外しても他の候補で拾える。名前が全部変わっても「何も出ない」に落ちるだけ（判定基準 3）。属性名の変更が**1箇所の編集**で済む |
| (b) | 実測が取れるまで実装を止める | 却下。要件は着手可能と判定済みで、優先度は希望。(a) なら推測が外れても害が「何も出ない」に収まる |
| (c) | 行のクラス名（ハッシュ付き）や行の親のウィジェット容器で行を特定する | 却下。CON-08 のとおりハッシュは変わる。要件の調査でも「属性側が耐性が高い」と結論が出ている |
| (d) | 行のテキスト（表示されている銘柄名）を読む | 却下。文言依存は ADR-0002 の 1 で一度捨てた経路。国内株の表示が銘柄名だけの場合に取れない |

初期値と、それぞれを載せる理由:

| 順 | 候補属性 | 根拠 | 期待する値 |
| --- | --- | --- | --- |
| 1 | `data-symbol-full` | 推測（TradingView のウォッチリストで一般に知られる名前） | `TSE:8253` |
| 2 | `data-symbol-short` | 同上。要件の「コード単独」に対応 | `8253`（**解釈に失敗する** → 次へ） |
| ~~3~~ | ~~`data-symbol`~~ | ~~保険。1 が別名になっていた場合の受け皿~~ **候補から外した**（下記の追補。汎用的すぎてチャート内に当たる危険が高い） | — |

- **市場種別（`jp` / `us`）は `EXCHANGE:` からしか決めない。** コード単独（`8253`）は
  取引所が分からないため解釈に失敗させ、次の候補へ送る。
  「4桁なら国内株」と当てにいくと米国株の行で誤ったリンクを出す（0 の重い失敗）
- 行かどうかの判定にも同じ配列を使う（`[data-symbol-full],[data-symbol-short]`）。
  **行と判定した要素で銘柄を解釈できなかった場合は、チャートへ落とさずに捨てる**
  （落とすとチャートの銘柄が出る＝ FR-04 違反）
- `data-symbol` はチャート側の要素に付いている可能性が他の2つより高い。
  **観測を待たず、再レビュー M-5 の時点で外した**（下記の追補）

### 追補1（2026-08-29 / 再レビュー M-5）: 「行」を属性の有無ではなく値の形で決める

**採用時の (a) には、指摘されるまで気づいていなかった穴があった。**
候補属性を1つでも持つ祖先があれば「行」と見なしていたため、
**チャート領域内の要素がその属性を持ち、値が `EXCHANGE:CODE` でなければ、
1 の「行は捨てる（チャートへ落とさない）」規則が働いてチャートの右クリック拡張が全面停止する。**

危険の重さが釣り合っていない。**FR-04 は必須で 1.13.0 から動いており、FR-19 は優先度「希望」。**
未確認の推測（属性名）で必須要件を止める形になっていた。

**決定: 「行」の定義を「候補属性を持つ」から「候補属性が `EXCHANGE:CODE` の形の値を持つ」に狭める。
あわせて候補から `'data-symbol'`（最も汎用的な名前）を外す。**

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 行の定義を値の形で決める（＋ `'data-symbol'` を外す） | チャート内の `main` / `8253` のような値は行と見なされず、**チャート起点が生きる**。本物の行は `EXCHANGE:CODE` を持つと要件が確定させているので**代償が無い**。実サイト情報を要さない |
| (b) `resolveContextMenuOrigin()` の先頭でチャートを判定し、内側なら即 `kind: 'chart'` を返す（reviewer の提案） | 却下。**危険の向きが提案時の見立てと違う。** 先頭で返すと行の判定に到達しないため、ウォッチリストが `div.chart-gui-wrapper` の内側にあった場合に**全行でチャートの銘柄が出る**。これは 0 の表で最も重いと定めた失敗（＝ FR-04 違反）で、**「新機能が動かない」ではない** |
| (c) `'data-symbol'` を外すだけ | 不足。`data-symbol-short`（値はコード単独）がチャート内にあれば同じ事故が起きる。**(a) の一部として採る** |
| — | **(a) だけでも塞ぎ切れなかった。** 形の字種が解釈側より広く、差分が「捨てる」に落ちていた（追補2） |
| (d) 何もせず実サイト確認を待つ | 却下。**必須要件が止まる危険を、希望要件の確認待ちにぶら下げることになる。** reviewer の「新機能が動かない側に倒す」という基準は正しい |

**reviewer の判断基準（新機能が動かない側に倒す）は受け入れ、手段だけを変えた。**
(a) はその基準を満たしたうえで、**重い失敗の経路を新設しない**点で (b) より強い。

**残す穴:** ウォッチリストが `div.chart-gui-wrapper` の内側にあり、かつ行が
`EXCHANGE:CODE` の形の値をどこにも持たない場合は、行がチャート起点になり誤った銘柄が出る。
ただし**その世界では FR-19 がそもそも動かない**（形の値が無ければ銘柄を取れない）ので、
A-13 が NG の時点で属性名の実測に進む。検出は A-13 と A-15。

**実装（1.15.0）:** 形の判定は純粋関数 `isSymbolShaped(text)` に切り出し（字種は**追補2 で `[A-Z]` に狭めた**）、
`findRowTickerCode()` が `shaped` フラグで戻り値を3値に作り分ける。起点の優先順位は変えていない。

**ただし、この判断を支える分岐そのものには自動テストが無い。**
固定されたのは `isSymbolShaped()` の真偽だけで、`$().closest()` を使う走査と
「`null` を返すか `{ code: null }` を返すか」の配線は**実 DOM でしか確かめられない**（CON-08）。
**「(a) なら代償が無い」という上の判定は、配線が意図どおりであることを前提にしている。**
確認は手動 A-13 / A-15 / A-17 で、SPEC-CS-23「実サイトで確認すべき事項」の **7** に残した。

### 追補2（2026-08-29 / 最終レビュー M-5b）: 形の字種を解釈側と揃える

**追補1 の手当てには、範囲を狭めただけで塞ぎ切れていない部分があった。**

形の判定 `/^[A-Za-z][A-Za-z0-9_]*:/` が、解釈側の取引所トークン `/^([A-Z]+)(_DLY)?:/` より**広い**。
その差分（`main:1` / `chart:2` / `pane:0` / `Widget:1` / `nyse:aapl`）は
**「形は満たすが解釈は絶対に成功しない」**ため、行と見なされたうえで捨てられる。
チャート内の要素がこの形の値を持てば、**追補1 で塞いだはずのチャート起点の停止がそのまま起きる。**

**決定: 形の字種を解釈側と揃える（`[A-Za-z]` → `[A-Z]`）。**

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 字種を `[A-Z]` に狭める | 巻き添えの集合が「**大文字＋コロン**」まで縮む。**本物の行は大文字**（`TSE:8253`）で、`nyse:aapl` は SPEC-TC-09 が既に不成立と定めた形。小文字の内部識別子（`main:1`）は TradingView の DOM にありうるが、**大文字の内部識別子はより考えにくい** |
| (b) 据え置き、差分を仕様とテストに明記するだけ | 却下。**危険の向きが FR-04（必須）を止める側**で、明記しても危険は減らない。ただし (b) が要求していた「差分をテストで固定する」は**採用案でも必要**（下記）ので、そこだけ取り込む |
| (c) 形の判定で `exchanges` を引き、差分を完全に消す | 却下。`SP:SPX` が「行ではない」になり、**指数の行にチャートの銘柄が出る**（判定基準 7 違反）。0 の非対称性に反する |

**差分は原理的に消えない。** 判定基準 7 が「`SP:SPX` を行として認識したうえで捨てる」ことを
要求している以上、**`exchanges` に無い大文字トークンはすべて差分に残る**。
(a) は消す手当てではなく**縮める**手当てで、**(c) がその下限を作っている**。

**上限と下限の両方をテストで固定する**（(b) から取り込んだ点）。

| 固定するもの | 内容 |
| --- | --- |
| 上限（広げすぎの防止） | `isSymbolShaped('main:1') === false` ほか。**次に触る人が「小文字も通そう」と戻すのを事故で起こさせない** |
| 差分が残ることの明示 | `isSymbolShaped('MAIN:1') === true`。**消えたと誤解させない** |
| 下限（狭めすぎの防止） | **`parseExchangeSymbol()` が `code` を返す値は必ず `isSymbolShaped()` が真**。狭めすぎると本物の行が行でなくなり、FR-19 が動かなくなる |

**実装（1.15.0）:** `isSymbolShaped()` の正規表現を `/^[A-Z][A-Z0-9_]*:/` に狭め、
上限（`MAIN:1` は真 / `main:1` ほかは偽）と下限（包含関係）をテストで固定した。
下限のテストは**同じループで `parseExchangeSymbol()` の `code` が非 null であることも断言**し、
サンプルが解釈できない値に置き換わって**テストが空振りする**事故を防いでいる。

> **総当たりでの裏づけ（開発時の確認。テストには入っていない）:**
> `exchanges` の全7キー × `_DLY` の有無 × 妥当なコード × 後続文字列の有無＝**108値**で
> 包含関係の違反 0 件。**「差分は原理的に消えない」という本追補の見立ても実測で裏づけられた**
> （`SP:SPX` / `MAIN:1` / `CME:ES1!` / `XETR:BMW` は形は真・解釈は `null`）。

**残す穴に一行加わる:** ウォッチリストが `div.chart-gui-wrapper` の内側にあり、
**行の値が小文字始まりのコロン値しか無い**場合、行はチャート起点になり誤った銘柄が出る。
**期待どおりの配置（ウォッチリストが外側）なら、(a) の前後で結果は変わらない**
（どちらも何も出ない）。差が出るのは入れ子配置のときだけで、そこは元々この穴の範囲。

## 3. `EXCHANGE:CODE` の解釈を再実装しない

**決定: 現行 `getTickerCode()` が持つ解釈手順（SPEC-TC-07 の 1〜3）を引数付きの関数に切り出し、
canvas の `aria-label` と行の属性値の両方が同じ関数を通る。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | `tradingview-cs.js` 内に `EXCHANGE:CODE` 解釈の1関数を作り、`getTickerCode()` はその呼び出しに変える | 取引所表（`exchanges` / SPEC-EL-09）とコード書式の規則が1本のまま。NFR-13 の二重管理を作らない。`getTickerCode()` の引数・戻り値・外から見た振る舞いは変えないので SPEC-CS-12 に影響しない |
| (b) | 行用に別の解釈を書く | 却下。取引所表の解釈が2箇所になる。指数・FX の除外規則（下記 4）も二重管理になる |
| (c) | いま `src/urls.js` へ移して Service Worker とも共有する | **保留 → 却下で確定（2026-08-29）**。採択時は「共有先の決定は FR-14 の設計（ticker-code.md）に属する」として判断を預けた。**FR-14 側（ADR-0009 の 3）が「入力の性質が違う」として共有を却下**したため、`tradingview-cs.js` 内に置いたままで確定した |

採用案の実装（1.15.0）は `parseExchangeSymbol(text)`。`getTickerCode()` は
`parseExchangeSymbol($(selectorOf('chart-canvas')).attr('aria-label'))` の1行になり、
行の属性値も同じ関数を通る。

`aria-label` は `TSE:7203 の 1 日 チャート` で、行の属性値は `TSE:8253` と長さが違うが、
解釈は**先頭からの前方一致**（`/^([A-Z]+)(_DLY)?:/` ＋ 先頭のコード書式）なので
**同じ関数がそのまま両方に通る。**

### 追補1（2026-08-29 / レビュー指摘）: 入力の性質が違う分を境界で埋める

**「後続文字の有無に依存しない」は誤りだった。** 採択時の想定は「前方一致だから両方に通る」だったが、
**2つの入力は後続文字の性質が違う。**

| 入力 | コードの後ろ |
| --- | --- |
| canvas の `aria-label` | 必ず空白＋日本語が続く |
| 行の属性値 | **何も続かない。値全体がシンボル**（`BRK.B` のように区切り記号が続くこともある） |

実装当初の米国コード書式 `/^[A-Z]{1,5}/` は後続境界を持たず、`NYSE:BRK.B` から `BRK`（別企業）を
返していた。`aria-label` 側では後ろが空白なので実害が出ず、**行を通し始めて初めて表に出た。**
（この状態は 1.15.0 のコミット前に塞いだため、利用者には届いていない。
**経緯として残すのは、後続境界が無いと誤読が起きるという実例だから。**）

**決定: 米国コードに後続境界を付け、取れないものは何も返さない。**
（このときの値は `(?![A-Za-z.])`。**後続の追補2で `(?![A-Za-z./+-])` に広げた**）

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 区切り記号を境界に含める | `BRK.B` / `RDS.A` / `ALPHABET` は `{ code: null }`。**誤った銘柄より「何も出ない」を選ぶ**（0 の非対称性そのもの） |
| (b) 当時の Service Worker の `(?![A-Za-z])` に揃える | 却下。`.` を境界に含めないため `BRK.B` から `BRK` を返す。**揃えることより誤読を止めることを優先**した（後日、**SW 側がこちらに追随して揃った**。下記「その後」／追補2） |
| (c) `BRK.B` を正しく解釈できるようにする | 見送り。遷移先サイトがクラス株をどの表記で受けるか（`BRK.B` / `BRK-B` / `BRK/B`）が**サイトごとに違い、未調査**。誤った URL を開くより出さない方が軽い（**FR-08 でも「積み残し（クラス株の表記そのもの）」として範囲外**と確認された） |

**代償:** 米国のクラス株表記・6文字以上のティッカーはウォッチリストからもチャートからも開けない
（従来から開けていなかったので退行ではない）。

**その後（同日）:** 一時的にあった Service Worker との食い違いは**解消した**。
SW 側も `usCodePattern` を `(?![A-Za-z.])` にし、`BRK.B` を認識しない扱いに揃えた
（判断と実装は FR-14 側 ／ `ticker-code.md`）。

### 追補2（2026-08-29 / FR-08 の新設）: 境界を4記号に広げた

**追補1 の「揃っているのは結果であって、仕組みではない」が、そのとおりになった。**

追補1 の直後は両者とも `(?![A-Za-z.])` で**揃って見えていた**が、
**同じ穴を両方が持っていただけ**だった。`BRK-B`（Yahoo Finance 系のクラス株表記）は
どちらも `BRK` を返していた。**一致していることは正しさを意味しない。**

| 段階 | TradingView 側 | Service Worker 側 | 見かけ |
| --- | --- | --- | --- |
| 追補1 の直前 | `.` を足した | `(?![A-Za-z])` | **食い違い**（片方を直しても他方は直らなかった） |
| 追補1 の直後 | `(?![A-Za-z.])` | `(?![A-Za-z.])` | **一致。ただし両方に `-` `/` `+` の穴** |
| 追補2 の直後 | `(?![A-Za-z./+-])` | `(?![A-Za-z./+-])` | 一致（4記号すべて。**なお足りず → 追補3**） |

**決定: 境界を `.` `-` `/` `+` の4記号にする**（`(?![A-Za-z./+-])`）。
決めたのは本 ADR ではなく**要件**（FR-08）で、
「**実装は共有しないが境界の値だけは揃える**」と明文化された。

> **この決定は追補3 で置き換えた**（禁止列挙 → 許可列挙）。
> 「境界の値だけは揃える」という約束のほうは、追補3 でも変わっていない。

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 要件（FR-08）が定める4記号に合わせる | `A`（Agilent）/ `U`（Unity）/ `AA`（Alcoa）/ `BBB`（Bed Bath & Beyond）が**実在する短いティッカー**であり、「切り出した結果が短すぎるから無害」という逃げ道が無い。**`-` は本拡張の遷移先（`finance.yahoo.co.jp`）の表記**で、自分が開いたページからコピーする経路がある |
| (b) TradingView 側だけ広げる | 却下。追補1 と同じ食い違いを作り直すだけ。**FR-08 が両経路に同じ結果を要求している** |
| (c) 記号の列挙をやめ「後ろは空白か終端だけ」の許可制にする | 却下（判断は FR-08 側）。`AAPL,` `AAPL)` `AAPL's` が全て開かなくなり、**現在ふつうに使えている選択が落ちる** |

**この一致を支えているのは要件であって、コードの構造ではない。**
解釈関数は依然として共有していない（ADR-0009 の 3）。
**境界を変えるときは、必ず `src/service_worker.js` の `usCodePattern` も変えること**
（SPEC-CS-23「米国コードの後続境界」に同じ注意を置いた）。

### 追補3（2026-08-29 / FR-08 の規則の反転）: 禁止列挙をやめて許可列挙にした

**追補2 の「4記号」も足りなかった。** 禁止列挙は**列挙し忘れた後続がすべて素通りする**形で、
`BRK&B` / `BRK_B` / `BRK1`（ASCII 記号 27 種と数字）が `BRK` を返し続けていた。
さらに「非 ASCII なら許す」に緩めると、全角の連結記号（`Ｓ＆Ｐ500` → `S`、`BRK・B` → `BRK`）が塞がらない。

**決定: 向きを反転し、「切り出してよい後続だけを許す」許可列挙にする。**
許すのは**終端 / 空白・ASCII の終止記号 / 非 ASCII の `\p{L}` と全角の終止記号**（値は FR-08・SPEC-TC-02 が正本）。
決めたのは本 ADR ではなく要件（FR-08）で、利用者判断を経ている。

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 許可列挙 | **未知の後続が既定で落ちる側**になる。列挙し忘れの害が「開かない」（軽い）に倒れ、「別銘柄を開く」（重い）に倒れない。0 の非対称性と向きが一致する |
| (b) 禁止列挙のまま記号を足し続ける | 却下。**追補1 → 2 → 3 と3回続けて足りなかった**のがそのまま根拠。列挙し忘れの害が毎回「別銘柄を開く」側に出る |
| (c) 「非 ASCII なら許す」で簡潔にする | 却下。全角の連結記号（`＆` `・`）が通ってしまう。**許可側を `\p{L}` に絞る**ことで塞いだ |

**`u` フラグが必須になった。** 外すと `\p{L}` がリテラル `p{L}` になり、
**例外も lint エラーも出ないまま「非 ASCII の文字が続く形」だけが黙って落ちる**。
TradingView 側は DOM 経路に自動テストが無い（CON-08）ため、この罠は特に効く。

### この ADR が残した警告の決着

本 ADR は追補1・2 で「**揃っているのは結果であって、仕組みではない。片方を直しても他方は自動では直らない**」
と書いた。**1.15.0 でこれにコード側の歯止めが付いた。**

`tests/service-worker.spec.mjs` の
`米国ティッカーの後続境界: 3経路で同じ値 › 3経路とも同じ境界で、u フラグが付いている` が、
`src/service_worker.js` と `src/tradingview-cs.js` のソースから `[A-Z]{1,5}` を含む正規表現リテラルを取り出し、
**件数が3であること・全件に `u` フラグがあること・境界文字列が完全一致すること**を固定する。

**ただし、テストが守るのは「一致」であって「規則の正しさ」ではない。**
追補2 で塞いだ穴（`BRK-B`）は**3経路が揃った状態で存在していた**もので、この歯止めでは検出できない。
**3経路が同時に間違っていれば、テストは緑のまま通る。**
規則そのものの妥当性は、入力別のテスト（SPEC-TC-02 側）と要件（FR-08）が受け持つ。

| 守るもの | 手段 |
| --- | --- |
| 3経路の境界が**揃っている** | 上記の3経路テスト（1.15.0 で新設） |
| 境界の値が**正しい** | FR-08 の規則と、SPEC-TC-02 / `parseExchangeSymbol` の入力別テスト |
| 実装を共有しない判断 | ADR-0009 の 3（入力の性質が違う）。**変わっていない** |

## 4. 指数・先物・FX・暗号資産の行を落とす方法（判定基準 7）

**決定: 追加の除外リストを持たない。`exchanges`（SPEC-EL-09）に載っていない取引所トークンは
対象外、という既存の規則だけで落とす。**

| 行の例 | 取引所トークン | `exchanges` | 結果 |
| --- | --- | --- | --- |
| `TSE:8253` | `TSE` | `jp` | 対象 |
| `NASDAQ:AAPL` | `NASDAQ` | `us` | 対象 |
| `SP:SPX`（指数） | `SP` | 無し | 対象外 |
| `TVC:NI225`（指数） | `TVC` | 無し | 対象外 |
| `CME_MINI:ES1!`（先物） | `CME_MINI` | 無し | 対象外 |
| `FX:USDJPY` | `FX` | 無し | 対象外 |
| `BINANCE:BTCUSDT` | `BINANCE` | 無し | 対象外 |

| 案 | 判定 |
| --- | --- |
| **(a) 採用** ホワイトリスト（`exchanges` に載っている取引所だけ通す） | 知らない商品が増えても既定で落ちる。表は既にあり、増えるのは参照だけ |
| (b) 指数・FX 等のブラックリストを作る | 却下。TradingView が扱う市場を数え上げられない。取りこぼしが「誤ったリンクを出す」側に出る |
| (c) 銘柄コードの書式だけで判定する | 却下。`FX:USDJPY` のような値は米国株の書式（`[A-Z]{1,5}`）と衝突しうる |

**取引所が同じでも書式が合わなければ落ちる**（既存のコード書式の規則がそのまま働く）。
例: `TSE:` に続く値が4桁の銘柄コード書式でなければ対象外になる。

## 5. 行にイベントを張らない（判定基準 8）

**決定: 行にも、ウォッチリストの容器にも、イベントや `MutationObserver` を張らない。
`document` の `contextmenu`（キャプチャ）1本で受け、`closest()` で行かどうかを判定する。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | `document` で受けて `closest()` | 行が仮想スクロールで差し替わっても、切り替え後のウォッチリストでも、**張り直しが要らない**（判定基準 8 が構造的に満たされる）。監視を増やさないので NFR-01 に影響しない。**現行のチャート起点の判定と同じ1つのリスナーを拡張するだけで、リスナーが増えない** |
| (b) | 行に `contextmenu` を張り、`MutationObserver` で新しい行に張り直す | 却下。仮想スクロールの差し替えごとに張り直しが要り、漏れると「スクロール後だけ効かない」という**再現しにくい欠け方**になる。他社サイトの DOM 変化を常時受け取る負荷も増える（CON-03, NFR-01） |
| (c) | ウォッチリスト容器に張って委譲する | 却下。容器の特定にハッシュ付きクラスが要る（CON-08）。(a) に対する利点が無い |

キャプチャ段階で受けるのは現行と同じ理由（サイト側が `stopPropagation()` しても届く）。
1回の右クリックで増えるコストは `closest()` 1〜2回で、実測不要な範囲。

## 6. 行の目印を `menuSelectors` に載せるか

**決定: 載せない。`tradingview-cs.js` 内の専用定数に置く。**

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 専用定数（候補属性の配列）に置く | ADR-0002 の 3 で `div.chart-gui-wrapper` を載せなかったのと同じ扱い。**属性名が推測である段階で検証対象に載せると、`check:selectors` の ❌ が「破損」なのか「最初から間違っていた」のかを区別できない** |
| (b) `menuSelectors` に足す | 却下（現時点）。SPEC-SC-02 の検証対象が 20 → 21 に増え、`targets.mjs` にページ識別セレクタと**ウォッチリストの行を右クリックする操作**の追加が要る。加えて `check:selectors` は未ログインで走る（FR-16）ため、未ログインのチャート画面にウォッチリストの行が出るかどうかが**未確認**で、0 件が常態化しかねない |

**この判断は「行の目印をどこに定義するか」だけを決めていて、
「目印がウォッチリストの中にしか無いか」は保証していない。**
`watchlistRowSelector` はページ全体で評価されるため、銘柄検索の候補一覧・スクリーナー等が
同じ属性を持てばそこでも起点になる（FR-19 判定基準 5 に反する）。
2 と同じく**実サイト未確認**で、SPEC-CS-23「実サイトで確認すべき事項」の 6 として残し、
手動確認 A-17 で見る。ウィジェットで絞るには容器の特定が要り、そこはハッシュ付きクラスに
戻ってしまう（CON-08）ため、**実際に出る場所が分かってから**決める。

**載せ替える条件**（満たしたら架け替えを再検討する）:

1. 実サイトで属性名が確定している
2. 未ログインのチャート画面にも銘柄行が出ることが確認できている

どちらも実サイトを見ないと決まらない。**1.15.0 の時点ではどちらも未確認**で、
手動確認 A-13 で 1 を先に確定させる。

## 7. メニューの形・項目の作り方は変えない

**決定: 起点の判定と銘柄の取得元だけを変え、`addTickerMenuAsync()` 以降（SPEC-CS-11 の3行、
SPEC-CS-17 の入れ子、SPEC-CS-18 の項目生成）には手を入れない。**

「株Link」ボタン（SPEC-CS-12）は canvas 由来のまま変えない（FR-19 の「やらないこと」）。
