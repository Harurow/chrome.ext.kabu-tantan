# ADR-0004 セレクタ検証ツールが残す「手がかり」の範囲

| | |
| --- | --- |
| 状態 | 採択（2026-08-23）。**1.12.0 で実装** |
| 対象 | FR-12 判定基準5（＋ FR-17, FR-20, NFR-12, CON-10） |
| 仕様 | [SPEC-SC-20 / 21 / 22 / 23](../specs/selector-check.md) |
| 発端 | 2026-08-23 の2回目の実行（2回目版 `git show fcd0d9a:docs/SELECTOR-CHECK.md`）で楽天証券12ページ中5ページが ⚠️。うち4ページは**拡張機能は正常でツールが到達できていないだけ**、1ページは**本物の破損**（FR-20）。この2つを結果ファイルから区別できなかった |

---

## 0. 何を決めるのか

FR-12 判定基準5 は「残してよいもの」を**題名・見出し・主要コンテナのタグ名/id/class 名**に限った上で、
「主要コンテナとして具体的に何を拾うかは設計側で決めてよい」としている。
**拾う範囲を広げるほど CON-10（ページ内容を保存しない）・NFR-12（認証情報を残さない）に近づく。**
この緊張の落としどころを決める。

---

## 1. 「主要コンテナ」の境界

**決定: `body` の直下要素（深さ 1）を文書順に最大 5 件。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| (a) | ページ識別セレクタの祖先チェーンを辿る | **却下。失敗している場面で何も採れない。** 識別セレクタが 0 件のとき、その祖先も存在しない。⚠️（識別 0 件）はまさにその状態で、拾えるものが常に空になる |
| (b) | `main` / `#main` / `[role="main"]` 等の固定候補リスト | 却下。対象5サイトのどれにも当たらない（楽天 `div#str-main-inner` / SBI `div#main` / 楽天スクリーナー `div#resultpanel` / SBI スクリーナー `div#root` / TradingView は SPA）。サイトごとに候補を足すと `targets.mjs` が肥大し、外れると情報が 0 になる |
| **(c) 採用** | `body` の直下要素・深さ 1・最大 5 件 | **必ず何かが採れる**（`body` が空のページは無い）。深さ 1 なので本文（表の行・銘柄名）まで降りない。ログイン画面とアプリ画面はヘッダ・フッタの `id` が違うので区別が付く |
| (d) | `body` 配下を深さ 3 まで走査 | 却下。区別できる情報は (c) からほとんど増えないのに、拾う要素数が数十倍になる。要素が増えるほど「`id`/`class` にデータが埋まっている要素」を踏む確率が上がる（CON-10） |

上限 5 件の根拠: 楽天証券は `body` 直下が 3〜5 要素（ヘッダ・メイン・フッタ・計測用 `div`）。
TradingView のような SPA は 1〜2 要素。**5 件で全サイトの骨格が収まる**（2026-08-23 の DOM を目視した範囲）。

### (a) を捨てた代わりに何をするか

「どこまで一致してどこで切れたか」は (a) の狙いそのもので、これは**捨てたくない**。
そこで**セレクタ側から**同じ情報を取る方式に置き換えた（SPEC-SC-21 プレフィックス追跡）。

| | 祖先チェーン走査 (a) | プレフィックス追跡（採用） |
| --- | --- | --- |
| 失敗時に情報が取れるか | 取れない（祖先が無い） | **取れる**（セレクタは常に手元にある） |
| 出力する情報の種類 | 要素の `id`/`class`（新規） | セレクタ文字列と件数（**既に SPEC-SC-14 が許可済み**） |
| 情報漏れの危険 | あり | **ゼロ**（元のセレクタの部分文字列しか出ない） |

**結果として、切り分けの主役はプレフィックス追跡、`body` 直下の骨格は
「別のページに着いていないか」を見る補助**という役割分担になった。

## 2. 題名にセッション ID・URL が混ざる場合の検出

**決定: パターン照合で疑いを検出し、当たったら題名を丸ごと記録しない。**

FR-12 は「題名にセッション ID・URL が含まれている場合は記録しない」とだけ書いており、
検出方法を定義していない。

| 案 | 内容 | 判定 |
| --- | --- | --- |
| (a) | 既知形式（`BV_SessionID=…` 等）を除去して残りを記録する | 却下。除去は「取りこぼしたら漏れる」点でパターン照合と同じ危険度なのに、**伏せ字だらけの題名は人が読めず**、残す価値だけが消える |
| **(b) 採用** | 4種類のパターンのどれかに当たったら**丸ごと記録しない** | 取りこぼしの危険は (a) と同じ。しかし**記録されたものは無加工で読める**ので、題名を残す目的（人がどのページか判断する）を損なわない |
| (c) | 常に記録しない | 却下。FR-12 が「唯一の本文テキストとして許す」と明示的に認めている情報を捨てることになり、⚠️ の切り分けができなくなる |
| (d) | 判定せず常に記録する | 却下。FR-12 違反 |

パターンは5つ（URL・既知のセッションパラメータ名・クエリ文字列様・20文字以上の英数字列・UUID 形）。
**取りこぼしは残る前提**で、判定を `diagnostics.mjs` の純関数 1 箇所に閉じ、
実例を観測したらパターンを足せるようにする（SPEC-SC-22）。

> 対象4サイトの題名は日本語の固定文言で、2026-08-23 時点でセッションが混ざる実例は観測していない。
> 「起きないと分かっている」のではなく「起きたら足せる」形にした。

### 記述子の `id` / `class` にも同じパターンを適用する

**決定: 同じパターン配列を使い、当たったトークンだけを `<withheld>` に置き換える。**

題名だけを厳しく見ても、`<div id="form_BV_SessionID_…">` のような `id` / `class` から漏れれば
NFR-12 / CON-10 を満たさない。一方で扱いは題名と変える。

| 対象 | 当たったときの扱い | 理由 |
| --- | --- | --- |
| 題名 | 丸ごと不記録 | 自然文なので一部を伏せると読めなくなる（上表の (a) 却下理由） |
| `id` / `class` トークン | **そのトークンだけ**伏せる | 識別子の列挙なので、1個伏せても他の `class`・タグ名・件数で切り分けできる |

| 案 | 判定 |
| --- | --- |
| (a) 記述子用に別のパターン配列を持ち、誤検知しないよう緩める | 却下。判定が2系統に分岐し、実例を観測したときに**両方に足す**必要が出る。「判定を1箇所に閉じる」という本節の決定が崩れる |
| **(b) 採用** 題名と同じ配列を使い、誤検知を許容する | 誤検知しても失うのはトークン1個。**手がかりは補助情報で判定・終了コードに影響しない**（下記 4）ので、伏せすぎても実害が小さい |

実測では `financialInformationTableWrapper`（31文字の camelCase）や `csrfTokenLink` が誤検知するが、
対象5サイトが現に使う `id` / `class` は1つも当たらない（SPEC-SC-20）。
「伏せすぎて読めない」が実運用で起きたら、**パターン4 だけをトークン用に条件付ける**逃げ道を残す。

## 3. 出力先を備考列にするか節にするか

**決定: 要約1行だけ備考列、詳細は対象ごとの節。**

| 案 | 判定 |
| --- | --- |
| (a) すべて備考列に `<br>` 区切りで詰める | 却下。1セルが数百文字になり、表全体が読めなくなる。⚠️ が5件出た 2026-08-23 の結果では致命的 |
| (b) すべて節に出す | 却下。表を見ただけでは手がかりの有無が分からず、節まで目を移す動機が生まれない |
| **(c) 採用** 備考にプレフィックス追跡の1行要約、節に全体 | 表を上から読んで「どこで切れたか」が分かり、必要なら節へ降りられる。既存の「追加検査」節（SPEC-SC-12）と同じ作りで、`report.mjs` の構造を増やさない |

---

## 4. 判定・終了コードへの影響

**決定: 手がかりは判定にも終了コードにも影響させない。**

手がかりの採取が失敗しても、判定は SPEC-SC-10 の表どおりに決める。
理由: 手がかりは人が読むための補助情報であり、これで判定が変わると
「ツールの都合で ❌ が ⚠️ になる」経路が生まれ、FR-12 判定基準3（機械的に区別できること）が濁る。
