## 0. 何が起きているか

入れ子の項目 `<tr>` は次の形（SPEC-CS-17）。

```html
<tr class="{accessible} {item}" data-role="menuitem" tabindex="-1">   ← click で Esc を送る(閉じるだけ)
  <td class="{iconCell}"></td>                                        ← 文字が無い
  <td><div class="{content}"><span class="{label}">
    <a href="…" target="_blank">株探/基本情報で開く</a>                ← ここだけが開く
  </span></div></td>
</tr>
```

**行に付いているハンドラは「メニューを閉じる」しかしない。** 開くのは `<a>` だけ。
だから文字の外を押すと**閉じるだけで何も起きない**。
行はホバーでハイライトする（サイト側の `{item}` クラス）ので、**見た目は押せると言っている。**
**この不一致が害の本体**で、「押したのに反応せず、やり直し」になる。

**初版からの構造**（FR-25「いつからの症状か」）。1.11.0 でラベルが短くなり、
文字の無い面積が広がって表面化しやすくなった。

## 1. どこにクリック範囲を広げるか

**決定: `<tr>` のハンドラで、`<a>` の外を押されたときだけ `<a>` のクリックを代行する。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | 行のハンドラで `event.target` が `<a>` の中かを見て、外なら `<a>` をクリックする | **開く経路が1本のまま**（URL・`target`・`rel` が二重管理にならない）。文字の上は今までどおり素のリンククリックで、**判定基準5 の退行が原理的に起きない**。アイコン列も上下の余白も、行の中ならすべて拾える |
| (b) | `<a>` を `display: block` にして行いっぱいに広げる | 却下。**アイコン列（左の `<td>`）は別セルなので覆えない**（判定基準1 が要求している）。行全体を1つの `<a>` で包むのは `<tr>` の中では作れない。加えて下線・ホバー範囲が変わり、見た目が TradingView の項目とずれる（FR-18 判定基準10） |
| (c) | 行のハンドラから `chrome.runtime.sendMessage({ type: 'open-url' })` を呼ぶ | 却下。**開く経路が2本になる**。同じ項目なのに、押した場所によって「リンクのクリック」と「拡張のメッセージ」で別経路を通る。切断状態（NFR-14）でも挙動が割れる。URL を2箇所で持つことにもなる |
| (d) | `<td>` それぞれにハンドラを付ける | 却下。(a) と結果は同じでハンドラが増えるだけ。行に1つで足りる |

**代行できるのは `click` だけ**で、中クリック・ネイティブのコンテキストメニューは埋まらない
（下記の追補2）。**それでも (a) を採る**のは、(b) が**アイコン列を覆えない**＝
判定基準1 をそもそも満たせないため。

**「株Link」ボタンのメニュー（SPEC-CS-12）は既に行全体が反応する。**
あちらは `<tr>` に直接ハンドラを付けて `openUrlAsync()` を呼ぶ作り（`<a>` を使っていない）。
**形が違うのは、あちらが「リンクではなくボタン」だから**で、揃える必要は無い（判定基準6 は非退行の確認）。

## 2. 二重に開かないための線引き

**決定: `event.target` が `<a>` の内側なら、行のハンドラは開く処理をしない。**

- 文字の上を押したとき → ブラウザが `<a>` を開く。行のハンドラは**閉じるだけ**（今までどおり）
- 文字の外を押したとき → 行のハンドラが `<a>` をクリックし、その後**閉じる**

`<a>` の中かどうかは `event.target.closest('a')` で見る。
`<a>` が見つからない項目（将来 `<a>` を持たない項目を足した場合）では**何もしない**。
**推測で別経路を開かない。**

### 追補（1.16.0 の実装）: 代行クリックの戻りを捨てる

**代行で発火した `<a>` のクリックは、同じ行まで再びバブルして戻る。**
そのままだとハンドラが2回走り、**`keyup`（Esc）を2回投げる**。

**決定: 行ごとのローカル変数（`delegating`）で、代行中に戻ってきたクリックを素通りさせる。**

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 行ローカルのフラグ | 状態が**1行1個・代行の一瞬だけ**。`try` / `finally` で必ず戻す。**利用者から見た挙動は変わらない**（開く → 閉じる、Esc は1回） |
| (b) `event.stopPropagation()` を代行クリック側で呼ぶ | 却下。**サイト側に届くはずのイベントまで止めうる**（CON-03 / NFR-01）。止める範囲が読めない |
| (c) Esc を投げる前に「もう投げたか」をメニュー単位で見る | 却下。状態の寿命がメニュー全体に広がり、次の右クリックまで持ち越す事故を作る |
| (d) 何もしない（Esc が2回でも実害は無いとみなす） | 却下。**他社サイトへ余計なキーイベントを渡さない**（NFR-01）。Esc はサイト側の閉じる処理を呼ぶ手段で、2回投げると別の動作を誘発しうる |

> **フラグは Esc の重複を防ぐためだけにある。** 開く経路が1本という 1 の決定は変わらない。

### 追補2（2026-08-30 / レビュー 🟡5）: 左クリック以外は代行しない

**代行の対象は `click` だけ。** 中クリック（`auxclick`）と右クリック（`contextmenu`）は代行しない。
その結果、**TradingView 側は「文字の外」では左クリックしか文字の上と同等にならない**
（FR-25 判定基準5 が挙げる中クリック・「リンクのアドレスをコピー」が効かない）。

| 案 | 判定 |
| --- | --- |
| **(a) 採用** 代行は `click` だけ | 合成イベントで再現できるのは実質 `click` のみ。**足りない分は「元から動かなかった」ままで、退行はしない** |
| (b) `auxclick` を拾って `<a>` へ合成イベントを投げる | 却下。合成イベントは信頼済みではなく、**ブラウザが「背景タブで開く」を実行する保証が無い**。動くかどうかが環境依存になる |
| (c) `auxclick` を拾って `sendMessage` で開く | 却下。**開く経路が2本**になる。押した場所で開き方が変わるという、本 ADR が消したばかりの不整合を別の形で作り直す |
| (d) `contextmenu` を代行する | **不可能。** 「リンクのアドレスをコピー」は**ブラウザのネイティブメニュー**で、JavaScript から開けない。`href` を持つ要素の**上で**右クリックされたときにブラウザが出すもので、`<a>` の箱の外に出す手段が無い |

**この差は手段の差から来ている。** 楽天・SBI（CSS 方式。4）は**面全体が `<a>`** なので
5つとも成立する。TradingView（JS 代行。1）は**アイコン列が別セルで `<a>` を広げられない**ため、
**JS で再現できる操作だけ**が同等になる。

> **「同じ拡張の中で押せる範囲を揃える」という利用者の判断は、左クリックについては満たされている。**
> **中クリック・コンテキストメニューまで揃えるには `<a>` の箱を広げるしかない**（追補3）。
>
> **要件側は 2026-08-30 に「クリック＝左クリック」と明示して決着した**（FR-25 判定基準1）。
> 本追補が書いているのは判定基準5 側の副次的な同等性で、**未達ではない**。

### 追補3（2026-08-30 / analyst の差し戻し）: 同じセル内を CSS で埋める案は見送り

**問い:** 「文字の外は左クリックだけ」が原理的なのは**アイコン列についてだけ**ではないか。
**文字の右の余白は同じセルの中**なので、そこだけ `<a>` の面を広げれば（楽天・SBI で採った手段）
**ネイティブのまま**中クリックもアドレスのコピーも効き、**残る制限はアイコン列だけ**になるのでは。

**指摘は正しい。** 「セルをまたげない」は**アイコン列にしか効かない理由**で、
同じセル内の余白を説明していなかった。

**決定: 現時点では採らない。実サイトで1つ測ってから判断する。**

| 案 | 判定 |
| --- | --- |
| **(a) 採用（現時点）** 何もしない | 下記の5点。**要件上の利得がゼロ**（判定基準1 は左クリックに確定）で、**リスクはサイト側 CSS 依存** |
| (b) `<a>` に `display: block` を足す | **保留。** 効くかどうかが `span.{label}` の幅で決まり、**内容幅なら何も変わらない**。効かない変更を入れると「入れたのに直っていない」状態を作る |
| (c) `{content}` / `{label}` に幅指定を当てて確実に届かせる | 却下。**模倣用クラスを機能の前提に格上げする**（SPEC-CS-16 / ADR-0002 の 6 が「崩れても機能は落ちない」と決めた線を越える）。TradingView のリリースごとに**押せる範囲が壊れうる** |
| (d) `<a>` を絶対配置でセルいっぱいに広げる | 却下。祖先に `position: relative` が要る＝**サイト側の要素を触る**。(c) と同じ問題に加え、重なりで矢印やハイライトを隠す危険がある |

**(a) の理由（5点）:**

| # | 理由 |
| --- | --- |
| 1 | **効くかどうかがサイト側の CSS 次第。** 親行では同じ `{content}` の中でラベルと矢印が左右に分かれており、`{label}` は内容幅である可能性が高い。その場合 (b) は無効 |
| 2 | **確実にするには (c) が要り、それは設計の線を越える**（模倣用クラスは検証対象外という前提） |
| 3 | **見た目を変えない保証を測れない**（CON-08。行の高さ・矢印の位置。FR-18 判定基準10） |
| 4 | **要件上の利得がゼロ。** 判定基準1 は左クリックに確定し、判定基準5 は「文字の上で退行しないこと」しか求めない |
| 5 | **1.16.0 の修正自体が実サイト未確認。** 未確認の土台の上にサイト側 CSS 依存の変更を積むのは順序が逆 |

**再検討の条件:** A-11 の実施時に **`<a>` の右端と `<td>` の右端**を比べ、
**`<a>` が既にセル幅いっぱいなら (b) を採る**（`display: block` を足すだけで余白が埋まり、
中クリックとアドレスのコピーが**ネイティブのまま**効く）。文字幅しかなければ現状のまま。

> **「やらない」を選んだのは、変更が悪いからではなく、
> 効くかどうかが測れていないから。** 測る手順は1つで、A-11 のついでに済む。

## 3. 閉じる処理は変えない

現在は `document` に `keyup`（`keyCode: 27`）を投げてサイト側にメニューを閉じさせている。
**この方法は変えない**（CON-03。サイト側の閉じる API は呼べない）。

- 判定基準4 は「行のどこを押しても閉じる」。**現在の行ハンドラが既にそうなっている**ので、
  順序（開く → 閉じる）だけを守る
- **閉じる処理を先に走らせない。** 先に閉じると `<a>` が DOM から外れ、代行クリックが空振りする

## 4. 楽天証券・SBI証券のリンクメニュー（`linkMenu.js`）

**決定: 対象に含める（利用者判断 2026-08-30）。ただし手段は TradingView と変える。
こちらは CSS だけで済ませ、ハンドラを増やさない。**

当初は対象外にしていた。(1) 利用者からの報告が無い、(2) 押しても**メニューが閉じない**ので
「やり直しになる」害が無い、(3) 余白が狭い、という違いがあったため。
**(2) は今も変わらない**が、「同じ拡張の中で押せる範囲が場所によって違う状態を残さない」
という判断で取り込んだ（FR-25 判定基準 2-d）。

DOM はこう（SPEC-CS-03）。**セルが分かれておらず、文字の外は「文字の右側」だけ。**

```html
<li class="x-kabu-menu-item" style="margin: 3px 6px">
  <a title="…" target="_blank" rel="noopener noreferrer" href="…">株探/基本情報</a>
</li>
```

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a) 採用** | CSS で `<a>` を `display: block` にし、`<li>` の内容ボックスいっぱいに広げる | **ハンドラを1つも増やさない**（NFR-01。注入先サイトのイベントに触れない）。`<li>` は既に `display: block; width: 100%` なので、`<a>` を block にするだけで文字の右も上下も `<a>` の中に入る。**二重に開く経路が生まれない** |
| (b) | TradingView と同じく `<li>` にハンドラを付けて `<a>` のクリックを代行する | 却下。**注入先サイトの DOM にハンドラを増やす**必要が無い。CSS で足りるところにイベントを足すと、サイト側のイベントとの干渉（NFR-01 / 判定基準7）を新たに考えることになる |
| (c) | `<li>` 全体を `<a>` で包む | 却下。DOM 構造が変わり、SPEC-CS-03 の構造・自動テストのセレクタ（`li.x-kabu-menu-item a`）が両方動く。得るものが (a) と同じ |

**なぜ TradingView と手段が違うのか。** TradingView の項目は
**アイコン列が別の `<td>`** で、CSS では `<a>` をセルをまたいで広げられない（1 の (b)）。
`linkMenu.js` の項目は `<li>` 1つで、CSS で足りる。
**要件が揃えるよう求めているのは利用者から見た挙動であって、実装の手段ではない。**

## 5. 隣の項目を開かせない（判定基準6）

**決定: 押せる範囲は `<li>` の**内容ボックス**まで。項目間の隙間は押せないままにする。**

`<li>` はインラインスタイルで `margin: 3px 6px`（SPEC-CS-03）。**マージンは要素の外側**なので、
`<a>` を `display: block` にしても**隙間はクリック範囲に入らない**。
`padding` を足して行を大きくする案は採らない（FR-25 の「やらないこと」＝見た目を変えない、
と判定基準6 の両方に抵触する）。

TradingView 側も同じ。代行するのは**行（`<tr>`）の中で起きたクリックだけ**で、
行の外は `<tr>` のハンドラに届かない。

## 6. 楽天・SBI 側は自動テストで固定できる

TradingView はフィクスチャで実サイトとの乖離を検出できない（CON-08）ため `manual` のままだが、
**`linkMenu.js` の項目は既存の自動テストの延長で固定できる**
（`tests/content-script.spec.mjs` が実オリジンのフィクスチャでメニューを開いている）。

- **仕様が決めるのは「文字の外を押したときに、文字の上と同じ URL へ行くことを自動テストで検知できること」まで。**
  どう書くか（座標指定のクリックか、要素の当たり判定の検査か）は developer に委ねた（NFR-08）
- **判定基準6（隙間で隣が開かない）も同じテストで見られる**位置にある

**実装された形（1.16.0）:** `<a>` の箱と、その中の**文字の矩形**（`Range`）を実測し、
**文字の外がいちばん広い項目**を選んで押す。**タイトルの長さ・設定の並び順に依存しない。**
CSS を `display: inline` に戻すとテストが落ちることも確認済み（**空振りしていない**ことの担保）。
詳細は SPEC-CS-25。
